# Smart Tender — Java 业务平台 设计

## 系统定位

Java 后端的角色是**薄业务网关**：处理认证授权、CRUD 资源管理、文件存储，所有 AI 智能负载（文档解析、Multi-Agent 审核、对话、搜索）透明转发给 Rust 引擎（`127.0.0.1:3001`）。

```
前端 (React)
    │
    ▼
┌─ Java Spring Boot (:8080) ────────────────────────────┐
│                                                        │
│  ┌──────────┐  ┌──────────┐  ┌──────────────────────┐ │
│  │ 认证鉴权  │  │ CRUD 管理 │  │  审核任务编排          │ │
│  │ JWT +    │  │ 项目/标书 │  │  创建→调度→监听→汇总  │ │
│  │ 拦截器    │  │ /知识库   │  │                      │ │
│  └──────────┘  └──────────┘  └──────────┬───────────┘ │
│                                          │              │
│  ┌──────────────────────────────────────┘              │
│  │  透明代理层 (RustApiClient / RustSseClient)          │
│  └──────────────────────────┬─────────────────────────┤
│                              │                          │
└──────────────────────────────┼──────────────────────────┘
                               │ HTTP + SSE
                               ▼
┌─ Rust AI Engine (:3001) ─────────────────────────────┐
│  文档解析 → Chunk 切分 → Embedding → Multi-Agent 审核   │
└───────────────────────────────────────────────────────┘
```

> **为什么 AI 逻辑不放在 Java 里？** Rust 引擎负责所有 LLM 调用、Agent 框架、嵌入计算——这些是 CPU 密集 + 长连接操作。Java 的强项是 Web 层的事务管理、权限校验、CRUD 模板化，让 Java 做它擅长的事。

## 1. 认证与鉴权

### 为什么不用 Spring Security？

| 维度 | Spring Security | 当前方案 (HandlerInterceptor) |
|------|----------------|------------------------------|
| 学习曲线 | 陡峭（Filter 链、SecurityContext、10+ 配置类） | 平（一个拦截器 + ThreadLocal） |
| 代码量 | 至少 3 个配置类 | 2 个文件 |
| 灵活性 | 需要理解框架约定 | 完全手控 |
| 依赖 | 引入整个 security 生态 | 零额外依赖 |
| 适用场景 | 多角色、多权限、OAuth2 | 单一 Bearer Token 校验 |

当前系统只需**登录 → 签发 JWT → 请求带 Token → 解析用户 ID**，无需 RBAC、无需 OAuth2。一个 80 行的拦截器足够。

### 认证流程

```
POST /api/auth/login {username, password}
    │
    ▼
UserServiceImpl.login()
    │
    ├── MD5(password) → 比对数据库
    ├── JwtUtil.createJWT(userId) → 签发令牌（HS256，24h 过期）
    └── 返回 {token, userId, username}

        后续请求:
        Authorization: Bearer <token>
            │
            ▼
        JwtTokenAdminInterceptor.preHandle()
            ├── 提取 Bearer token
            ├── JwtUtil.parseJWT(token) → userId
            ├── BaseContext.setCurrentId(userId)   ← ThreadLocal
            └── return true
```

### 关键设计决策

- **MD5 而非 bcrypt**：早期快速实现的选择。生产环境应升级为 `BCryptPasswordEncoder`。
- **密钥硬编码**：`"smart_tender_secret_key_123456"` 同时出现在 `UserController` 和 `JwtTokenAdminInterceptor`。应抽取为配置项并通过环境变量注入。
- **无 Token 刷新机制**：当前 `/api/auth/refresh` 端点已定义但未实现真正的 refresh token 模式。
- **登出**：将 token 加入 Redis 黑名单（TTL = token 剩余有效期）。

## 2. 审核任务生命周期

这是整个系统最核心的业务流程——从用户上传标书到拿到审核报告。

```
用户点击"开始审核"
    │
    ▼
┌─ 阶段 1: 创建任务 ──────────────────────────────────────┐
│                                                         │
│  AuditTaskController.createTask()                       │
│    ├── 校验 bidId 存在                                  │
│    ├── 生成 taskId (UUID)                               │
│    ├── INSERT audit_task (status=PENDING, stage=UPLOADING) │
│    └── @Transactional 提交                              │
│                                                         │
│  TransactionSynchronizationManager.afterCommit()        │
│    └── dispatcher.dispatch(taskId)                      │
│        ├── Async: auditTaskExecutor.submit(() -> ...)   │
│        ├── Redis List: LPUSH queue:audit:tasks          │
│        └── Redis Stream: XADD queue:audit:tasks * ...   │
│                                                         │
└─────────────────────────────────────────────────────────┘
    │
    ▼
┌─ 阶段 2: 引擎执行 (@Async) ─────────────────────────────┐
│                                                         │
│  AuditEngineServiceImpl.start(taskId)                   │
│                                                         │
│  Step 1 — 上传文档到 Rust                               │
│    rustDocumentService.ensureUploaded(bidId)            │
│    ├── 检查 Tender.rustDocumentId 是否已有              │
│    ├── 没有 → RustApiClient.uploadDocument(file)        │
│    └── 更新 Tender.rustDocumentId                       │
│                                                         │
│  Step 2 — 发起 Rust 审核 + SSE 中继                      │
│    RustSseClient.connectAndRelay(taskId, callback)      │
│    ├── POST /api/review/start → Rust 返回 SSE URL       │
│    ├── 连接 Rust SSE 流                                 │
│    └── callback.onEvent(event) → SseHub.emit(taskId, event) │
│                                  → 持久化 audit_task_event │
│                                                         │
│  Step 3 — 收集 findings → issues                        │
│    RustSseClient 收到 COMPLETE 事件                     │
│    ├── RustApiClient.getReviewResult(taskId)            │
│    ├── 映射 RustRiskFinding → AuditIssue (12 个字段)     │
│    └── batch INSERT audit_issue                         │
│                                                         │
│  Step 4 — 完成                                          │
│    ├── UPDATE audit_task SET status=COMPLETED           │
│    └── SseHub.emit(taskId, COMPLETE)                    │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### 任务状态机

```
PENDING(0) ──→ PROCESSING(1) ──→ COMPLETED(2)
                    │
                    └──────────→ FAILED(3)
                    (异常或超时，记录 errorMsg + failedStages)
```

### 为什么事务提交后才 dispatch？

任务创建（INSERT `audit_task`）必须在 dispatch 前落库。如果 dispatch 在事务内：

- dispatch 成功、事务回滚 → Rust 引擎审核了不存在的任务
- dispatch 失败、事务提交 → 任务永远停留在 PENDING

`TransactionSynchronizationManager.afterCommit()` 保证 dispatch 只在事务确认落库后触发。

## 3. 任务队列：策略模式

审核是长任务（分钟级），需要在后台异步执行。不同部署场景需要不同的调度方式：

| 模式 | 实现类 | 适用场景 |
|------|--------|---------|
| **Async** (默认) | `AsyncAuditTaskDispatcher` | 单机部署，开发环境 |
| **Redis List** | `RedisListAuditTaskDispatcher` | 多实例，BLPOP 阻塞轮询 |
| **Redis Stream** | `RedisStreamAuditTaskDispatcher` | 多实例，消费者组 + ACK 机制 |

```
interface AuditTaskDispatcher {
    void dispatch(String taskId);
}

┌──────────────────────────┐
│ AsyncAuditTaskDispatcher  │  ← @Async("auditTaskExecutor")
│                           │    线程池: core=2, max=4, queue=100
│                           │    拒绝策略: CallerRunsPolicy
└──────────────────────────┘

┌──────────────────────────────┐
│ RedisListAuditTaskDispatcher │  ← LPUSH + BLPOP
│                              │    Worker 线程阻塞等待
│                              │    简单可靠，无 ACK
└──────────────────────────────┘

┌────────────────────────────────┐
│ RedisStreamAuditTaskDispatcher │  ← XADD + XREADGROUP
│                                │    消费者组: smart-tender-group
│                                │    ACK + PEL 重试 + DLQ
│                                │    支持 maxRetry=3
└────────────────────────────────┘
```

### 配置切换

```yaml
# application.yml
audit:
  queue:
    mode: async          # async | redis-list | redis-stream
    stream-key: queue:audit:tasks
    consumer-group: smart-tender-group
    block-ms: 5000
    max-retry: 3
```

### 为什么需要三种模式？

- **开发阶段**：Async 模式零外部依赖，`mvn spring-boot:run` 即可工作
- **单机生产**：Async 够用，但不支持优雅重启（正在执行的任务丢失）
- **多实例生产**：Redis List/Stream 提供任务分发和故障恢复。Stream 比 List 多了 ACK 和死信队列，适合需要审计追溯的生产环境。

## 4. SSE 实时推送

前端需要实时看到审核进度（正在审查哪个条款、发现了什么问题）。技术选型：

| 方案 | 结论 |
|------|------|
| **SSE (Server-Sent Events)** | ✅ 采用 — 单向推送、HTTP 原生、自动重连 |
| WebSocket | ❌ 全双工不需要（前端只需接收，指令走 REST） |
| 轮询 | ❌ 延迟高、浪费带宽 |

### 架构

```
Rust SSE Stream ──→ RustSseClient ──→ callback.onEvent(event)
                                           │
                                           ├── SseHub.emit(taskId, event)
                                           │     └── ConcurrentHashMap<String, SseEmitter>
                                           │         每个 taskId → 多个 SseEmitter（多个浏览器标签页）
                                           │
                                           └── AuditTaskEventService.save(event)
                                                 └── INSERT audit_task_event
```

### 断线重连（Last-Event-ID）

```
前端断开重连:
  GET /api/audit-tasks/{taskId}/stream
  Header: Last-Event-ID: 42
      │
      ▼
  AuditTaskEventService.replayEventsSince(taskId, 42)
      ├── SELECT * FROM audit_task_event WHERE taskId=? AND id>42 ORDER BY id
      └── 先推送历史事件，再接入实时流
```

### SSE 事件类型

```java
public enum SseEventTypeEnum {
    PROGRESS,        // 进度更新（百分比 + 当前阶段描述）
    ISSUE,           // 发现问题（实时推送单条 issue）
    AGENT_PROGRESS,  // Agent 级别进度（哪个 Agent 在审哪个条款）
    TRACE,           // 审查追溯事件（ReAct 步骤详情）
    PHASE,           // 阶段切换（UPLOADING → REVIEWING → SUMMARY）
    STATS,           // 统计信息（已审条款数 / 发现问题数）
    COMPLETE         // 审核完成
}
```

## 5. Rust 引擎透明代理

### RustApiClient — 同步 HTTP 代理

```
Java                                         Rust (:3001)
──────                                       ─────────────
POST /api/audit-tasks/{id}/result      →    GET  /api/review/{id}/result
POST /api/chat                         →    POST /api/chat
POST /api/audit-tasks/{id}/blocks      →    GET  /api/review/{id}/blocks
GET  /api/chat/history                 →    (本地 DB 查询)
```

使用 JDK 11 `HttpClient`（非 OkHttp/Retrofit），保持依赖最小化。连接超时 5s，读取超时 900s（审核最长 15 分钟）。

### RustSseClient — SSE 流中继

最复杂的代理组件——连接 Rust 的 SSE 流，解析事件，通过回调函数桥接到 Java 的 `SseHub`：

```
RustSseClient.connectAndRelay(taskId, callback)
    │
    ├── 1. POST /api/review/start → 获取 Rust SSE URL
    │
    ├── 2. HttpClient.newHttpClient()
    │       .send(HttpRequest.newBuilder(SSE_URL).GET().build(),
    │              BodyHandlers.ofLines())     ← 流式读取
    │
    └── 3. 逐行解析 SSE 协议:
            "data: {...json...}\n\n"
              │
              ▼
            callback.onEvent(event) → SseHub + DB
```

### RustDocumentService — 文档生命周期管理

确保标书文件在 Rust 引擎中已上传（懒上传 + 断线重连）：

```
ensureUploaded(bidId)
    │
    ├── Tender.rustDocumentId 已存在?
    │   ├── 是 → 验证 Rust 端文档状态
    │   │   ├── 200 → 直接返回 rustDocumentId ✅
    │   │   └── 404 (Rust 重启丢失) → 重新上传
    │   └── 否 → RustApiClient.uploadDocument(file)
    │           └── 更新 Tender.rustDocumentId
```

### 降级策略

```
getResult(taskId):
    ├── 1. RustApiClient.getReviewResult(taskId)  ← 优先
    │   └── 成功 → 返回 Rust 内存中的 findings
    │
    └── 2. 失败 (Rust 未运行/已重启) → fallback
        └── SELECT * FROM audit_issue WHERE auditId=?  ← DB 兜底
```

Rust 审核结果存在内存中，重启即丢失。Java 在收到 COMPLETE 事件时已将 issues 持久化到 MySQL，所以 DB 兜底总是可用的。

## 6. 数据库设计

### ER 概览

```
sys_user 1──N project 1──N bid_document 1──N audit_task 1──N audit_issue
                                    │            │
                                    │            1──N audit_report
                                    │            1──N audit_task_event
                                    │
                                    1──N chat_message
                                    │
                                    1──N trace_session 1──N trace_event 1──N trace_event_block
```

### 核心表

| 表名 | 核心字段 | 说明 |
|------|---------|------|
| `sys_user` | id, username, password(MD5), real_name, email | 用户表 |
| `project` | id, user_id, project_name, supplier_name | 项目（一个项目有多个版本标书） |
| `bid_document` | id, file_name, file_path, version, project_id, rust_document_id | 标书文件（`rust_document_id` 是 Rust 引擎文档 UUID） |
| `audit_task` | id, task_id(UUID), bid_id, task_status(0-3), stage, progress, version(@Version) | 审核任务（乐观锁防并发） |
| `audit_issue` | id, audit_id, issue_no, severity, category, description, suggestion, page_number | 审核发现的问题 |
| `audit_report` | id, audit_id, doc_content(Markdown), version | 审核报告 |
| `audit_task_event` | id, task_id, event_type, event_data(LONGTEXT) | SSE 事件持久化（断线重连回放） |
| `chat_message` | id, project_id, bid_id, user_id, role( user/assistant), content | 对话历史 |
| `knowledge_file` | id, file_name, file_path, category, status | 知识库文件（标准范本库） |
| `trace_session` | id(UUID), task_id, agent_name, clause_id, severity, total_turns | Agent 审查追溯（一个 Agent 审一个条款 = 一条） |
| `trace_events` | id, event_id(UUID), session_id, agent_name, event_type, turn, payload(JSON) | ReAct 步骤详情 |
| `trace_event_blocks` | id, event_id, block_id | JSON block ID → PDF 高亮坐标关联 |

### 关键设计决策

**JSON 列 + 自定义 TypeHandler**：`audit_task.enabled_checks` 和 `audit_task.failed_stages` 是 `List<String>`，在 MySQL 中存为 JSON 字符串，通过 `StringListJsonTypeHandler` 自动序列化/反序列化。比建关联表简单，适合"配置型"数据（不会单独查询列表中的单个元素）。

**乐观锁**：`audit_task.version` 字段 + `@Version`。审核引擎在多个步骤中更新同一行（progress、stage、status），乐观锁防止并发更新覆盖。

**无 XML Mapper**：所有查询通过 MyBatis-Plus `LambdaQueryWrapper` 程序化构建。理由是：① 查询模式简单（单表 CRUD + 简单分页），不需要复杂 SQL；② 编译期类型安全（Lambda 引用字段名而非字符串）。

## 7. 文件管理

### 存储路径策略

```java
// StoragePathService — 多路径 Fallback
@Value("${storage.root-path}")          // D:/smart-tender/data
private String storageRoot;

// 投标文件: {root}/tenders/{yyyy-MM}/{userId}/{uuid}_{filename}
// 知识库:   {root}/knowledge/{yyyy-MM}/{uuid}_{filename}
// 预览缓存: {root}/preview-cache/{sha256}.pdf
```

### DOCX → PDF 预览转换

```
TenderController.download(id, preview=true)
    │
    ├── 文件已是 PDF? → 直接返回 ✅
    │
    └── 文件是 DOCX?
        │
        ▼
    DocumentPreviewService.convertToPdf(docxFile)
        ├── 计算文件 SHA-256
        ├── 检查缓存: {preview-cache}/{sha256}.pdf 存在? → 返回缓存 ✅
        └── 未缓存 → POST http://jodconverter:8080/lool/convert-to/pdf
                    └── 结果写入缓存目录
```

使用 **JODConverter**（LibreOffice Online REST封装）而非本地 LibreOffice headless。优点：Docker 化部署、HTTP 接口、零本地依赖。
