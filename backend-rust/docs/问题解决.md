# 双标书 Chunk 质量问题 — 解决方案设计

> 基于 2026-06-23 验证报告，对 4 个确认问题逐一设计修复方案。
> 核心原则：**从管道整体视角出发，让每个环节各司其职，避免打补丁式局部修复。**

---

## 管道全景

```
PDF → pdf_extract_service → RawDocument { pages: [{ blocks, tables }] }
  → sectionize_service   → Section tree (仅消费 blocks，忽略 tables)
  → chunking_service     → Chunk list
  → main.rs              → 孤儿块兜底 push（绕过切分管线）
```

**根因诊断**：当前管道有三个"断头路"——

1. **Tables 被提取但从未消费** — `RawTable` 在 `RawPage.tables` 中完整存在，但 sectionize 和 chunking 只看 `blocks`
2. **孤儿块绕过了切分管线** — `main.rs:314` 直接 `chunks.push()`，不经 `split_long_chunk()` 也不经 `merge_tiny_chunks()`
3. **纯标题 Section 被静默丢弃** — `traverse_and_chunk` 对 `body_text` 为空 + 无子节点的节点直接 `return`
4. **merge_tiny_chunks 只有单向合并** — 前向失败后不尝试后向

---

## 方案一：孤儿块融入切分管线（P0）

### 现状

[main.rs:312-322](src/main.rs#L312-L322)：

```rust
let orphan_ids: Vec<String> = orphan_blocks.iter().map(|b| b.id.clone()).collect();
chunks.push(ai_bid::domain::chunk::Chunk {
    chunk_id: String::new(),
    chunk_type: ai_bid::domain::chunk::ChunkType::Leaf,
    section_path: vec!["未归类内容".to_string()],
    text: orphan_text,                    // ← 可能是 1904 chars！
    // ...
});
```

这段代码直接构造了一个 Leaf chunk，**绕过了 `split_long_chunk()`**（规则 4），也**绕过了 `merge_tiny_chunks()`**（后处理）。如果 orphan_text 超过 1500 字符（如清华大学 ch_000 = 1904 chars），就会产生违规超大 chunk。

### 方案

**将孤儿块包装为临时 `Section`，追加到 sections 列表中，一起送入 `chunk_sections()`。** 这样孤儿文本会经过完整的规则 1-4 + 后处理管线。

### 修改点

**文件**：`src/main.rs`，第 259–329 行

**改动**：将孤儿块处理从"构造裸 Chunk"改为"按连续页码分组构造临时 Section 并追加到 sections 列表"。

**关键设计决策**：

1. **按连续页码分组**（而非全部合并为一个 Section）：孤儿块可能分散在文档各处（如第 3、7、40 页），若全部合并为一个 Section 会导致 `page_start..=page_end` 虚假膨胀（如 3–40），使得每个 Split chunk 的 page 元数据不准确，与正常 chunk 产生虚假重叠。分组后每组 Section 的 page 范围精确反映孤儿块的实际位置。

2. **孤儿 Section 必须在表格注入之前构造**（见下方管道顺序修正）：否则孤儿块的页面上的表格不会被注入。

```rust
let chunking_config = ChunkingConfig::default();

// ─── 阶段 2.5: Orphan blocks 兜底 → 构造临时 Section 融入管线 ────
// 注意：此步骤必须在阶段 2.6（表格注入）之前执行，
// 确保孤儿 Section 也能接收表格内容注入。
// 收集所有已分配的 block_id
let assigned: std::collections::HashSet<&str> = sections_output
    .sections
    .iter()
    .flat_map(|s| collect_all_block_ids(s))
    .collect();

// 找出未分配的 orphan blocks
let orphan_blocks: Vec<&ai_bid::domain::raw_document::RawBlock> = raw_doc
    .pages
    .iter()
    .flat_map(|p| p.blocks.iter())
    .filter(|b| !assigned.contains(b.id.as_str()))
    .collect();

// 将孤儿块按连续页码分组，每组构造一个临时 Section，
// 使其走完整的 chunking 管线（含 split_long_chunk + merge_tiny_chunks）。
let mut all_sections = sections_output.sections.clone();

if !orphan_blocks.is_empty() {
    // Step 0: 构建 block_id → page_index 索引（避免 O(P×B×O) 嵌套扫描）
    let block_page: std::collections::HashMap<&str, usize> = raw_doc
        .pages
        .iter()
        .flat_map(|p| p.blocks.iter().map(move |b| (b.id.as_str(), p.page_index as usize)))
        .collect();

    // Step 1: 按页码分组 orphan blocks
    let mut page_to_blocks: std::collections::BTreeMap<usize, Vec<&ai_bid::domain::raw_document::RawBlock>> =
        std::collections::BTreeMap::new();
    for block in &orphan_blocks {
        if let Some(&page_idx) = block_page.get(block.id.as_str()) {
            page_to_blocks.entry(page_idx).or_default().push(*block);
        }
    }

    // Step 2: 将连续页码合并为组（相邻页码 → 同一组）
    let sorted_pages: Vec<usize> = page_to_blocks.keys().copied().collect();
    let mut page_groups: Vec<Vec<usize>> = Vec::new();
    let mut current_group: Vec<usize> = Vec::new();
    for &p in &sorted_pages {
        if current_group.is_empty() || p == current_group.last().unwrap() + 1 {
            current_group.push(p);
        } else {
            page_groups.push(std::mem::take(&mut current_group));
            current_group.push(p);
        }
    }
    if !current_group.is_empty() {
        page_groups.push(current_group);
    }

    // Step 3: 每组构造一个临时 Section
    for group in &page_groups {
        let group_start = *group.first().unwrap();
        let group_end = *group.last().unwrap();
        let group_blocks: Vec<&&ai_bid::domain::raw_document::RawBlock> = group
            .iter()
            .flat_map(|p| page_to_blocks[p].iter())
            .collect();
        let orphan_ids: Vec<String> = group_blocks.iter().map(|b| b.id.clone()).collect();
        let orphan_text = group_blocks
            .iter()
            .map(|b| b.text.as_str())
            .collect::<Vec<_>>()
            .join("\n");

        let orphan_section = ai_bid::services::sectionize_service::Section {
            level: 0, // 特殊层级：未归类内容
            title: format!("未归类内容 (第{}-{}页)", group_start + 1, group_end + 1),
            pattern: "orphan".to_string(),
            page_start: group_start,
            page_end: group_end,
            block_ids: orphan_ids,
            body_text: orphan_text,
            children: Vec::new(),
            body_page_start: group_start,
            body_page_end: group_end,
        };

        all_sections.push(orphan_section);
    }

    println!(
        "  已补充 {} 个 orphan block（{} 个连续页码组）兜底 Section",
        orphan_blocks.len(),
        page_groups.len()
    );
}

// 注意：此处不立即调用 chunk_sections，而是先执行阶段 2.6（表格注入），
// 再由统一的 `let mut chunks = chunk_sections(&all_sections, &chunking_config);` 处理。
// 见下方"管道顺序修正"。
```

**管道顺序修正**（与原方案的关键差异）：

原方案将孤儿 Section 构造放在 Phase 3（chunking 调用处），但方案二的表格注入在 Phase 2.6。这导致孤儿 Section 错过表格注入。**修正后的管道顺序**：

```
Phase 2:   sectionize → sections_output
Phase 2.5: 孤儿块 → 分组构造 Section，追加到 all_sections  ← 移到这里
Phase 2.6: 表格注入 all_sections（含孤儿 Section）          ← 方案二
Phase 3:   chunk_sections(&all_sections, &config)           ← 统一入口
```

在 `main.rs` 中的具体布局：

```rust
// ─── 阶段 2.5: Orphan blocks → Section（在表格注入之前）───
// （代码见上方）

// ─── 阶段 2.6: 表格内容注入 Sections ───────────────────────
ai_bid::services::sectionize_service::inject_tables_into_sections(
    &mut all_sections,
    &raw_doc,
);

// ─── 阶段 3: Sections → Chunks ────────────────────────────
let mut chunks = chunk_sections(&all_sections, &chunking_config);
```

**级联影响**：

| 下游 | 影响 | 处理 |
|------|------|------|
| `split_long_chunk` | 孤儿文本 > 1500 字会被自动切分为 Split chunks | ✅ 这正是我们需要的 |
| `merge_tiny_chunks` | 孤儿切分后的碎片（如末段 < 50 字）会被合并 | ✅ 无问题 |
| chunk_id 排序 | 孤儿块页码通常在开头，排序后 id 自动正确 | ✅ `chunk_sections` 内部已排序 |
| embed_text | path = `["未归类内容 (第3-5页)"]`，前缀正常 | ✅ 无问题 |
| 表格注入 | 孤儿 Section 先于表格注入构造 → 孤儿页面的表格也能被注入 | ✅ 管道顺序修正 |
| page 元数据 | 每组 Section 的 page span 精确，不虚假膨胀 | ✅ 连续页码分组 |

**为什么不在 chunking_service 内部改**：把孤儿处理逻辑下放到 `chunk_sections` 会增加其参数复杂度（需要传入 `RawDocument`）。保持 `chunk_sections` 只消费 `Section[]` 的纯函数语义更清晰。

## 方案二：表格内容注入管线（P0）

### 现状

- `pdf_extract_service.rs` 将 PDF 表格提取为 `RawTable`，存储在 `RawPage.tables` 中
- `sectionize_service.rs` 的 `extract_section_body()` 只从 `blocks` 中提取文本，**完全忽略 `tables`**
- `chunking_service.rs` 只消费 `Section.body_text`，对表格内容无感知

**结果**：智慧教室 44 张表格的二维结构全部丢失，单元格文本被 PDF 布局引擎挤在一起（如 `"3内墙腻子国产1、▲须符合JG/T298-2010..."`）。

### 方案

**在 `sectionize_service` 输出 Section 树之后、`chunking_service` 消费之前，增加一个表格注入步骤**：将每张表格格式化为 Markdown 表格文本，追加到所属 Section 的 `body_text`。

### 设计决策

**Q: 为什么在 sectionize 之后注入，而不是在 chunking 中处理？**

A: 分两层考虑——

1. **结构归属**：表格属于哪个 Section，由 sectionize 的页面归属逻辑决定（表格所在页被哪个 Section 覆盖）。在 sectionize 之后注入可以利用 Section 已有的 `body_page_start..=body_page_end` 范围。
2. **格式转换**：将 `RawTable.rows[][]` 转为 Markdown `| col1 | col2 |` 是纯文本处理，不依赖 chunking 逻辑。注入后的效果等同于"表格文本本来就是 body_text 的一部分"，chunking 管线零改动。

**Q: 表格的 block_id 追溯怎么办？**

A: 表格已经有自己的 `id`（如 `t_2_0`）。将其追加到 Section 的 `block_ids` 中，下游 LLM 可通过 table ID 定位到原始 PDF 位置。**注意**：需验证渲染层是否已支持 `t_*` 前缀 ID 的高亮回溯（当前 `raw_document.rs` 的 ID 命名规则只显式列出 `w_*` 和 `b_*`，`t_*` 的回溯链路可能需补充）。

**Q: 为什么要去重？同一张表格会被多个 Section 覆盖吗？**

A: 会。容器 Section 的 `page_start..=page_end` 涵盖所有子孙节点的页面范围。如果不做去重，page 15 的一张表格会被同时注入到"第五章"（page 10–50）和"5.1 技术参数"（page 12–20）两个 Section。**应对**：

1. **深度优先递归**：先递归处理子节点，再处理当前节点。这样表格优先归属到最深层（最精确）的 Section。
2. **`visited_tables` 全局去重**：已被子孙 Section 消费的表格，祖先 Section 跳过。
3. **使用 `body_page_start..=body_page_end`**：纯容器 Section（无 body_text）的 body_page 范围为空或极小，自然不会吞并子节点的表格。

### 新增函数

**文件**：`src/services/sectionize_service.rs`（或新建 `src/services/table_inject_service.rs`）

```rust
/// 将 RawDocument 中的表格内容注入到 Section 树的 body_text 中。
///
/// 对每个 Section，查找其 **body 实际页码范围**（body_page_start..=body_page_end）
/// 覆盖的页面上的表格，将表格格式化为 Markdown 表格文本，追加到 body_text 末尾。
/// 同时将表格 ID 追加到 block_ids 以便回溯。
///
/// # 去重策略
///
/// 使用全局 `visited_tables: HashSet<String>` 确保每张表格只注入一次——
/// 注入到**最先遇到**的 Section（递归深度优先，即最深层级最精确的 Section）。
/// 祖先 Section 不会重复注入已被子孙 Section 消费的表格。
///
/// # Markdown 表格格式
///
/// ```markdown
/// | 品目号 | 品目名称 | 采购标的 | 数量 | 是否允许进口 |
/// |--------|----------|----------|------|-------------|
/// | 1-1    | 教育用房施工 | 东莞理工学院... | 1(项) | 否 |
/// ```
///
/// - 单元格内的换行符替换为空格
/// - 空单元格输出为空字符串
/// - 表格之间用 `\n\n` 分隔
pub fn inject_tables_into_sections(
    sections: &mut [Section],
    raw_doc: &RawDocument,
) {
    // 构建 page → tables 索引（只读，一次扫描）
    let page_tables: std::collections::HashMap<usize, &[RawTable]> = raw_doc
        .pages
        .iter()
        .map(|p| (p.page_index, p.tables.as_slice()))
        .collect();

    let mut visited_tables: std::collections::HashSet<String> = std::collections::HashSet::new();
    inject_tables_recursive(sections, &page_tables, &mut visited_tables);
}

fn inject_tables_recursive(
    sections: &mut [Section],
    page_tables: &std::collections::HashMap<usize, &[RawTable]>,
    visited_tables: &mut std::collections::HashSet<String>,
) {
    for section in sections.iter_mut() {
        // 先对子节点按 body_page_start 排序，确保页码小的 Section
        // 优先认领边界页表格，行为确定化。
        section.children.sort_by_key(|c| c.body_page_start);

        // 先递归处理子节点（深度优先），确保表格优先归属到最深层 Section
        inject_tables_recursive(&mut section.children, page_tables, visited_tables);

        // 收集该 Section **body 实际页码范围**内的表格
        // 使用 body_page_start..=body_page_end 而非 page_start..=page_end：
        // 容器 Section 的 page_start..=page_end 涵盖所有子孙节点页面，
        // 若用此范围会吞并属于子节点的表格。body_page 范围只反映 Section
        // 自身正文的实际页面，精确归属。
        let mut table_texts: Vec<String> = Vec::new();

        for page_idx in section.body_page_start..=section.body_page_end {
            if let Some(tables) = page_tables.get(&page_idx) {
                for table in *tables {
                    // 去重：跳过已被更深层 Section 消费的表格
                    if visited_tables.contains(&table.id) {
                        continue;
                    }
                    if let Some(md) = format_table_as_markdown(table) {
                        table_texts.push(md);
                        visited_tables.insert(table.id.clone());
                        // 将 table ID 加入追溯链
                        if !section.block_ids.contains(&table.id) {
                            section.block_ids.push(table.id.clone());
                        }
                    }
                }
            }
        }

        // ── Fallback: 纯容器 Section 的 page span 扫描 ──────────
        // 纯容器 Section（无 body_text，body_page_start/end 通常为 0）
        // 其子节点覆盖的页面范围可能存在间隙（如子节点 A 覆盖 30-35 页、
        // 子节点 B 覆盖 40-60 页，第 36-39 页为容器过渡页）。
        // 这些间隙页上的表格不被任何子节点认领，也不会被 body_page 扫描
        // （body_page 为 0..=0），导致彻底丢失。
        //
        // 此处使用容器的完整 page_start..=page_end 范围做一次兜底扫描，
        // 拾取子节点遗漏的表格。由于 visited_tables 已被子节点消费过，
        // 不会造成重复注入。
        if !section.children.is_empty() && section.body_text.is_empty() {
            for page_idx in section.page_start..=section.page_end {
                if let Some(tables) = page_tables.get(&page_idx) {
                    for table in *tables {
                        if visited_tables.contains(&table.id) {
                            continue;
                        }
                        if let Some(md) = format_table_as_markdown(table) {
                            table_texts.push(md);
                            visited_tables.insert(table.id.clone());
                            if !section.block_ids.contains(&table.id) {
                                section.block_ids.push(table.id.clone());
                            }
                        }
                    }
                }
            }
        }

        if !table_texts.is_empty() {
            let table_section = table_texts.join("\n\n");
            if section.body_text.is_empty() {
                section.body_text = table_section;
            } else {
                section.body_text = format!("{}\n\n{}", section.body_text, table_section);
            }
        }
    }
}

/// 将 RawTable 格式化为 Markdown 表格字符串。
///
/// 返回 None 如果表格为空（无行或无列）。
fn format_table_as_markdown(table: &RawTable) -> Option<String> {
    if table.rows.is_empty() {
        return None;
    }

    // 计算列数（取最大行宽）
    let col_count = table.rows.iter()
        .map(|row| row.len())
        .max()
        .unwrap_or(0);

    if col_count == 0 {
        return None;
    }

    let mut lines: Vec<String> = Vec::new();

    for (row_idx, row) in table.rows.iter().enumerate() {
        let cells: Vec<String> = (0..col_count)
            .map(|col| {
                row.get(col)
                    .and_then(|opt| opt.as_ref())
                    .map(|s| s.replace('\n', " ").trim().to_string())
                    .unwrap_or_default()
            })
            .collect();

        lines.push(format!("| {} |", cells.join(" | ")));

        // 表头后添加分隔行
        if row_idx == 0 {
            let sep: Vec<String> = (0..col_count).map(|_| "---".to_string()).collect();
            lines.push(format!("| {} |", sep.join(" | ")));
        }
    }

    Some(lines.join("\n"))
}
```

**级联影响**：

| 下游 | 影响 | 处理 |
|------|------|------|
| `body_text` 长度 | 表格文本追加后 body_text 变长 | 可能触发 `split_long_chunk` — 这正是期望行为 |
| `block_ids` | 混入了 `t_*` 前缀的 table ID | `source_block_ids` 正常包含，LLM 可引用 |
| 短 Section 合并 | 含表格的短 Section 不再被合并（body_text 够长） | ✅ 合理：含表格的 Section 语义自足 |
| 表格重复注入 | 同一表格不被多个祖先 Section 重复注入 | ✅ `visited_tables` 全局去重 + 深度优先 |
| 子 Section 范围 | 使用 `body_page_start..=body_page_end` 精确归属 | ✅ 纯容器不会吞并子节点表格 |
| 孤儿 Section 的表格 | 孤儿 Section 在表格注入前已构造（见方案一管道顺序修正） | ✅ 孤儿页面的表格也能被注入 |
| 纯容器间隙表格 | 容器 fallback 扫描 `page_start..=page_end`，拾取子节点遗漏的表格 | ✅ 间隙表格不丢失 |
| 兄弟节点边界页表格 | 子节点按 `body_page_start` 排序后递归，页码小的先认领 | ✅ 行为确定化 |

**已知限制：跨页表格**：如果 PDF 中一张大表跨越多个页面（如 page 5–6），pdf_extract 会在每页各产生一个 `RawTable`。注入后会变成两张独立 Markdown 表格，而非一张连续表格。这是上游提取机制的限制，当前方案比完全丢失好，后续可考虑基于表头匹配的跨页表格合并（P2）。

**已知限制：表格 Markdown 被硬切腰斩**：表格注入后 `body_text` 变长，可能触发 `split_long_chunk`（规则 4）对 Section 进行硬切。当前 `find_para_boundaries()` 只在 `\n\n` 和中文序号处识别段落边界，Markdown 表格行之间只有单个 `\n`，**不会被识别为段落边界**。因此切分点可能落在表格中间，导致：

```
前半段: | 品目号 | 品目名称 | ... |        ← 表头+分隔行完整
        | 1-1    | 教育用房施工 | ... |    ← 数据行被拦腰截断
后半段: | 1-3    | 给排水工程 | ... |      ← 无表头，LLM 无法解析
```

**应对**：在 `find_para_boundaries()` 中增加 Markdown 表格边界识别——表格前的空行（`\n\n|` 模式）和表格后的空行（`|\n\n` 模式）作为强制段落边界，确保切分点不落入表格内部。具体修改：

```rust
fn find_para_boundaries(text: &str) -> Vec<usize> {
    // ... 现有逻辑 ...
    for i in 0..chars.len() {
        // 新增：Markdown 表格行前空行作为段落边界
        // 匹配 \n\n| 模式（空行后紧跟表格行）
        if chars[i] == '\n' && i + 1 < chars.len() && chars[i + 1] == '\n'
            && i + 2 < chars.len() && chars[i + 2] == '|'
        {
            boundaries.push(i + 1); // 在第二个 \n 之后
            continue;
        }
        // 新增：表格行后的空行作为段落边界
        // 匹配 |\n\n 模式（表格行后紧跟空行）
        if chars[i] == '\n' && i + 1 < chars.len() && chars[i + 1] == '\n'
            && i > 0 && chars[i - 1] == '|'
        {
            boundaries.push(i + 1); // 在第二个 \n 之后
            continue;
        }
        // ... 现有 \n\n 和中文序号逻辑 ...
    }
    // ...
}
```

此修改封装在 `find_para_boundaries` 中，**不改变切分服务的外部行为**，仅补充表格边界信息，确保 `split_long_chunk` 在表格前后切分而非表格内部。

**关于 `RawTable.rows` 的数据结构**：

}
```

## 方案三：merge_tiny_chunks 双向合并（P1）

### 现状

[chunking_service.rs:456-515](src/services/chunking_service.rs#L456-L515) 的 `merge_tiny_chunks` 只做前向合并（合并到 `prev` chunk）。当前向合并因 `same_parent` 失败时，碎片 chunk 被原样保留。代码末尾（494-515 行）有一个特殊后处理，但只覆盖了"第一个 chunk 是碎片"的特例。

**具体案例**：

```
ch_050 (path=["第二部分..."])  ──正常──▶  result
ch_051 (40 chars, path=["第三部分...", "一、说明"])  ──prev不匹配──▶  保留（BUG!）
ch_052 (path=["第三部分...", "一、说明"])  ──prev匹配──▶  正常push
```

`ch_051` 与 `prev`（ch_050）路径不匹配 → 合并失败 → 保留为碎片。但 `ch_051` 与 `next`（ch_052）路径匹配 → 如果尝试后向合并就能解决。

### 方案

**在前向合并（Pass 1）之后，增加反向扫描（Pass 2）**：对仍未合并的碎片 chunk，尝试合并到**后一个**相邻 chunk。

### 修改点

**文件**：`src/services/chunking_service.rs`，`merge_tiny_chunks` 函数

**改动**：在现有代码的 Pass 1（456-492 行）和特殊后处理（494-515 行）之间，插入反向合并逻辑。同时用新的反向合并逻辑**替代**现有的特殊后处理（因为反向合并可以覆盖"第一个 chunk 是碎片"的情况，消除特例代码）。

```rust
fn merge_tiny_chunks(chunks: Vec<Chunk>, config: &ChunkingConfig) -> Vec<Chunk> {
    let min = config.min_chunk_size;
    let mut result: Vec<Chunk> = Vec::new();

    // ── Pass 1: 前向合并（合并到 prev chunk）──
    for chunk in chunks {
        if chunk.text.chars().count() < min {
            if let Some(prev) = result.last_mut() {
                if same_parent(&prev.section_path, &chunk.section_path) {
                    // 合并 chunk → prev
                    prev.text = format!("{}\n\n{}", prev.text, chunk.text);
                    prev.page_end = prev.page_end.max(chunk.page_end);
                    for bid in &chunk.source_block_ids {
                        if !prev.source_block_ids.contains(bid) {
                            prev.source_block_ids.push(bid.clone());
                        }
                    }
                    let child_count = match &prev.chunk_type {
                        ChunkType::Merged { child_count: c, .. } => c + 1,
                        _ => 2,
                    };
                    prev.chunk_type = ChunkType::Merged {
                        rule: "tiny_merge".to_string(),
                        child_count,
                    };
                    continue; // 已合并，跳过 push
                }
                // ← 前向合并失败：继续执行 push，由 Pass 2 处理
            }
        }
        result.push(chunk);
    }

    // ── Pass 2: 后向合并（合并到 next chunk）──
    // 对 Pass 1 未能合并的碎片，尝试合并到后一个相邻 chunk。
    // 从后向前扫描，确保 remove 不影响后续索引。
    let mut remove_indices: Vec<usize> = Vec::new();
    for i in 0..result.len() {
        if result[i].text.chars().count() >= min {
            continue; // 不是碎片，跳过
        }
        // 尝试合并到 next chunk (i+1)
        if i + 1 < result.len()
            && same_parent(&result[i].section_path, &result[i + 1].section_path)
        {
            let next = &mut result[i + 1];
            // 将碎片内容前置到 next chunk
            next.text = format!("{}\n\n{}", result[i].text, next.text);
            next.page_start = result[i].page_start; // 扩展起始页
            for bid in &result[i].source_block_ids {
                if !next.source_block_ids.contains(bid) {
                    next.source_block_ids.insert(0, bid.clone());
                }
            }
            let child_count = match &next.chunk_type {
                ChunkType::Merged { child_count: c, .. } => c + 1,
                _ => 2,
            };
            next.chunk_type = ChunkType::Merged {
                rule: "tiny_merge".to_string(),
                child_count,
            };
            remove_indices.push(i);
        }
        // ← 双向都失败：保留独立碎片（极少发生，仅在两个不同 top-level
        //   section 之间出现孤立标题碎片时）
    }

    // 安全移除（降序）
    for &idx in remove_indices.iter().rev() {
        result.remove(idx);
    }

    // 移除原有的特殊后处理（494-515 行）——
    // Pass 2 的反向合并已经覆盖了"第一个 chunk 是碎片"的场景。

    result
}
```

### 级联影响

| 场景 | 行为 | 验证 |
|------|------|------|
| ch_051（碎片，prev 不匹配，next 匹配） | Pass 1 保留 → Pass 2 合并到 ch_052 | ✅ 修复 |
| ch_114（碎片，prev 不匹配，next 匹配） | Pass 1 保留 → Pass 2 合并到 ch_115 | ✅ 修复 |
| 第一个 chunk 是碎片 + next 匹配 | Pass 1 保留 → Pass 2 合并到 ch_001 | ✅ 消除特例 |
| 正常碎片（prev 匹配） | Pass 1 合并 → Pass 2 跳过 | ✅ 行为不变 |
| 碎片 + 双向都不匹配 | 保留独立（极少发生） | ✅ 合理降级 |
| 连续两个碎片 + 同 parent | 第一个被 Pass 1 合并到 prev → 第二个在 Pass 2 合并到 next | ✅ 正确 |
| Merged chunk 的 child_count | 双向都正确递增 | ✅ 正确 |

**已知限制：交替路径连续碎片**：当连续碎片以交替路径出现时（如 `ch1(path=[A], 30 chars) → ch2(path=[B], 30 chars) → ch3(path=[A], 30 chars)`），Pass 1 和 Pass 2 均因路径不匹配而失败，三个碎片全部残留。此场景在标书中极为罕见（"格式自拟"页通常连续出现且同属一个顶级章节），若出现则碎片独立保留，内容至少不丢失。

## 方案四：纯标题 Section 生成占位 Chunk（P1）

### 现状

[chunking_service.rs:74-85](src/services/chunking_service.rs#L74-L85) 的 `traverse_and_chunk`：

```rust

当 Section 的 `body_text` 为空且无子节点时（即"纯标题"：只有标题行，没有正文内容），该 Section 被完全丢弃。

**具体案例**：清华大学标书中"四、投标人相关资质（格式自拟）""五、投标人自主知识产权产品情况（格式自拟）""5.2、技术方案与组织实施（格式自拟）"等页面——这些是留给投标人填写的空模板，只有标题没有正文。它们的标题文本（如"技术方案与组织实施（格式自拟）"）没有出现在任何 chunk 中。

### 方案

**在丢弃纯标题 Section 之前，检查标题是否非空。如果非空，生成一个最小 Leaf chunk（仅含标题文本）。**

这样的最小 chunk 随后会经过 `merge_tiny_chunks`，可能会被合并到相邻的同路径 chunk（类似"格式自拟"页面被合并到 `第五部分投标文件格式` 容器 chunk），从而保留模板结构信息。

### 修改点

**文件**：`src/services/chunking_service.rs`，`traverse_and_chunk` 函数，第 83-84 行

**改动**：

```rust

## 方案五：启发式表格检测（P1 — 弥补 pdfplumber 盲区）

### 问题

方案二只消费 `RawPage.tables` 中已有的表格。但对于清华大学标书，Rust pdfplumber **完全没有检测出任何表格**（检测率 0%），所以方案二对清华大学完全无效。

然而，`analyze_chunks.py` 发现清华大学 raw JSON 中有 **~319 个含 `|` 分隔符的 block**——这些是 PDF 中的表格内容，以混乱的文本形式存在于 `RawBlock` 中（如 `"序号|名称|规格|数量\n1|教育用房|..."`）。

### 方案

在 pdf_extract 和表格注入之间，增加一个**启发式表格检测模块**：扫描 blocks 中连续多行含 `|` 分隔符且列数一致的段落，将其识别为"伪表格"，转为 `RawTable` 结构后合并到 `raw_doc.tables` 中。后续方案二的 `inject_tables_into_sections` 即可正常消费。

### 设计决策

**Q: 为什么不修复 pdfplumber 本身？**

A: Rust pdfplumber 的表格检测基于边框线/矩形定位，对纯文本型表格（无边框线、仅靠 `|` 分隔）的检测是已知上游限制。修复上游库代价高、周期长。启发式模块以 ~50 行代码换来立即可用的结果，且不影响已有功能。

**Q: 会不会误判正文为表格？**

A: 有风险。通过以下约束降低误判率：
1. **至少 2 行连续**——单行 `|` 分隔符可能是正文中的分隔线符号
2. **列数一致**——相邻行的 `|` 分隔出的列数必须相同
3. **最小列数 ≥ 2**——单列不是表格
4. **所在 block 类型为 `paragraph`**（非 `heading`）——降低标题被误判的概率

### 新增函数

**文件**：`src/services/sectionize_service.rs`（或新建 `src/services/heuristic_table_service.rs`）

```rust
/// 从 blocks 中启发式检测纯文本型表格（`|` 分隔），补充到 raw_doc 的 tables 中。
///
/// 对每个页面，扫描 blocks 中连续含 `|` 分隔符且列数一致的段落组，
/// 每组构造一个 RawTable，追加到对应 RawPage.tables。
///
/// # 检测条件
///
/// - 至少连续 2 行含 `|` 分隔符
/// - 相邻行 `|` 分隔出的列数相同（≥2）
/// - block 类型非 heading
///
/// # 返回
///
/// 检测到的伪表格数量（用于日志输出）。
pub fn detect_pipe_tables(raw_doc: &mut RawDocument) -> usize {
    let mut total_detected = 0;

    for page in &mut raw_doc.pages {
        let mut i = 0;
        while i < page.blocks.len() {
            let block = &page.blocks[i];

            // 跳过非 paragraph 类型（降低误判）
            if block.block_type != BlockType::Paragraph {
                i += 1;
                continue;
            }

            // 检查是否含 `|` 分隔符
            let cols = block.text.split('|').count();
            if cols < 2 {
                i += 1;
                continue;
            }

            // 收集连续且列数一致的 blocks
            let mut table_blocks: Vec<&RawBlock> = Vec::new();
            let mut j = i;
            while j < page.blocks.len() {
                let next = &page.blocks[j];
                if next.block_type != BlockType::Paragraph {
                    break;
                }
                let next_cols = next.text.split('|').count();
                if next_cols != cols {
                    break;
                }
                table_blocks.push(next);
                j += 1;
            }

            // 至少 2 行才认为是表格
            if table_blocks.len() < 2 {
                i = j;
                continue;
            }

            // 构造 RawTable
            let rows: Vec<Vec<Option<String>>> = table_blocks
                .iter()
                .map(|b| {
                    b.text
                        .split('|')
                        .map(|cell| {
                            let trimmed = cell.trim().to_string();
                            if trimmed.is_empty() {
                                None
                            } else {
                                Some(trimmed)
                            }
                        })
                        .collect()
                })
                .collect();

            let table_id = format!("t_{}_{}", page.page_index, page.tables.len());
            let table = RawTable {
                id: table_id,
                bbox: None, // 启发式表格无精确定位 bbox
                rows,
            };
            page.tables.push(table);
            total_detected += 1;

            i = j; // 跳过已消费的 blocks
        }
    }

    total_detected
}
```

### 级联影响

| 下游 | 影响 | 处理 |
|------|------|------|
| 方案二 `inject_tables_into_sections` | 补充的 RawTable 被正常消费，生成 Markdown 表格 | ✅ 透明集成 |
| `RawPage.tables` | 追加了启发式检测的表格，与原 pdfplumber 表格共存 | ✅ 不冲突 |
| 误判风险 | 正文中含 `|` 且连续 2 行以上、列数一致 | ⚠️ 极低概率，接受 |

### 已知限制

1. **无 bbox**：启发式表格没有精确包围盒，`table.bbox` 为 `None`。如果需要高亮回溯，需通过 block ID 间接定位。
2. **`|` 分隔符**：只检测竖线分隔的文本表格。空格对齐型、制表符分隔型表格不在此模块范围内（这些通常已被 pdfplumber 的边框检测覆盖）。
3. **异常列数**：如果表格首行是合并单元格（如 `"序号|名称|规格"` = 3 列），后续行也是 3 列，则正常检测。如果某行因合并单元格导致列数变化，整组会被跳过。

## 不改什么（有意留白）

| 问题 | 原因 |
|------|------|
| 智慧教室短 chunk 比例偏高（27.2%） | 大量 50-120 字符的短 chunk 来自投标格式条款的独立编号项。这些是**语义上正确的**——每个编号项是一个可独立评审的条款。提高 `merge_min_len` 会破坏语义完整性。 |
| `RawTable.rows` 的 `Option<String>` vs `String` 兼容性 | 已在方案二中增加**前置验证步骤**（见上文 ⚠️ 前置验证）。兼容性由 serde 自动处理（JSON `null` → `None`，`"text"` → `Some("text")`）。若验证发现异常，需在 pdf_extract_service 中增加自定义 deserializer。 |
| table ID（`t_*`）溯源高亮链路 | 方案二将 table ID 写入 `chunk.source_block_ids`，下游 LLM 引用 `t_2_0` 时需渲染层支持回溯高亮。当前 `raw_document.rs` 的 ID 命名规则只显式列出 `w_*`（单词）和 `b_*`（段落块），需验证 `t_*` 的回溯链路是否已实现。若未实现，需在渲染层补充。 |
| 跨页表格被拆为独立 Markdown 表格 | 上游 pdf_extract 按页提取表格，无法自动拼合。后续可考虑基于表头匹配的跨页合并（P2）。 |
| 启发式表格的 bbox 定位 | 方案五构造的 `RawTable.bbox` 为 `None`。若要支持"表格级"高亮回溯（非 block 级），需从 source blocks 的 bbox 聚合计算表格整体 bbox。标记为 P2。 |
