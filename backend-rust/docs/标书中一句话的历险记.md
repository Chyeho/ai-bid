# 标书中一句话的历险记

> 以 ch_001 为主角，完整走一遍从 PDF 切分到最终风险报告的旅程。
> 帮助你理解多 Agent 如何协作、记忆如何流转、通信如何运作。

---

## 0. 诞生：ch_001 从哪里来

招标文件是一份 PDF，经过 chunking（语义切分）后变成了若干条款。ch_001 是其中之一：

```
ch_001: "本项目指定采用某品牌专利技术，且须提供原厂商针对本项目的唯一授权函。"
分级:    L3（高风险 — 含"品牌"+"指定"+"唯一授权"等排他性关键词）
页码:    第15页
章节:    ["第三章", "技术要求"]
```

系统把它包装成一个 `ReviewClause` 结构体，连同其他 6 条条款一起交给 Coordinator。

---

## 1. ROUTE — 关键词分配：谁来看我？

Coordinator 拿出 ch_001 的文本，逐个 Agent 匹配其 `section_keywords`：

| Agent | 匹配？ | 原因 |
|-------|:---:|------|
| **FactCheck** | ✅ | 关键词 `品牌` 命中 |
| **Procedure** | ❌ | 不含"采购方式""保证金""公告期限"等程序关键词 |
| **RuleEngine** | ✅ | `唯一`、`必须` 类硬性规则关键词命中 |
| **SemanticRisk** | ✅ | `品牌` + `唯一授权` → 隐性排他信号 |
| **Scoring** | ❌ | 不含"评分""分值""权重""评审因素" |
| **Demand** | ✅ | `专利技术` → 技术需求倾向性 |
| **Contract** | ❌ | 不含合同条款关键词 |

**路由结果：ch_001 被分配给 FactCheck、RuleEngine、SemanticRisk、Demand 四个 Agent。**

> 这个阶段，ch_001 只是被放进了各 Agent 的「待办清单」里，还没有任何人真正动手。

---

## 2. PRELOAD — 写入共享白板

Coordinator 把所有条款和 Agent 预先写入 SessionGraph。此时 ch_001 在图上只是一个安静的节点：

```
SessionGraph.chunks:
  ┌──────────────────────────────────────┐
  │ chunk_id:     "ch_001"               │
  │ text_preview: "本项目指定采用某品牌..." │
  │ tier:         L3 (高风险)             │
  │ section_path: ["第三章", "技术要求"]    │
  │ page_start:   14                     │
  │ page_end:     15                     │
  └──────────────────────────────────────┘

SessionGraph.agents:
  FactCheck, Procedure, RuleEngine, SemanticRisk,
  Scoring, Demand, Contract, BlindSpot
```

**此刻的图还是安静的——有节点，但没有边（连线）。没有谁审过谁，没有风险发现。**

---

## 3. EXECUTE — 四个 Agent 并行开审

`tokio::spawn` 启动 4 个并行任务。每个 Agent 拿到自己的：

- 🧠 **LLM 客户端**（独立实例，各自的对话上下文）
- 🔧 **工具集**（web_search、search_document、read_section、output_finding）
- 📖 **SessionGraph 引用**（读白板 / 签到 / 写发现）
- 📡 **AgentBus 引用**（收广播 / 发广播）

**四个 Agent 同时开始工作，但速度不同。** 我们以 FactCheckAgent 为主线，SemanticRiskAgent 为支线来看。

---

### 3.1 FactCheckAgent 的 ReAct 循环

#### Turn 1：认识条款，开始搜索

**Step 0a — 拉取共享记忆（SessionGraph）：**

```
FactCheck 问 SessionGraph: "ch_001，谁审过你？有什么发现吗？"

SessionGraph 回答:
  reviewed_by:     []        ← 还没有人来过
  risks:           []        ← 没有风险发现
  linked_chunks:   []        ← 没有关联条款
  same_law_chunks: []        ← 没有引用相同法条的其他条款
  contradictions:  []        ← 没有矛盾
```

什么都没有，所以这一轮**不注入任何记忆**到对话里。

然后，FactCheck 签到：

```
SessionGraph.reviewed_by["ch_001"].push(FactCheck)
```

> 此时图变成了： `ch_001 ──reviewed_by──▶ [FactCheck]`

**Step 0b — 检查实时广播（AgentBus）：**

```
AgentBus.try_recv() → 队列空的，没有人广播过
```

**Step 1 — LLM 收到对话，开始思考：**

```
┌─ 对话窗口 ─────────────────────────────────────────────┐
│ [System] 你是 FactCheckAgent。职责：提取结构化事实，     │
│          对照法规阈值，判定是否存在排斥性/排他性条款。    │
│                                                         │
│ [User]   【L3 - 深度审查】请审查以下条款:                │
│          条款ID: ch_001                                  │
│          条款内容: "本项目指定采用某品牌专利技术，        │
│                    且须提供原厂商针对本项目的唯一授权函。" │
│          请使用 web_search 搜索法规 → search_document     │
│          跨条款联动 → read_section 精读 → 输出结论。     │
└─────────────────────────────────────────────────────────┘
```

LLM 决定先搜法规：

```
LLM: → 调用 web_search("政府采购法 指定品牌 唯一授权 限制竞争")
```

工具返回了关键信息：

```
搜索结果:
  《政府采购法实施条例》第20条：
  "采购人或者采购代理机构有下列情形之一的，属于以不合理的条件
   对供应商实行差别待遇或者歧视待遇：……
   （三）采购需求中的技术、服务等要求指向特定供应商、特定产品；"
```

#### Turn 2：深挖关联

**Step 0a — 拉取共享记忆（仍然只有自己）：**

```
SessionGraph: reviewed_by = [FactCheck], risks = []
```

（还没有其他 Agent 审完，ch_001 依然是处女地。）

注入到对话：
```
[System] [Session 记忆] 已审查 Agent: FactCheckAgent
已知风险: （无）
```

**Step 0b — AgentBus 依然安静。**

**Step 1 — LLM 继续深挖：**

```
LLM: → 调用 read_section(ch_004, ch_005)
      # "我看看相邻条款有没有更多上下文"

LLM: → 调用 search_document("授权函 原厂商")
      # "全文搜索 '授权函'，看有没有其他条款也涉及"
```

#### Turn 3：证据够了，输出结论

剩余轮次预警触发：
```
[System] ⏳ 剩余 3 轮审查机会。请开始汇总已收集的信息……
```

LLM 决定收网：

```
LLM: → 调用 output_finding({
  "no_risk": false,
  "severity": "High",
  "risk_type": "品牌指定+唯一授权限制竞争",
  "source_quote": "指定采用某品牌专利技术……唯一授权函",
  "legal_basis": ["《政府采购法实施条例》第20条(三)"],
  "reason": "要求'某品牌专利技术'+'唯一授权函'构成指向性条款，
            排斥其他品牌参与竞争，违反公平竞争原则",
  "suggestion": "删除品牌指定，改为性能技术参数；
                删除唯一授权要求，允许兼容产品投标",
  "confidence": 0.92
})
```

**🎉 FactCheckAgent 审查完成！**

#### 输出瞬间发生了两件事：

**① 写入 SessionGraph（拉取侧 — 给后来者看）：**

```
SessionGraph 新增:

  节点:
  risks["R_003"] = RiskNode {
    risk_type:  "品牌指定+唯一授权限制竞争",
    severity:   High,
    clause_ids: ["ch_001"],
    legal_basis: ["《政府采购法实施条例》第20条(三)"],
    confidence: 0.92,
    ...
  }

  边（连线）:
  ch_001 ──has_risk──▶ R_003
  R_003  ──cites─────▶ 《政府采购法实施条例》第20条(三)
  《采购法条例》第20条(三) ──cited_by──▶ R_003  (反向索引，O(1)查询)
```

**② 广播到 AgentBus（推送侧 — 实时通知其他 Agent）：**

```
AgentBus 广播:
  📡 from:      FactCheckAgent
     severity:  High
     summary:   "品牌指定+唯一授权限制竞争"
     clause:    ["ch_001"]
     risk_type: "品牌指定+唯一授权限制竞争"
```

> 只有 High 级别才广播——Medium/Low 不广播，靠 SessionGraph 拉取。

### 3.2 SemanticRiskAgent 的并行时间线

SemanticRiskAgent 也在审 ch_001，但它节奏稍慢，现在刚到 Turn 2。

#### Turn 2 — 看到了 FactCheck 的脚印

**Step 0a — 拉取 SessionGraph（这次有东西了！）：**

```
SemanticRisk 问 SessionGraph: "ch_001，现在什么情况？"

SessionGraph 回答:
  reviewed_by: [FactCheck]     ← 有人来过了！
  risks: [
    {
      risk_type: "品牌指定+唯一授权限制竞争",
      severity: High,
      confidence: 0.92,
      reason: "要求'某品牌专利技术'+'唯一授权函'构成指向性条款……"
    }
  ]
  linked_chunks: []
  same_law_chunks: []
```

系统把这些信息注入到 SemanticRisk 的对话中：

```
[System] [Session 记忆] 以下条款已被审查或存在已知发现:

已审查 Agent: FactCheckAgent

已知风险:
- [High] 品牌指定+唯一授权限制竞争 (confidence=0.92):
  要求'某品牌专利技术'+'唯一授权函'构成指向性条款，
  排斥其他品牌参与竞争，违反公平竞争原则。
```

**Step 0b — 检查 AgentBus（也有东西了！）：**

```
AgentBus 消息队列:
  📡 FactCheckAgent 发现 High 风险: 品牌指定+唯一授权限制竞争
     涉及条款: ch_001
```

注入到对话：
```
[System] [AgentBus] FactCheckAgent 发现 High 风险:
品牌指定+唯一授权限制竞争
涉及条款: ch_001
如果你审查的条款与此相关，用 search_document 和 read_section 做交叉验证。
```

**Step 1 — SemanticRisk 的反应：**

> "FactCheck 已经发现了品牌指定的问题。但我是隐性风险专家，角度应该不同——这个'唯一授权'是否隐含了对中小企业的事实排斥？"

```
LLM: → 调用 web_search("原厂商唯一授权 中小企业 隐性准入门槛")
LLM: → 调用 search_document("授权函")  # 全文搜索
```

最终它发现了另一个维度：

```
LLM: → 调用 output_finding({
  "no_risk": false,
  "severity": "Medium",
  "risk_type": "原厂授权隐含隐性准入壁垒",
  "reason": "'原厂商唯一授权'排除了代理商/经销商投标资格，
             且中小企业在获得原厂授权方面处于弱势地位，
             构成事实上的准入歧视",
  "confidence": 0.78,
  ...
})
```

> 💡 **这里体现了 SessionGraph 和 AgentBus 的核心价值**：SemanticRisk 看到 FactCheck 已经发现了品牌问题，就不再浪费轮次去重复发现同样的东西，而是从另一个角度切入。它写入 Medium 级别风险（不广播），静默写入 SessionGraph。

## 4. MERGE — 合并去重

所有 Agent 的 findings 汇总到 Coordinator：

```
FactCheck:    [R_003: 品牌指定 High   0.92]  ┐
RuleEngine:   [R_006: 限制竞争 High   0.88]  ─┤ 关于 ch_001
Demand:       [R_008: 技术指向 High   0.91]  ┘  的三个发现
SemanticRisk: [R_001: 格式问题 Info   0.95]  (关于格式)
              [R_005: 隐性准入 Medium 0.78]  (关于 ch_001)
```

去重逻辑：按 `risk_type | clause_ids | agent` 做 key，保留 confidence 更高的：

```
R_003 (品牌指定) vs R_006 (限制竞争) → risk_type 不同，都保留
R_008 (技术指向)                     → risk_type 不同，保留

最终: ch_001 关联 4 条发现 (3 High + 0 Medium + 1 Info)
```

## 6. BLINDSPOT — 盲点扫描

BlindSpotAgent 读取完整的 SessionGraph 快照，评估每个条款的覆盖程度：

```
ch_001:
  reviewed_by = [FactCheck, RuleEngine, SemanticRisk, Demand]  (4人)
  risks = [R_001, R_003, R_005, R_006, R_008]  (发现丰富)
  
  → ✅ 充分覆盖，无需复查
```

它转而把精力放在覆盖不足的条款上（比如只被 1 个 Agent 审过、还没发现风险的 ch_007）。

## 总结：三条记忆线，各司其职

| 记忆层 | 载体 | 生命周期 | 作用 | ch_001 的例子 |
|--------|------|----------|------|-------------|
| **瞬时记忆** | ReAct 对话窗口 | 单个 Agent 审查期间 | LLM 的工具调用链和推理过程 | FactCheck 搜了 3 轮、读了 2 段原文、权衡后输出 |
| **中期记忆** | SessionGraph | 一次审查 Session | 结构化共享：谁审过、发现了什么、条款间关联 | SemanticRisk 拉取时看到 FactCheck 的发现，避免重复劳动 |
| **实时通知** | AgentBus | 单次广播 | 高优先级推送：发现 High 风险立即通知所有人 | FactCheck 一发现品牌问题就广播，SemanticRisk 实时收到 |
| **长期记忆** | TraceLog | 审计追溯 | 记录每个 Agent 每轮的决策和通信 | 出问题时回溯"R_003 是 FactCheck 在 Turn 4 发现的" |
| **最终产出** | CoordinatorOutput | 交付给调用方 | 排序好的风险清单 + 图快照 | 直接用于撰写标书审查报告 |

**一句话概括 ch_001 的历险记**：

> 被路由分给 4 个 AI 审查员 → 每个人在白板上签到、读别人留下的笔记、发现有价值的东西就写上去、严重的还广播一嗓子 → 最后总管合并整理、校验法条、扫描遗漏 → 产出排序好的风险报告。全程每个人独立工作，但通过白板和广播彼此感知，最终画出一张完整的风险关系图。
