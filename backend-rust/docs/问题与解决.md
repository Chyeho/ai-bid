## 1. 多 Agent 并发下 risk_id 碰撞导致 SessionGraph 数据静默丢失

**日期**：2026-06-26

**严重度**：🔴 Critical

**现象**：
集成测试 `memory` 中，Coordinator 启用 7 个 Agent 审查 5 条条款。Triage 阶段正确统计到 4 条风险（3 High + 1 Medium），但 SessionGraph snapshot 仅包含 2 个 RiskNode——另外 2 条风险节点被静默覆盖丢失。

**根因**：
`ReActLoop::review()` 中 risk_id 生成逻辑为 `format!("R_{:03}", idx + 1)`——每个 Agent 独立从 R_001 开始编号。当多个 Agent 并发写入共享 SessionGraph 时，`SessionGraph.risks: HashMap<String, RiskNode>` 以 risk_id 为 key，后写入的 Agent 直接覆盖前面 Agent 的 RiskNode。ContractAgent 的 R_001（ch_003 "工期违规"）被 SemanticRiskAgent 的 R_001（ch_004 "品牌指定"）覆盖，后者又被 DemandAgent 的 R_001（同样是 ch_004）再次覆盖。

**修复**：
将 risk_id 的生成权从 Agent 局部层级上移到共享状态容器 SessionGraph，使用 `AtomicU64` 全局计数器保证唯一性。

**改动文件**：

| 文件 | 改动 |
|------|------|
| `src/agents/session_graph.rs` | struct 新增 `risk_id_counter: AtomicU64` 字段 + `next_risk_id()` 方法 |
| `src/agents/react_loop.rs` | `review()` 中 risk_id 改为 `graph.next_risk_id()` 优先，无 graph 时回退 |

**核心代码**：

```rust
// session_graph.rs — 全局唯一 ID 生成
pub fn next_risk_id(&self) -> String {
    let id = self.risk_id_counter.fetch_add(1, Ordering::Relaxed);
    format!("R_{:03}", id + 1)
}

// react_loop.rs — 使用方
let risk_id = self.graph
    .as_ref()
    .map(|g| g.next_risk_id())
    .unwrap_or_else(|| format!("R_{:03}", idx + 1));
```

**验证**：
- 164 个单元测试全部通过，无回归
- 集成测试 `memory`：`risks=2` → `risks=3`（无碰撞丢失）
- risk_id 序列从 `R_001` 到 `R_008` 全局递进，log 可读性同时提升

**架构教训**：
在共享状态（SessionGraph）被多个并发写入者（Agent）修改时，写入者不应自行分配全局域的标识符。正确的所有权归属是：**状态容器拥有 ID 分配权，写入者向容器申请 ID**。这是一个典型的"局部状态假设在并发环境中失效"的案例——ReActLoop 被设计为独立审查引擎，但其产物（RiskFinding）需要写入全局共享的 SessionGraph，risk_id 的局部生成假设在共享环境下被打破。

**关联文件**：
- `src/agents/react_loop.rs` — ReActLoop::review()
- `src/agents/session_graph.rs` — SessionGraph struct + add_risk_with_edges()
- `src/agents/coordinator.rs` — execute_agents() 并发写入路径
- `src/bin/test_agents.rs` — memory 集成测试

### 2.1 LegalVerifyAgent 搜索循环耗尽（5 轮无有效输出）

**现象**：
集成测试 `memory` 中，LegalVerifyAgent 的 5 轮 max_turns 全部用于 `web_search`，从未调用 `output_finding`。日志中连续 5 次搜索返回相同结果列表，Agent 不断换 query 重试直到 max_turns 耗尽。

**根因**（3 层叠加）：
1. **搜索引擎同质化返回**：DashScope 搜索对不同 query（"请查找 87 号令第十七条原文" vs "请查找财政部官网 87 号令第十七条"）返回相同的 top-3 结果列表，Agent 误以为换 query 可以找到新信息
2. **空搜索检测不触发**：现有 `consecutive_empty_searches` 机制仅检测 `hit_count == 0` 的情况。但这些搜索返回了 10 条结果（`hit_count > 0`），计数器被重置，升级逻辑从不触发
3. **有效轮次不足**：`effective_max_turns = min(tier_max_turns=5, default_max_turns=5) = 5`，而 LegalVerifyAgent 需要逐条验证多个法条引用，5 轮不够

**修复**（4 处改动）：

| 文件 | 改动 |
|------|------|
| `src/agents/react_loop.rs` | 新增**搜索重复检测**：连续 2 次 web_search 返回相同 top-3 URL → 触发强制 `output_finding`。新增 `extract_top_urls()` 辅助方法和 `consecutive_duplicate_searches`/`last_search_urls` 状态变量 |
| `src/agents/coordinator.rs` | LegalVerifyAgent 的 `tier_max_turns: 5 → 8` |
| `src/agents/registry.rs` | LegalVerifyAgent 的 `default_max_turns: 5 → 8`（之前 `min(8,5)=5` 抵消了上一项修改） |
| `src/agents/prompts.rs` | 搜索上限 5→3，新增指令：2 次搜索不成功则基于已知法规常识判断；提示搜索引擎覆盖范围限制 |

**核心代码**：
```rust
// react_loop.rs — 搜索重复检测（插入在空搜索检测之后、硬性上限之前）
if self.is_search_tool(tool_name) {
    let current_urls = Self::extract_top_urls(&result, 3);
    if !current_urls.is_empty() && current_urls == last_search_urls {
        consecutive_duplicate_searches += 1;
        if consecutive_duplicate_searches >= 2 {
            // 强制 output_finding（与 L2 空搜索相同的升级措辞）
            conversation.push(ChatMessage::System {
                content: "🛑 连续 2 次搜索返回相同的结果列表，搜索引擎对不同 query 返回了相同内容。\n\
                    基于已搜索到的信息 + 条款原文 + 已知法规常识，立即调用 output_finding 输出结论。"
                    .to_string(),
            });
            continue;
        }
    } else {
        consecutive_duplicate_searches = 0;
        last_search_urls = current_urls;
    }
}

// react_loop.rs — 提取 top-N URL（兼容 sources[].url 和 sources[].link）
fn extract_top_urls(result: &serde_json::Value, n: usize) -> Vec<String> {
    if let Some(arr) = result.get("sources").and_then(|s| s.as_array()) {
        arr.iter()
            .filter_map(|item| {
                item.get("url").or_else(|| item.get("link"))
                    .and_then(|u| u.as_str())
                    .map(|s| s.to_string())
            })
            .take(n)
            .collect()
    } else {
        Vec::new()
    }
}
```

### 2.2 BlindSpotAgent "ReAct 无产出" 日志误导

**现象**：
BlindSpotAgent 实际产出了 2 条 `no_risk=true` 的 finding（ch_002 和 ch_003 确认无风险），但 Coordinator 中 `!no_risk` filter 将其全部过滤后，日志打印 `[BLINDSPOT] ReAct 无产出，回退到 fallback`。日志信息与实际情况不一致——Agent 工作了，只是没发现新风险。

**根因**：
过滤逻辑（`findings.into_iter().filter(|f| !f.no_risk).collect()`）不区分"Agent 真的零产出（空 Vec）"和"Agent 产出了但结论全是 no_risk"。统一用"无产出"描述，误导调试和监控。

**修复**：

| 文件 | 改动 |
|------|------|
| `src/agents/coordinator.rs` | 统计 `total_findings` 和 `no_risk_count` 后再过滤。日志区分三种情况：①有真实风险发现（`发现 N 条新风险 (另有 M 条 no_risk 结论)`）；②仅有 no_risk 结论（`ReAct 产出 M 条 no_risk 结论，无新增风险发现`）；③零产出（`ReAct 无任何产出 (0 条 finding，共 N 候选条款)`） |

**核心代码**：
```rust
// coordinator.rs — 修改后
let findings = agent.review(&candidate_clauses).await;

let total_findings = findings.len();
let no_risk_count = findings.iter().filter(|f| f.no_risk).count();
let real_findings: Vec<RiskFinding> =
    findings.into_iter().filter(|f| !f.no_risk).collect();

if real_findings.is_empty() {
    if no_risk_count > 0 {
        eprintln!("  [BLINDSPOT] ReAct 产出 {} 条 no_risk 结论，无新增风险发现，回退到 fallback",
            no_risk_count);
    } else {
        eprintln!("  [BLINDSPOT] ReAct 无任何产出 (0 条 finding，共 {} 候选条款)，回退到 fallback",
            total_findings);
    }
    // ... fallback
}
```

### 架构教训

1. **搜索引擎的同质化返回是常见失败模式**：当搜索引擎覆盖不足时，不同的 query 措辞可能返回相同的缓存结果。Agent 框架需要在工具执行层做去重检测，不能仅依赖 LLM 自行判断搜索效果。
2. **日志的可观测性需要区分"零产出"和"产出被过滤"**：这是两种不同性质的边界情况——前者是 Agent/LLM 故障，后者是业务逻辑正常工作。混淆二者会误导故障排查方向。
3. **测试数据设计需要关键词覆盖率检查**：基于关键词路由的多 Agent 系统，测试数据必须覆盖所有 Agent 的关键词集。应该在测试中做自动化断言而非依赖人工检查——这正是本次新增 Check 5 的目的。
