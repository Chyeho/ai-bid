# 优化记录

Multi-Agent 审核系统的 LLM 浪费率优化过程。

---

## 2026-07-09 上午 — BatchSearch 并行化

### 背景

Coordinator 批量搜索阶段耗时 219s（串行逐个搜索）。

### 改动

- `coordinator.rs`: `batch_search_phase()` 改为 `JoinSet` 并行执行所有搜索
- 收集所有唯一 query → 并行 spawn tokio task → 收集结果

### 结果

| 指标 | 串行 | 并行 |
|---|---|---|
| BatchSearch | 219s | 26s |
| 总耗时 | 359s | 143s |

### 教训

并行化是明显的正确选择——搜索之间无依赖关系，JoinSet 是最佳模型。

## 2026-07-09 上午 — 预搜索结果注入优化（V1：300字摘要 → V2：紧凑索引）

### 背景

预搜索结果全文（300 字摘要 + 来源）注入 Agent prompt → 413K input tokens，LLM 在长上下文中迷失，DemandAgent 并行版比串行版多 7 次调用。

### 改动

1. **`react_loop.rs` `format_clause_prompt()`**: 注入从 300 字摘要改为按 URL 去重的 1 行法规索引
2. **`react_loop.rs` `cached_search_knowledge()`**: 缓存匹配增加 bigram Jaccard fallback（精确匹配 miss 后模糊匹配）
3. **`prompts.rs`**: 7 个 Agent 的 Scout 段落更新为"法规索引 + web_search 缓存优先"

### 结果

| 指标 | V1 (全文注入) | V2 (紧凑索引) |
|---|---|---|
| Input tokens | 413K | 342K (-17%) |
| LLM calls | 51 | 45 (-12%) |
| 成本 | ¥0.36 | ¥0.30 (-17%) |
| 浪费率 | 69% | 67% |

### 教训

✅ **紧凑索引是正确的**——Agent 不需要看到搜索结果的全文摘要，只需要知道"有哪些法规可以用"。
紧凑索引节省了 ~17% input tokens，且不影响 Agent 的判断质量。

## 2026-07-09 中午 — answer 文本匹配（❌ 失败回退）

### 背景

bigram 匹配只比对缓存 key（keyword 格式："87号令 第二十条 原文"），与 Agent 的自然语言提问（"政府采购招标文件中是否允许指定特定平台作为唯一移动端解决方案？"）几乎无重叠，缓存命中率低。

### 尝试

在 `cached_search_knowledge()` 中增加第三层匹配：query n-gram vs 缓存 **answer 文本**（DashScope 返回的 AI 摘要，自然语言格式）。

### 结果

| 指标 | V2 | +answer 匹配 |
|---|---|---|
| LLM calls | 45 | 50 ❌ |
| Input tokens | 342K | 400K ❌ |
| 成本 | ¥0.30 | ¥0.34 ❌ |
| 浪费率 | 67% | 70% ❌ |

### 根因分析

缓存命中的 answer 文本被完整注入到对话历史的 tool result 中，等效于"预搜索结果全文注入 prompt"——这正是 V1 被否定的问题。

**缓存命中 → answer 注入对话 → 下一轮 LLM 看到更长的上下文 → 迷失 → 更多调用。**

### 补救尝试：截断

在缓存命中返回时截断 answer 到 200 字符 + 标注 `[缓存命中，原文已截断，需要完整内容请用更具体的查询搜索]`。

### 结果

| 指标 | +answer | +截断 |
|---|---|---|
| LLM calls | 50 | **68** ❌ |
| Input tokens | 400K | **548K** ❌ |
| 成本 | ¥0.34 | **¥0.48** ❌ |

### 根因

"需要完整内容请用更具体的查询搜索" 这句话起到了反效果——Agent 被诱导去"获取完整内容"，
DemandAgent 的搜索从 31 次涨到 34 次。

### 回退决策

**回退到 V2（紧凑索引 + bigram key 匹配）状态。** 这是当前最优版本。

## 关键教训

### 1. 缓存层的信息不能充当 Agent 的阅读材料

预搜索结果应该让 Agent **知道有这些东西存在**（紧凑索引），但不要让 Agent **阅读这些内容的全文**（无论是 prompt 注入还是缓存命中后的 tool result）。

### 2. 不要在 tool result 中给出"下一步行动建议"

`[需要完整内容请重新搜索]` 之类的话会被 LLM 理解为"你应该去搜索"。任何元信息的注入都会改变 Agent 的行为——通常朝着不可预期的方向。

### 3. 不要匹配 answer 文本做缓存

answer 是给人类看的摘要，不是给缓存 key 用的索引。缓存匹配应该基于 query 的**关键实体**（法规名、条款号），而不是全文 n-gram 相似度。

### 4. ReAct 浪费的天花板是结构性的

经过三轮优化（批量搜索 → 紧凑索引 → bigram 缓存），浪费率从 73% 降到 67%，边际收益递减。
剩余浪费主要来自 Agent 的**Turn 1 习惯性搜索**——这是 ReAct 循环的结构性特征，
prompt 和缓存层面的优化已接近上限。

### 5. 测试要跑全流程再看结论

answer 匹配在理论上"应该更好"（自然语言 vs 自然语言），但实际跑出来更差。
理论推导不能代替实测，特别是 LLM 行为涉及复杂的上下文效应。

## 2026-07-09 下午 — V5：法规摘要注入（边际改善，未突破天花板）

### 背景

V2 紧凑索引只告诉 Agent "有什么法规"（URL + 标题），没告诉"法规说了什么"。Agent 为了获取法规具体内容，Turn 1 必须搜索 → 53-67% 的 Turn 1 是 web_search。

V1 给了 300 字摘要（太多，Agent 迷失），V2 只给 URL（太少，Agent 必须搜）。**中间地带还没试过。**

### 改动

1. **`react_loop.rs`**: 新增 `extract_snippet()` 辅助函数 — 从搜索答案中提取第一句实质性内容（去掉 LLM 引导语，最长 120 字）
2. **`react_loop.rs` `format_clause_prompt()`**: 注入格式从 `[标题](URL) | [标题](URL)` 改为逐条摘要：
   ```
   📋 法规摘要:
   - 87号令：**"招标文件不得将非实质性条款作为否决投标的依据"** [来源](url)
   - 政府采购法第22条：**"不得以不合理的条件对供应商实行差别待遇"** [来源](url)
   ```
3. **`prompts.rs`** (×7): "法规索引" → "法规摘要"，对齐新格式

### 结果

| 指标 | V2 | V5 |
|---|---|---|
| LLM calls | 45 | 45 |
| Input tokens | 342K | 304K (-11%) |
| 成本 | ¥0.30 | ¥0.27 (-10%) |
| 浪费率 | 67% | 67% |
| Turn1 web_search | 8/15 | 9/15 |

### 分析

Agent **读到了摘要、理解了内容**（有 Agent 明确说"根据法规摘要，政府采购法及其实施条例并未对微信小程序作出专门规定"），但依然要 web_search 去"验证"。

摘要给了 Agent 答案，但它不信任摘要——必须亲自查一遍才敢下结论。这是法律审查场景下的固有问题：**Agent 被训练成"引用法规必须查原文"**，摘要只是"听说"，不是"查到"。

Input tokens -11% 是实在的收益：摘要比 V2 的 URL-only 格式更省 token，因为 Agent 不需要为了"看法规写了什么"而搜索（搜索结果的注入 token 比摘要大得多）。

### 教训

✅ **V5 是当前 prompt 层面最优配置** — 成本和浪费率综合最佳。

❌ **prompt 层面优化的天花板已确认：~67% 浪费率。** 经过四轮优化（V1→V2→V3→V4→V5），浪费率从 73% 降到 67%，边际收益已趋近于零。剩余浪费来自 ReAct 循环的结构性特征（"先搜再判"的行为模式），prompt 和缓存优化无法突破。

### 下一步方向

只有结构性改造能突破天花板：

1. **Turn 1 硬禁搜** — 快速实验，但有 V4 式回旋镖风险（Agent 可能用其他工具替代或被延迟的搜索补偿）
2. **两阶段架构** — Agent 先输出"信息需求清单" → Coordinator 统一获取 → Agent 一次性判断。可能将浪费率降到 <30%，但需要较大架构改动

## 2026-07-09 下午 — V6：可信度标注（❌ 失败回退）

### 背景

V5 的法规摘要给了 Agent 法规内容，但 Agent 仍然"必须亲自搜索验证"。假设是：Agent 不信任搜索结果摘要，因为摘要没有区分"可靠来源"和"AI 总结"。

借鉴外部思路（分层可信度 + 差异化处理），尝试给每条摘要标注来源可信度（🟢政府网站/🟡百科/🔵网络搜索），配合分层判断 prompt，让 Agent 对高可信度来源直接引用、只对关键条款措辞才搜索核实。

### 改动

1. **`react_loop.rs`**: 新增 `source_credibility()` 函数 — URL 域名 → 可信度等级 + 标签
2. **`react_loop.rs` `format_clause_prompt()`**: 摘要按可信度分组排列（🟢→🟡→🔵），header 改为"🟢可直接引用 | 🟡参考 | 🔵需核实"
3. **`prompts.rs`** (×7): 判断流程改为 4 步分层指引：
   ```
   1. 先看🟢摘要是否已覆盖 → 直接引用
   2. 🟢不够看🟡🔵 → 引用并注明"据搜索摘要"
   3. 涉及精确措辞 → web_search（最多2次）
   4. 明显遗漏 → web_search 补充（最多3次）
   ```

### 结果

| 指标 | V5 | V6 | 变化 |
|---|---|---|---|
| LLM calls | 45 | **56** | **+11 (+24%) ❌** |
| Input tokens | 304K | **481K** | **+177K (+58%) ❌** |
| 成本 | ¥0.27 | **¥0.42** | **+¥0.15 ❌** |
| 浪费率 | 67% | **73%** | **+6pp ❌** |
| Turn1 web_search | 9/15 | 9/15 | 不变 |
| Badge 被 Agent 引用 | — | 🟢1次 | 基本被忽略 |

**Agent 级别：**

| Agent | V5 calls | V6 calls | 变化 |
|---|---|---|---|
| FactCheckAgent | 5 (0浪费) | **11 (7浪费)** | ❌ 从最佳变最差 |
| DemandAgent | 24 | **30** | ws 11→15 |
| RuleEngineAgent | 8 | 8 | 不变 |

### 根因分析

**1. Agent 完全忽略了可信度标注。** 15 个 Agent 实例中只有 1 个在思考中提到 🟢。分层判断的 4 步流程没有被执行——Agent 仍然按"看到摘要 → 搜索验证"的固定模式运作。

**2. Prompt 膨胀起了反作用。** 4 步分层判断指南 ~200 字 × 7 Agent × 多个 clause → 大量累积 prompt token。更长、更复杂的 prompt 让 Agent 迷失——这正是 V1 的失败模式（长上下文 → 迷失 → 更多调用）。V5 的简洁 prompt 被替换成了复杂的决策树。

**3. FactCheckAgent 的崩溃是最关键的信号。** 之前在 V2/V5 中始终保持 0 浪费的高效 Agent，在 V6 中变成了 11 次调用 + 7 次浪费。冗长的判断流程指南干扰了它原本简洁高效的"读条款 → 判"模式。**好 Agent 被坏指南拖累了。**

**4. 可信度分层是正确思路，但用错了实现方式。** Agent 确实需要区分可靠来源和 AI 摘要——但区别应该在信息注入层面处理（只注入高可信度摘要），而不是把判断负担转嫁给 Agent（让 Agent 自己决策"这个来源可信吗"）。Agent 不是搜索引擎，给它更多的元数据不会让它做出更好的决策，只会增加认知负荷。

### 教训

❌ **不要在 prompt 中构建决策树。** 4 步分层判断流程把 Agent 的认知负担从"判断条款合规性"变成了"判断条款合规性 + 判断来源可信度 + 选择判断策略"。每增加一个决策维度，模型性能呈非线性下降。

❌ **简洁的 prompt 胜过全面的 prompt。** V5 的 4 行简洁指令比 V6 的 12 行决策树效果好得多。LLM 对简洁指令的执行力远高于复杂指令——这不是人类直觉（越详细越好），而是 LLM 的特性（越简洁越准确）。

❌ **可信度问题的正确解在数据层，不在 prompt 层。** 如果要让 Agent 区分可信度，应该在 `format_clause_prompt()` 中直接过滤低可信度来源（只注入 🟢 政府网站的内容），而不是把所有来源都塞进去然后让 Agent 自己判断。

✅ **单变量实验的价值。** V5→V6 只改了一个维度（可信度标注），结果清晰归因到 prompt 膨胀。如果要同时改多个维度（如 V3+V4 同时改 answer 匹配 + 截断），根本不知道哪个导致失败。

### 回退

已回退到 V5（紧凑摘要 + 扁平格式 + 简洁 prompt）。V5 是当前 prompt 层面已验证的最优配置。

## 2026-07-09 下午 — 降本优化：从 ¥70 到 ¥3.8（-95%）

### 背景

V5 在 2 页测试文件上表现良好（¥0.27, 67% 浪费率），但跑到 92 页真实文档时成本爆炸：¥70/次，耗时 21.5 分钟。用户的 DashScope 账户实际扣费 ¥70，远超可接受范围（目标：≤¥10/次）。

### 问题诊断

分析成本结构后发现三个主要黑洞：

| 去向 | 占比 | 问题 |
|---|---|---|
| Scout 阶段 | 51% | LLM 扫描全部 264 clause 产出 Hypothesis，但 48% clause 最终无 finding |
| Execute 阶段 | 36% | 7 个 Agent 共 653 次 LLM 调用，其中 SemanticRiskAgent (11.2 calls/finding) 和 ScoringAgent (6.4 calls/finding) 效率极低 |
| LegalVerify + web_search | 13% | LLM 验证法条引用 + 400 次独立 API 调用 |

且 Scout、LegalVerify、web_search 的 LLM 调用均未被 metrics 追踪（未调用 `.with_metrics()`），导致已统计成本（¥40.89）与实际账单（¥70）之间存在 ¥29 的巨大缺口。

### 改动

**1. 切模型：qwen-plus → qwen-turbo（`.env` 1 行）**

qwen-turbo 价格是 plus 的 37%（¥0.3/1M input vs ¥0.8/1M input）。法律审查的大部分工作是对照法条判断合规性——模式匹配而非深度推理，turbo 够用。

**2. 干掉 Scout 阶段（`coordinator.rs` ~20 行）**

Scout 用 LLM 读全部 clause → 判断"有没有风险"→ 产出 Hypothesis。但关键词路由（`route_clauses`）已经按 clause 内容分配到对应 Agent，Agent 的领域知识足以判断风险。Scout 是用 LLM 判断"值不值得用 LLM 审"——逻辑上就是浪费。

修复了 BatchSearch 在没有 Hypothesis 时的 fallback 路径：从 clause 文本提取关键词自动生成搜索 query，确保 Agent 仍能拿到预搜索的法规摘要。

**3. 关掉低效 Agent（`types.rs` 2 行）**

从 `all_reviewers()` 中移除：
- SemanticRiskAgent：56 calls → 5 findings (11.2 calls/finding)
- ScoringAgent：32 calls → 5 findings (6.4 calls/finding)

减少 13% 调用，仅损失 7% finding。RiskEngineAgent + DemandAgent 的审查范围已覆盖这些 Agent 的风险类型。

**4. 关掉 LegalVerify（`types.rs` 1 行）**

`enable_legal_verify: false`。Agent 引用法规时自带来源 URL，turbo 模型下法条验证的边际价值低于其成本。

**5. 精简 prompts（`prompts.rs` ×7）**

去掉 Scout Hypothesis 引用（"Session 记忆与 Scout 初筛结果"段），改为简洁的审查流程指引。

### 结果

**2 页测试文件：**

| 指标 | V5 (plus) | 降本后 (turbo) | 变化 |
|---|---|---|---|
| 成本 | ¥0.27 | ¥0.14 | -48% |
| 耗时 | 140s | 64s | -54% |
| Scout | 27s | 0s | ✅ |

**92 页真实文档：**

|---|---|---|---|

| 耗时 | 1293s (21.5min) | 479s (8min) | -63% |
| LLM 调用 | 653 | 356 | -45% |
| Input tokens | 50.7M | 2.4M | -95% |
| web_search | 368 | 166 | -55% |
| 活跃 Agent | 7 | 5 | -2 |

**各阶段耗时：**

| 阶段 | 改动前 | 改动后 |
|---|---|---|
| Scout | 655s | **0s** ✅ |

### 关键教训

✅ **模型切换是 ROI 最高的降本手段。** 一行业务代码不改，砍掉 63% 成本。对法律审查这种"模式匹配 > 深度推理"的场景，turbo 完全够用。

✅ **Scout 是最大的成本黑洞。** 用 LLM 判断"值不值得用 LLM 审"是架构反模式。关键词路由 + Agent 领域知识足以完成 clause 分配。且 Scout 的 LLM 调用未被 metrics 追踪，导致成本盲区。

✅ **Agent 数量不是越多越好。** 11.2 calls/finding 的 Agent 拖累整个系统。关掉 2 个最差的 Agent，损失 7% finding 换来 13% 成本下降和更简洁的管线。

✅ **成本指标需要完整覆盖。** 之前 metrics 只追踪 Execute 阶段，Scout + LegalVerify + web_search 的 API 调用全部漏记。这个缺口导致已统计 ¥40.89 vs 实际 ¥70 的巨大偏差。后续应给所有 ReAct 调用统一加上 `.with_metrics()`。

✅ **Debate 值得保留。** 只对 High + confidence ≤ 0.85 的边界案例触发，turbo 下成本 ¥0.02/次可忽略，提供三角色对抗验证提升质量。
