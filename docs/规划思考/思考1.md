# 把系统做的更加强大
## 一、文档解析与处理层
厂商做了重度专项优化
招采系统 80% 耗时耗在PDF/Word 解析，这块商用系统优化拉满：
1. 专用文档解析引擎，抛弃通用库
智采这类系统不用开源的 PyPDF、python-docx，自研基于 PDF 内核解析器：
• 跳过水印、图片、空白页眉页脚、广告冗余内容；
• 自动识别招标章节（投标人须知、评分标准、商务条款）结构化分块；
• 扫描件 PDF 内置轻量 OCR 加速模型，GPU 并行文字识别；
你自研大多套通用开源库：逐页全量读取、图片文字串行识别、不分章节，一份几百页标书解析就要十几秒。
2. 文档分片并行处理
厂商把一份招标文件拆成：商务、技术、评分、资质 4 个子块，多线程 / 多进程并行解析、并行 AI 校验；
自研普遍单线程从头到尾串行处理，阻塞等待。
3. 缓存机制重度落地
• 固定模板、法律法规、标准资质条款全局热缓存；
• 同一单位、同类采购项目历史解析结果持久化缓存；
你自研基本无缓存，每次打开文件都重复解析、重复 AI 调用。

文档解析与理解
• Docling (IBM)：2024年开源，将PDF转为统一的DoclingDocument格式（含布局、表格、层级），支持导出Markdown/JSON，是当前工程化最好的工具。
• MinerU：可提取高质量PDF内容，在复杂中文表格上表现优异，可配合pdf2image做视觉端提取。
• Florence-2 (Microsoft)：轻量级多模态基础模型，微调后可同时做版面分析、OCR、表格结构识别，单图推理速度极快，适合做解析层引擎。
• Qwen2.5-VL / InternVL2：可作为“整页理解”后端，直接让模型输出页面全部字段的结构化JSON，适合极致简化流水线（但成本较高，建议用量化版做批量提取）。

## 三、业务逻辑层
重计算异步化，替代当前的全同步阻塞
商用系统标准分层设计（丝滑无等待）
1. 前端：即时渲染，重任务丢后台队列
上传文件后立刻展示预览，合规审查、预算大数据比对、AI 生成标书全部丢 MQ 消息队列异步执行，前端只轮询进度，不会卡死页面；
2. 计算层拆分轻重任务
• 轻任务（关键词检索、简单格式校验）同步即时返回；
• 重任务（全文 AI 违规检测、上万条历史成交价匹配、长篇标书生成）异步排队，分布式多机器消费；
自研典型反面写法
全部逻辑写在同一个接口内：上传文件 → 解析全文 → 调用 AI 逐条审核 → 查询历史成交数据 → 一次性全部返回，长文档直接接口超时、页面转圈几十秒。

## 四、数据层

千万级行业数据做预索引，自研裸查数据库
1. 厂商数据提前结构化、预计算索引
全国政府采购成交数据、法规条文、违规案例，提前：
• 向量化存入向量数据库；
• 建立多级倒排索引、分类标签索引；

每次检索成交记录都like %关键词%，几十万条数据查询耗时秒级，文档一多直接雪崩。

## 五、AI业务逻辑工程优化

1. 提示词工程 + 输出结构化约束
商用系统固定强约束 Prompt，强制 AI 返回 JSON 结构化结果，不用再写代码解析大段自然文字；
自研简单 Prompt，AI 输出自由文本，还要额外正则、分割处理，增加耗时。
2. 规则引擎前置，减少 AI 调用次数
先通过硬规则过滤 90% 简单问题（资质年限、标书时长、金额阈值），只有模糊、复杂合规问题才调用大模型；
你自研不管简单复杂全部丢给 AI，大量冗余推理拖慢速度。
3. 批量合并请求
多条条款一次性批量送入模型推理，而非循环逐条调用 AI 接口，大幅减少网络往返开销。
六、网络与部署层面差距
4. 商用厂商：内网私有推理服务，内网毫秒延迟；
自研：公网调用第三方大模型 API，网络波动、限流、分片上传下载都增加耗时；
5. 负载均衡分布式部署：多台机器分担用户并发；
自研单服务单实例，多人同时上传文件直接堵塞。

## 六、底层算力与推理架构层
本地GPU推理模块

### 1、小模型
• 小模型
智采只训练政府采购领域数据，把通用 GPT / 大模型蒸馏成几十层轻量专用小模型，参数量只有通用大模型 1/10 甚至更小，单条文本推理毫秒级；
你自研大概率直接调用通用 API（GPT、通义、文心原生大模型），通用模型冗余层多、推理慢。

垂直领域轻量化本地模型蒸馏、量化（1 人研究）
解决通用大模型推理慢、显存占用高问题，零训练集群成本：
1. 模型轻量化路线：
• 选用开源基座：Qwen-7B、Llama3-8B、GLM4-9B
• 领域蒸馏：拿政府采购标书、法规数据做微调蒸馏，压缩到 4B/3B 小参数量
• 量化落地：GPTQ/AWQ 4bit/8bit 量化，大幅降低显存占用，单卡同时承载多请求
2. 业务约束 Prompt 结构化输出，减少后处理耗时
3. 本地推理部署：基于 vLLM/TGI 加载量化模型，打通文档解析 AI 校验流程
产出：适配招采场景的量化垂直小模型权重，可本地 GPU 一键启动。


### 2、KV Cache缓存复用机制
KV Cache 缓存复用机制（核心提速点，1 人研究）
研究内容完全贴合本地模型推理，无依赖大额框架：
1. 基础原理：Transformer 推理 KV 缓存生成、复用、淘汰策略
2. 开源落地：vLLM / Text Generation Inference (TGI) 底层 KV 池实现
3. 业务适配：
• 招标文件长文本多轮校验场景下，同一份文档多条款复用 KV，减少重复计算
• 实现简单 LRU 缓存淘汰，控制显存占用，防止 2～3 并发显存溢出
4. 对比实验：关闭 KV 缓存 vs 开启 KV，单文档推理耗时、显存占用量化对比
产出：一套封装好的本地推理服务，自带 KV 缓存复用，对外 http 接口调用。

### 3、批量推理+文档分片并行预处理
批量推理 + 文档分片并行预处理（1 人研究）
串联 GPU 算力与业务文档，实现 2-3 并发流畅处理：
1. 连续批处理（Continuous Batching）机制调研：vLLM 动态批处理原理
2. 文档分片并行：PDF/Word 拆分为商务、评分、资质多块，多线程预处理
3. 任务队列轻量化实现（不用重型 MQ）：Python SimpleQueue/RabbitMQ 轻量单机版
• 前端上传文档丢本地队列，GPU 消费进程批量取任务并行推理
• 限制队列最大并发数 = 3，控制负载，防止显卡打满
4. 向量批量编码加速：GPU 批量生成文档片段向量，替代 CPU 逐条计算
产出：文档并行解析 + 批量推理调度模块，对接 KV 推理服务。
