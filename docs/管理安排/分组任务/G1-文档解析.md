# G1 文档解析 — Phase 1-4 完整推进

> 3 人 | Python 为主（Docling / MinerU / PaddleOCR）
> 阻塞级别：Phase 1-2 阻塞 G2/G3，是整条链路的入口

---

## Phase 1：基础建设（W1-W2）

1. 找 3 份学校采购招标文件 PDF（办公设备 / 信息化 / 物业各一），作为全组共用测试样本
2. 研究 Docling + MinerU，跑通一份 PDF 的完整解析流程，记录遇到的坑
3. 定义 `docs/schemas/parsed-document.schema.json`：章节层级、条款文本、表格结构、页码坐标、元数据。参考 [项目架构设计 §3.2](../../项目架构设计.md) 中的 Schema 模板
4. 用 3 份 PDF 跑解析，产出 3 份 Mock JSON -> `docs/mocks/sample-parsed-document-*.json`
5. W1 周三前交出 Schema 初稿给 G2/G3；W2 周三前 3 份 Mock 全部就绪

**Phase 1 交付物**：
- `docs/schemas/parsed-document.schema.json` 定稿
- 3 份 Mock JSON

---

## Phase 2：稳定解析（W3-W5）

1. 解析质量达标：表格识别率 > 90%，章节分割准确率 > 85%
2. 性能达标：100 页 PDF 解析 < 10 秒
3. 实现分片并行：大文档拆 4 片并行（商务/技术/评分/资质）
4. 坏页容错：单页失败不中断，标记 `parse_error` 字段
5. W3 末更新 3 份 Mock JSON 为真实解析结果，供 G2/G3 联调
6. W3 周五与 G2/G3 联调：传递真实解析结果

**Phase 2 交付物**：
- 稳定解析引擎，5 份测试文件通过质量检查
- 解析耗时 < 10 秒/百页

---

## Phase 3：质量提升+投标文件适配（W6-W8）

1. 表格识别率 > 95%，扫描件 OCR > 95%
2. 新增投标文件 .docx 格式适配（docx -> pdf -> 解析）
3. 中文表格增强：MinerU 接入，处理复杂中文表格场景
4. 扫描件兜底：PaddleOCR 接入，处理图片型 PDF
5. 解析结果缓存：同文件 hash 不重复解析

**Phase 3 交付物**：
- 解析质量达标（表格>95%，OCR>95%）
- .docx 格式支持

---

## Phase 4：维护修复（W9-W10）

1. 端到端测试：50 份文档批量解析，统计错误率
2. Bug 修复：解析错误、坐标偏移、表格漏检等
3. 性能优化：大文档解析耗时进一步压缩
4. 配合部署：解析服务容器化，接入 Redis Streams 任务队列

**Phase 4 交付物**：
- 解析服务稳定运行
- 部署文档中解析引擎部分
