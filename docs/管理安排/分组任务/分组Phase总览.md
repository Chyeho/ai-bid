# 分组 Phase 总览

> 最后更新：2026-07-11

---

## 什么是 Phase

本项目分 4 个阶段交付，每个阶段称为一个 Phase。MVP = Phase 1-2（审招标文件），后续逐步扩展。

| 阶段 | 周次 | 审核对象 | 核心交付 |
|---|---|---|---|
| **Phase 1** | W1-W2 | 基础建设 | 环境搭建 + 接口契约锁定 + Mock 数据 |
| **Phase 2** | W3-W5 | 审招标文件 | 单文档合规审核全链路跑通 |
| **Phase 3** | W6-W8 | +审投标文件 | 双文档独立审核 + 知识飞轮闭环 |
| **Phase 4** | W9-W10 | 招投标全流程 | 招标+投标对照审核 + 部署上线 |

---

## Phase 1：基础建设（W1-W2）

目标：锁定接口契约，各组产出 Mock 数据，下游拿到就能独立开发。

| 时间 | 事件 |
|---|---|
| W1 周一 | 全员环境搭建完成 |
| W1 周三 | G1 产出 Schema 初稿，G2/G3 开始适配 |
| W1 周五 | 各组组长汇报进度 |
| W2 周三 | 全部 Schema 存入 `docs/schemas/`，Mock 存入 `docs/mocks/` |
| W2 周五 | Phase 1 终检 |

各组 Phase 1 核心交付：

- **G1**：3 份学校采购招标文件 Mock JSON
- **G2**：行业分类体系 + 法规清单(>=20部) + 5条示范规则 YAML
- **G3**：向量库搭建 + 200条切片入库
- **G4**：代码理解文档 + 精简方案初稿(11->3 Agent)
- **G5**：工具筛选结果 + Judge Prompt v1
- **G6**：Neo4j Schema设计 + Curator Pipeline方案
- **G7**：研究方向确认 + GPU资源状态
- **G8**：数据库ER图 + OpenAPI文档 + 认证可运行
- **G9**：页面原型 + 路由结构

---

## Phase 2：MVP 审招标文件（W3-W5）

目标：单文档审核全链路跑通。上传招标文件 -> 输出结构化审核报告。

| 周 | 联调节点 |
|---|---|
| W3 周五 | G1->G2/G3：真实解析结果传递 |
| W4 周五 | G2->G4 + G3->G5：规则/知识 API 联调 |
| W5 周五 | 全链路联调：G1->G2->G3->G4->G5->G8->G9 |

各组 Phase 2 核心交付：

- **G1**：表格识别>90%，章节分割>85%，百页PDF<10秒，W3末更新Mock
- **G2**：规则库>=100条（8大类学校采购聚焦），匹配耗时<1秒，W4末HTTP API就绪
- **G3**：知识库>=1500条（法规+案例+负面清单），检索<500ms，W4中HTTP API就绪
- **G4**：精简Pipeline（3 Agent串行：RuleAgent->JudgeAgent->CriticAgent），W5中全链路联调
- **G5**：4核心工具就绪 + Judge/Critic Prompt v2，W4中与G3联调
- **G6**：Session快照存储（PostgreSQL表+G8接口），不启动Curator Pipeline
- **G7**：第一份技术调研报告
- **G8**：文件上传+审核任务CRUD+结果回调+MinIO+Session快照表，W3末API就绪
- **G9**：审核工作台（双栏+SSE进度+报告展示），W5全链路联调

Phase 2 检查标准：
- 上传5份真实学校采购招标文件，每份输出>=10条审核发现
- 误报率<30%
- 端到端耗时：百页文档<5分钟

## Phase 3：产品扩展（W6-W8）

目标：+审投标文件 + 知识飞轮闭环 + SaaS产品化 + G4恢复高级特性。

各组 Phase 3 核心交付：

- **G1**：表格>95%，扫描件OCR>95%，+投标文件.docx格式适配
- **G2**：+投标文件规则库>=100条（漏项/参数偏离/资质响应/格式等），总规则>=200
- **G3**：知识库>=3000条，Neo4j图库上线（>=1000节点，法规->条款->案例关系）
- **G4**：恢复Agent并发（3 Agent并行tokio::spawn）+ AgentBus + +投标文件审核模式
- **G5**：+4工具（check_cross_reference/calculate_timeline/compare_with_template/extract_obligations）+ 投标Prompt
- **G6**：Curator Pipeline MVP首次启动（月度去重->建图->向量化->保鲜）
- **G7**：第二份调研报告，如有突破封装API
- **G8**：多租户+成员管理+用量统计+报告导出API(PDF/Word)
- **G9**：+投标文件审核工作台+管理后台+报告导出+人在回路面板

Phase 3 检查标准：
- 审招标文件：误报率<20%，召回率>90%
- 审投标文件：单文档>=8条发现
- 知识飞轮：至少跑通一次完整Curator Pipeline
- SaaS：多租户注册->创建项目->上传->审核->查看报告完整闭环

---

## Phase 4：全流程+打磨上线（W9-W10）

目标：招投标对照审核 + 性能达标 + 部署上线。

各组 Phase 4 核心交付：

- **G2+G4+G5**：招标要求 vs 投标响应逐条自动比对
- **G4**：恢复Debate阶段 + HumanReviewAgent三节点
- **G6**：Curator Pipeline自动化（Cron触发）
- **G7**：最终技术报告，如有突破完成API接入
- **G8+G9**：端到端测试+性能优化+Bug修复+部署文档+运维手册

Phase 4 检查标准：
- 产品部署到服务器，外部用户可注册使用
- 招投标对照审核报告可用
- 百页文档端到端<5分钟

---

## 组间依赖关系

```
Phase 1-2 主链路:
  G1(Schema) --> G2(规则) --> G4(Agent) --> G8(回调) --> G9(前端)
  G1(Schema) --> G3(知识) --> G5(工具) --^

Phase 3-4 知识飞轮:
  G4+G5(审核结果) --> G8(Session快照) --> G6(Curator) --> G3(知识库更新)
                                                   --> G7(推理接入,可选)

并行组:
  G4 <--trait--> G5      (完全并行,仅依赖接口签名)
  G8 <--OpenAPI--> G9    (完全并行,Mock Server)
  G6, G7                 (独立,不进主链路)
```
