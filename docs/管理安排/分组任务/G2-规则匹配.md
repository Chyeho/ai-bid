# G2 规则匹配 — Phase 1-4 完整推进

> 2 人 | Rust（YAML 规则引擎）
> 依赖 G1 Schema | 被 G4 调用

---

## Phase 1：领域建模（W1-W2）

Phase 1 不写代码，做领域建模。规则引擎的难点是把法规转化为可执行规则，不是技术实现。

1. 阅读 [项目架构设计 §3.3](../../项目架构设计.md) 中的规则 YAML 格式，理解 `industry` / `source` / `conditions` 三个核心字段的设计意图
2. 建立学校采购行业分类树（8 大类 -> 子类）：办公设备 / 信息化建设 / 物业管理 / 教材图书 / 实验室设备 / 食堂采购 / 校园工程 / 安保服务
3. 梳理核心法规清单（>= 20 部）：法规全名 + 版本/修订年份 + 生效日期 + 官方来源 URL。覆盖：政府采购法及实施条例、招标投标法及实施条例、财政部令（74号/87号/94号）、各省政府采购负面清单
4. 从法规中挑 5 条"可检查的条款"（如《政府采购法》第 5 条：不得以地域限制排斥潜在供应商），逐条写成 YAML 示范规则
5. 用 G1 的 Mock 数据手动验证这 5 条规则能否命中
6. 产出 `docs/schemas/rule-match.schema.json`

**Phase 1 交付物**：
- 行业分类体系 v1（8 大类 + 子类树）
- 核心法规清单（>= 20 部，含版本和来源 URL）
- 5 条示范规则 YAML
- `docs/schemas/rule-match.schema.json` 初稿

## Phase 2：规则库建设（W3-W5）

1. 编写规则匹配引擎（Rust）：正则 + 关键字 + 字段比较，目标匹配耗时 < 1 秒/百页文档
2. 规则库扩充到 >= 100 条，聚焦学校采购 8 大类：
   - 资质要求 / 业绩要求 / 报价要求 / 工期要求
   - 人员要求 / 安全要求 / 环保要求 / 评分合理性
   - 排斥性条款（地域限制/品牌指定/特定业绩）
3. 每条规则必须包含：`industry`（行业分类）、`source`（法律来源追溯）、`conditions`（触发条件）
4. 搭建 HTTP API 供 G4 调用：`POST /rules/match`（接收 ParsedDocument -> 返回 RuleMatch[]）
5. W4 末 HTTP API 就绪，与 G4 联调
6. 用 AI 批量从法规文件提取规则 -> 人工逐条校验 -> 写入 YAML

**Phase 2 交付物**：
- 规则匹配引擎 + HTTP API
- 规则库 >= 100 条（召回率 > 95%）
- 匹配耗时 < 1 秒/百页文档

## Phase 3：投标文件规则（W6-W8）

1. 新增投标文件规则库 >= 100 条，覆盖：
   - 漏项检测（招标要求有、投标响应无）
   - 参数偏离检测（技术参数负偏离）
   - 资质响应检测（资质证书是否齐全、是否在有效期内）
   - 商务文件检测（营业执照/纳税/社保等）
   - 格式要求检测（盖章/签字/装订等）
2. 规则总数达到 >= 200 条
3. 规则质量迭代：每周人工抽查 20 条规则的匹配结果，建立规则评审机制
4. 规则版本管理：YAML 纳入 Git，修改规则走 PR 流程

**Phase 3 交付物**：
- 规则总数 >= 200 条
- 支持招标+投标双文档类型
