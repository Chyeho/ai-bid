可以，我直接给你一个**能照着实现**的版本：这一步不要把 6 万行原文直接喂给 LLM，而是先把 `RawDocument` 切成“**带回溯信息的 chunk**”，再让 LLM 对 chunk 做结构化抽取。 [milvus](https://milvus.io/ai-quick-reference/what-are-best-practices-for-chunking-lengthy-legal-documents-for-vectorization)

## 先说你要切成什么

你现在的原始数据已经有：
- `page_index`
- `text`
- `words`
- `tables`
- `lines`
- `rects`

下一步切块时，不是只按字数切，而是优先按**文档结构**切成下面几类 chunk：

1. `section_chunk`：标题 + 本节正文。
2. `table_chunk`：一张完整表格。
3. `list_chunk`：编号列表或条目列表。
4. `paragraph_chunk`：普通段落。
5. `fallback_chunk`：太长时再按长度切。 [infohub.delltechnologies](https://infohub.delltechnologies.com/es-es/p/chunk-twice-retrieve-once-rag-chunking-strategies-optimized-for-different-content-types/)

## 切块时要保留什么

每个 chunk 都必须保留**回溯字段**，这是后面高亮和证据链的根：

```json
{
  "chunk_id": "ch_000123",
  "document_id": "efec145e-...",
  "chunk_type": "section_chunk",
  "section_path": ["第一章", "投标须知", "1.3 资格要求"],
  "page_range": [12, 13],
  "block_ids": ["p12_b3", "p12_b4", "p13_b1"],
  "bbox_refs": [
    {"page": 12, "bbox": [72, 120, 512, 160]},
    {"page": 13, "bbox": [70, 80, 520, 130]}
  ],
  "text": "......",
  "source_text_hash": "sha256...",
  "prev_chunk_id": "ch_000122",
  "next_chunk_id": "ch_000124"
}
```

这里最重要的是：
- `block_ids`：告诉你这个 chunk 来自哪些原始块。
- `bbox_refs`：告诉你后面高亮框画在哪里。
- `prev_chunk_id / next_chunk_id`：告诉你它前后邻居是谁，方便补上下文。 [linkedin](https://www.linkedin.com/posts/kirylkatushkin_ai-llm-dataengineering-activity-7467577173118464000-jk-D)

## 具体怎么切

### 1. 先按页遍历
先把所有页按顺序扫描，不要急着抽业务。 [0xfauzi](https://0xfauzi.com/blog/2025/01/15/rag-architecture-for-legal-documents)

### 2. 找标题和编号
识别类似：
- `第一章`
- `1.1`
- `一、`
- `（一）`
- `1.1.1`
- `第X条`

这些通常是 chunk 边界信号。 [milvus](https://milvus.io/ai-quick-reference/what-are-best-practices-for-chunking-lengthy-legal-documents-for-vectorization)

### 3. 表格独立成块
只要发现表格，就尽量整张表单独形成 `table_chunk`，因为表格里经常直接藏着要求、响应、评分点。 [infohub.delltechnologies](https://infohub.delltechnologies.com/es-es/p/chunk-twice-retrieve-once-rag-chunking-strategies-optimized-for-different-content-types/)

### 4. 段落按语义合并
没有标题的连续段落，先合并到同一个 chunk，直到遇到新的标题、表格或明显主题变化。 [0xfauzi](https://0xfauzi.com/blog/2025/01/15/rag-architecture-for-legal-documents)

### 5. 超长再切
如果一个 chunk 还是太长，再按长度切，但要**带 overlap**，比如前后留一点重叠，避免断上下文。 [openreview](https://openreview.net/forum?id=74QmBTV0Zf)

## 怎么喂给 LLM

LLM 不要直接看整个文档，而是看**一个 chunk + 必要邻居**。 [randeepbhatia](https://randeepbhatia.com/ai-architecture/contract-review-system)

比如你要抽 `requirement`，输入给 LLM 的内容应该长这样：

```json
{
  "task": "extract_requirement",
  "chunk": {
    "chunk_id": "ch_000123",
    "section_path": ["第二章", "投标人须知", "2.3.1 资格条件"],
    "text": "投标人应具有独立承担民事责任的能力...",
    "page_range": [12, 13]
  },
  "context": {
    "prev": "上一小节标题和最后两句",
    "next": "下一小节标题和前两句"
  },
  "output_schema": {
    "requirements": [
      {
        "title": "",
        "content": "",
        "mandatory": true,
        "requirement_type": "qualification|format|delivery|other",
        "source_block_ids": [],
        "source_page_range": [],
        "confidence": 0.0
      }
    ]
  }
}
```

LLM 的任务只有一个：**把这个 chunk 里属于 requirement 的内容抽出来，按 schema 返回 JSON**。 [github](https://github.com/brandonrobertz/llm-document-extraction/blob/main/README.md)

## LLM 输出后你要做什么

LLM 返回后，程序做三件事：

1. **schema 校验**：JSON 格式是否正确。
2. **引用校验**：`source_block_ids` 是否真的存在。
3. **内容校验**：抽出来的文字能不能在原文中找到。 [casemark](https://casemark.com/workflows/bulk-document-extraction-review)

如果失败，就：
- 补充前后邻居 chunk。
- 或重新抽一次。
- 或进入人工确认。 [ibm](https://www.ibm.com/think/insights/llms-drive-information-analysis-compliance-validation)

## 你最应该记住的逻辑

### 切块不是为了省 token
切块是为了：
- 保持条款完整。
- 保持上下文。
- 保持高亮回溯能力。
- 保持后续图数据库和证据链可用。 [arxiv](https://arxiv.org/html/2602.10271v1)

### 业务抽取不是最终结论
它只是把原文变成：
- `Requirement`
- `Response`
- `RiskFlag`
- `RegulationRef`

这些对象都要带来源信息。 [dev](https://dev.to/tensorlake/make-rag-provable-page-bbox-citations-for-all-extracted-data-4ipc)

### 高亮一定回原始层
不要直接拿 LLM 输出去高亮，必须通过 `source_block_id -> RawDocument.page.blocks.bbox` 回查。 [customgpt](https://customgpt.ai/ai-for-document-analysis/)

## 最简单的实现顺序

如果你要马上写代码，我建议按这个顺序：

## 一句话版本

**先按章节/表格/段落切成带 `chunk_id + block_ids + bbox_refs + prev/next` 的 chunk，再让 LLM 对单个 chunk 做结构化抽取，抽取结果必须带来源，最后通过来源回到原始页和 bbox 做高亮。** [linkedin](https://www.linkedin.com/posts/kirylkatushkin_ai-llm-dataengineering-activity-7467577173118464000-jk-D)

如果你愿意，我下一条可以继续给你写：
**一个具体的 Rust 伪代码流程：`RawDocument -> Chunk -> LLM -> Requirement JSON`。**

不是把 `page_index/text/words/tables/lines/rects` 一次性整篇丢给 AI 让它“自己切”。更合理的是：**你先用程序按结构切成候选 chunk，再把每个 chunk 连同它的上下文交给 LLM 做“确认/修正/命名/抽取”**。 [bluente](https://www.bluente.com/blog/rag-pipeline-legal-document-processing)

## 正确方式

### 先程序切，再让 LLM 处理
第一步最好由代码做，因为你的 `RawDocument` 已经有足够信息：
- `page_index` 看跨页。
- `text` 看正文。
- `tables` 识别表格。
- `lines/rects` 识别分隔线、框、表头。
- `words` 辅助判断标题、编号、列表。 [milvus](https://milvus.io/ai-quick-reference/what-are-best-practices-for-chunking-lengthy-legal-documents-for-vectorization)

也就是说，**切块规则先由程序做**，比如：
- 遇到章节标题切。
- 遇到条款编号切。
- 遇到表格单独切。
- 遇到列表单独切。
- 段落连续就合并。
- 太长再按长度切并留 overlap。 [unstract](https://unstract.com/blog/how-intelligent-chunking-strategies-makes-llms-better-at-extracting-long-documents/)

### LLM 做什么
LLM 不负责“从零切全文”，而是负责：
- 判断程序切得是否合理。
- 给 chunk 命名，比如“资格要求”“投标文件格式要求”。
- 从 chunk 中抽取业务对象，如 requirement / response / risk。
- 在边界不清时帮助决定 chunk 是否要合并或拆分。 [machinelearningmastery](https://machinelearningmastery.com/essential-chunking-techniques-for-building-better-llm-applications/)

## 最稳的流水线

### 阶段 1：结构切块
程序先扫描整个文档，生成很多候选 chunk：
- `section_chunk`
- `table_chunk`
- `list_chunk`
- `paragraph_chunk`。 [redis](https://redis.io/blog/llm-chunking/)

每个 chunk 带：
- `chunk_id`
- `page_range`
- `block_ids`
- `bbox_refs`
- `section_path`
- `prev_chunk_id`
- `next_chunk_id`。 [bisok](https://bisok.com/hierarchical-chunking-with-auto-merge-for-better-enterprise-rag/)

### 阶段 2：LLM 轻量确认
把**一个 chunk + 少量邻居**喂给 LLM，让它做三件事：
1. 这个 chunk 属于什么类型。
2. 里面有哪些业务对象。
3. 需不需要和前后 chunk 合并。 [casemark](https://casemark.com/workflows/bulk-document-extraction-review)

### 阶段 3：输出结构化结果
LLM 输出的不是“答案”，而是：
- chunk 标签。
- requirement / response / risk 候选。
- source 引用。 [github](https://github.com/ryanmcdonough/nda-extraction)

## 不要怎么做

不要把整个 6 万行原文一次性发给 LLM 让它“自己分块”。  
原因是：
- 太长会漏。
- 结构会被压扁。
- 表格和条款边界会乱。
- 你后面很难追溯。 [reintech](https://reintech.io/blog/build-legal-document-analysis-system-llms-rag)

## 你最适合的切块策略

### 规则优先
先用规则识别边界：
- 标题。
- 编号。
- 表格。
- 列表。
- 页眉页脚变化。 [infohub.delltechnologies](https://infohub.delltechnologies.com/es-es/p/chunk-twice-retrieve-once-rag-chunking-strategies-optimized-for-different-content-types/)

### LLM 辅助
只在以下情况用 LLM：
- 边界模糊。
- 标题不明显。
- 表格跨页。
- 一段文字包含多个语义单元。 [machinelearningmastery](https://machinelearningmastery.com/essential-chunking-techniques-for-building-better-llm-applications/)

### 邻居补上下文
如果 chunk 太短，或者 LLM 判断不完整，就把前后 chunk 也带上。  
这是 legal 文档里特别常见的做法。 [linkedin](https://www.linkedin.com/posts/v-chandra-sekhar_bad-chunking-is-why-your-legal-chatbot-sounds-activity-7463170478979850243--Q2u)

## 一个非常具体的理解

你可以把它想成这样：

- **程序**：先把整篇标书切成 200 个候选小段。
- **LLM**：检查每一段，告诉你“这段是不是一个完整要求”“这段是不是表格中的评分点”“这段是不是跟上一段属于同一条款”。
- **程序**：把 LLM 的判断整理成最终 chunk JSON。 [bluente](https://www.bluente.com/blog/rag-pipeline-legal-document-processing)

## 结论

**不是整篇丢给 AI 切，而是程序先做结构化预切块，LLM 再对候选 chunk 做确认、命名和抽取。**  
这样既省 token，又能保留逻辑链和回溯能力。 [milvus](https://milvus.io/ai-quick-reference/what-are-best-practices-for-chunking-lengthy-legal-documents-for-vectorization)
