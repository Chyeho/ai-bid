# 智能标书审核系统 — 团队招募

> 暑期 10 周，15-20 人，做一个能卖的 AI 产品。

---

## 我们在做什么

一款 **AI 驱动的标书合规性审核 SaaS**。客户上传招标文件，系统自动检测：哪些条款违法、哪些资质缺失、哪些参数有倾向性、哪些地方可能废标——每条结论引法律原文、标原文位置、给修改建议。

这不是课程项目。目标是 10 周后放一个能注册、能上传、能审核、能出报告的产品，给学校财务处用。

现有基础：8000+ 行 Rust Multi-Agent 审核引擎（Coordinator + ReAct Loop + AgentBus + SessionGraph），11 个 Agent，11+ 个审查工具，React 前端骨架。你们不是从零开始——你们是站在一个已经跑通的框架上，把它推到能卖的水平。

---

## 9 个组，选一个你们愿意拥有的领域

---

### G1 文档解析引擎（3 人）

**你们会构建**一个文档理解引擎，把混乱的 PDF 招标文件变成机器可读的结构化数据。

真实世界的标书不是干净的 Markdown——它有嵌套表格、合并单元格、扫描件印章、多级条款编号。你们会用到 Docling、MinerU、PaddleOCR 这些前沿的 Document AI 工具，解决中文排版里最棘手的版面理解和表格识别问题。

**Result**：你们让系统能读懂学校采购招标文件——表格识别率 > 90%，章节分割 > 85%，100 页文档 10 秒内解析完成。

---

### G2 规则匹配引擎（2 人）

**你们会构建**一个确定性规则引擎，在毫秒级内过滤招标文件中的硬性合规问题。

资质没写、日期过了、金额超了——这些不需要大模型判断。你们会从《政府采购法》《招标投标法》等法规中逐条抽取可程序化验证的规则，建立带来源追溯和适用条件的规则库。这是整个系统速度最快、成本最低、结果最可复现的一层。

**Result**：你们整理了 200 条招标投标合规规则，每一条都能追溯到具体法律条款。规则召回率 > 95%，零 API 成本。

---

### G3 知识检索引擎（2 人）

**你们会构建**一个法律知识检索系统，让 AI Agent 在审核时能在 500ms 内找到最相关的法规、案例和负面清单。

你们会用 BGE-M3 嵌入模型对法规全文做向量化，用 BM25 做关键词精准匹配，用 Reranker 精排结果——这是 RAG（检索增强生成）在法律场景的真实落地。

**Result**：你们构建了一个覆盖 3000+ 条法规的知识库，Top-10 检索命中率 > 85%。Agent 引用的每一条法条都真实存在。

---

### G4 Agent 智能组（3 人）

**你们会构建**一个 AI 审核系统的评测和优化体系——这是决定产品能不能卖出去的核心。

现有框架跑通了 Multi-Agent 调度，但没人知道 Agent 审得有多准。你们会发现它在参数倾向性检测上 F1 可能只有 0.62，在特定类型的幻觉上犯错率高达 35%。你们建立 50 份人工标注的 Benchmark，搭建自动化评测 Pipeline，跑 5 种 Multi-Agent 协作模式的对比实验——Pipeline vs 并行投票 vs 辩论 vs 分工——用数据回答"哪种模式在什么场景下最优"。

**如果你们有更好的架构想法——提出来，跑对比实验，用 F1 数据证明你们比现有设计更好，就用你们的。你们的目标是做出最准的 Agent，不是维护现有代码。**

**Result**：你们设计的评测体系跑通了全链路，你们跑完了协作模式对比实验，你们知道在不同场景下串行、并行、辩论哪种最有效。你们让审核 F1 从"不知道"变成了一个可测量的数字，并且这个数字在涨。

---

### G5 领域工具组（3 人）

**你们会构建** Agent 的领域能力——审查工具、Prompt 模板、知识注入。

Agent 审得不准，经常不是模型的问题，是工具覆盖有缺口、Prompt 没有校准。你们会为每个审查维度维护专用工具（数值验证、矛盾检测、时间线计算、义务提取），为每个 Agent 迭代 System Prompt。和 G4 形成闭环——G4 跑评测告诉你们哪个 Agent 哪个场景不行，你们改 Prompt 和工具，再跑评测验证。你们还要验证现有工具是否全部设计正确——设计场景用例，确认每个工具在真实审核中能被正确触发、返回正确结果。

**Result**：你们维护的工具集在 200 个测试用例上准确率 > 95%。你们的 Prompt 模板库覆盖 8 大采购类别，每次 Prompt 变更必须通过 A/B 测试——F1 不退化才合并。你们为每个工具设计了触发场景验证，确保该调的时候调得到、调的结果是对的。

---

### G6 知识沉淀引擎（2 人）

**你们会构建**知识飞轮——每次审核完成后，自动把高质量的审核结论、法条引用、风险模式沉淀到 Neo4j 图数据库和 Qdrant 向量库。

下次审核时，这些沉淀的知识被 G3 检索到，系统越用越聪明。这是整个项目最有战略价值的部分——1000 份标书 × 10 万条审核案例积累起来，是任何竞品短期内无法复制的壁垒。

**Result**：你们搭建了知识飞轮系统，用 Neo4j 图数据库建模法规→条款→案例→风险的关系网络。跑通了至少一次完整的 Curator Pipeline，月度沉淀有效知识 100+ 条。

---

### G7 推理优化研究（1-2 人）

**你们会探索**一个关键问题：能不能不调云端大模型，在本地 GPU 上跑一个小模型，拿到同等甚至更好的审核效果？

你们会研究模型量化（GPTQ/AWQ 4bit）、KV Cache 复用、批量推理优化，甚至尝试用 LoRA 微调一个标书审核专用模型。这是非阻塞研究——不进入主链路，有突破则接入。允许失败。

**Result**：你们产出了可复现实验代码和技术报告。如果你们做到了本地模型接近云端效果，这条线会成为产品的核心竞争力。

---

### G8 SaaS 业务平台（3-4 人）

**你们会构建**产品的 SaaS 外壳——多租户架构、用户认证、文件管理、任务队列、API Gateway。

这是前端和 AI 引擎之间的桥梁，也是产品从"技术 Demo"变成"可售卖 SaaS"的关键一步。你们会用 Spring Boot 3 + PostgreSQL + Redis 搭建生产级后端，支撑 50 并发用户同时上传和审核。

**Result**：你们构建了一个多租户 SaaS 平台，完整实现了注册→创建项目→上传文件→审核→查看报告→导出 PDF 的完整闭环。API P99 延迟 < 500ms。

---

### G9 前端体验（3-4 人）

**你们会构建**用户看到和触碰的一切——审核工作台、报告展示、文档高亮定位、管理后台。

审核结果如果只有 JSON，没有人会付费。你们的工作是把 AI 的推理过程变成用户一眼能看懂的界面：哪里有问题、有多严重、为什么、怎么改。用 React 18 + Ant Design 5 + react-pdf 构建双栏审核工作台——左边 PDF 原文，右边问题列表，点击任意风险，PDF 自动滚动到对应位置并高亮原文。

**Result**：你们构建了一个 AI 审核工作台——双栏联动 + PDF 高亮定位，用户 30 秒内理解一份 100 页招标文件的关键风险。5 人可用性测试任务成功率 > 90%。
