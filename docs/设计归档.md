# AI 标书审核系统 — 架构设计

## 1. 项目概述

AI 辅助招投标文档审核系统。输入 PDF 或 DOCX 格式的标书文件，自动提取结构化内容，
通过 LLM 进行合规性审核、条款比对、格式检查等，最终输出带原文高亮的审核报告。

核心设计原则：
- **可追溯**：每个 AI 输出都能回溯到原始 PDF 的页码和 bbox 坐标
- **分层解耦**：解析 / 切片 / 检索 / 推理各自独立，可单独替换
- **先程序后 LLM**：能用规则引擎的不调 LLM，LLM 只做边界模糊的语义判断

## 2. 整体架构

### 2.1 处理管线

```
DOCX/PDF 输入
    │
    ├── .docx ──→ LibreOffice headless → .pdf
    │
    └── .pdf  ──→ pdf_extract_service
                     ├── ① Rust lopdf 主引擎
                     └── ② Python pdfplumber 兜底
                              │
                              ▼
                      RawDocument JSON
                    (文本 + 单词坐标 + 表格 + bbox)
                              │
                              ▼
                      sectionize_service
                    (章节结构识别 → Section 树)
                              │
                              ▼
                      chunk_service              ← 当前阶段
                    (3 层切片: 自适应语义切分
                     → 上下文增强 → 双索引)
                              │
                              ▼
                      extract_service
                    (LLM 抽取: Requirement /
                     Evidence / RiskFlag)
                              │
                              ▼
                      混合检索 + 证据链确认
                    (向量召回 → 图关系确认 → 输出)
```

### 2.2 四层存储架构

```
┌──────────────────────────────────────────────────────┐
│  Layer 0: 原始层 — 文件系统                            │
│  原始 PDF/DOCX 文件、LibreOffice 转换中间产物            │
│  职责: 存档、重新解析、原始PDF渲染高亮                    │
└──────────────────────────────────────────────────────┘
                         │
                         ▼
┌──────────────────────────────────────────────────────┐
│  Layer 1: 结构层 — PostgreSQL JSONB                   │
│  RawDocument、SectionizeOutput、Chunk                 │
│  所有带 bbox / block_ids 的定位数据                     │
│  职责: 精确分页查询、高亮坐标回查、结构化过滤              │
└──────────────────────────────────────────────────────┘
                         │
            ┌────────────┼────────────┐
            ▼            │            ▼
┌──────────────────┐    │    ┌──────────────────────┐
│  Layer 2: 检索层  │    │    │  Layer 3: 关系层      │
│  向量数据库        │    │    │  图数据库             │
│  · embed_text     │    │    │  · Requirement       │
│  · 语义相似度搜索  │    │    │  · Evidence          │
│                   │    │    │  · RiskFlag          │
│  职责: "哪里像"    │    │    │  · supports/violates │
│  宽召回候选集      │    │    │                      │
│                   │    │    │  职责: "什么关系"      │
│                   │    │    │  证据链与多跳查询      │
└──────────────────┘    │    └──────────────────────┘
                         │
                         ▼
                   LLM 推理 + 输出
              (Reranker 精排 → Agent 验证 → 结构化结果)
```

**各层职责边界：**

| 层 | 存什么 | 不存什么 |
|----|--------|---------|
| 原始层 | PDF/DOCX 文件、版本号 | — |
| 结构层 | page/block/table 的 JSON、bbox、chunk 全文、section_path | embedding 向量、图关系 |
| 检索层 | embed_text 的向量、chunk_id 外键 | chunk 全文、图关系 |
| 关系层 | Requirement/Evidence/Risk 节点、supports/violates 边、证据链 | chunk 全文、embedding |

**跨层协作流程：**

```
用户查询: "这个项目有哪些资质要求，投标人响应了吗？"
    │
    ▼
Step 1 — 向量召回 (检索层)
    把查询 encode → 在向量库中匹配 Top-20 chunk
    │
    ▼
Step 2 — 邻居补全 (结构层)
    通过 chunk_id → 查 JSONB → 拉取 prev/next chunk → 拼接完整上下文
    │
    ▼
Step 3 — 关系确认 (关系层)
    把候选 chunk 映射到图 → 查 Evidence→Requirement 边 → 发现缺失和冲突
    │
    ▼
Step 4 — LLM 推理
    输入: 补全后的上下文 + 图关系子图
    输出: 审核结论 + source_block_ids 引用
    │
    ▼
Step 5 — 高亮回溯 (结构层)
    source_block_ids → 查 JSONB → 拿到 bbox → 渲染高亮
```

## 3. 文档切片方案

### 3.1 核心问题：为什么固定层级切法不行？

基于两份真实标书的 sectionize 输出，四种方案的对比：

| 方案 | chunk 数 | 中位数 | 最小–最大 | ＜200字占比 | 判决 |
|------|----------|--------|-----------|-------------|------|
| 按章 (L1) | 6 | 12,430字 | 2,666–14,837 | 0% | ❌ 太肥，检索噪音 95%+ |
| 按节 (L2) | 97 | 99字 | 5–5,345 | 68% | ❌ 方差爆炸 |
| 按 L3/L4 | 408 | 66字 | 4–2,147 | 86% | ❌ 太碎，embedding 质量差 |
| 按叶子节点 | 581 | 82字 | 17–2,136 | 91% | ❌ 太碎，丢失层级上下文 |

根因：
1. **"标题即内容"**：87% 的 section 的 body_text ≈ 0，条款正文直接写在标题里
2. **嵌套深度不均匀**：同一份文档里，有的 L2 直接挂正文，有的 L2→L4→L5→L5

结论：需要用**自适应语义切分**替代固定层级切分。

### 3.2 Layer 1 — 自适应语义切分（规则引擎）

**原则**：一个 chunk = 一个可以独立理解、独立评估的完整语义单元。

**规则 1 — 自包含节点直接成 chunk**

```
L2: 三.获取磋商文件  [title=15字, body=195字, children=0]
→ chunk_042: section_chunk, 210 字
  section_path: ["第一章", "三.获取磋商文件"]
  可独立理解: ✅
```

**规则 2 — 纯容器节点不生成 chunk，子节点向上聚合**

```
L2: 二.供应商的资格要求           ← 容器 (body=0)
  L4: 1.供应商应具备《政府采购法》第22条... ← 容器 (body=0)
    L5: 1）具有独立承担民事责任的能力...
    L5: 2）有依法缴纳税收和社会保障资金...
    ...（5条叶子合并为1个 chunk, ~270字）
  section_path: ["第一章", "二.供应商的资格要求",
                  "1.供应商应具备《政府采购法》第22条"]
  语义单元: "政府采购法第22条规定的5项基本条件" → 完整独立
```

**规则 3 — 相邻短叶子合并**

```
L4: 1.项目地点：东莞理工学院松山湖校区6号教学楼。  ← 41字
L4: 2.项目工期：合同签订后60个日历日内完成。       ← 35字
L4: 3.质保期：项目验收合格之日起2年。              ← 30字
L4: 4.完工后，成交供应商需提供竣工图纸。           ← 47字
→ 合并为 1 个 chunk, ~150 字
```

**规则 4 — 超长 chunk 在段落边界硬切**

```
chunk > 1500 字 → 找最近的段落边界（\n\n 或句号换行）
前后 chunk 保留 200 字 overlap
标记为 paragraph_chunk（或 fallback_chunk）
```

**规则 5 — 表格独立成 chunk**

```
在 section.block_ids 覆盖的页面中查找未归属的 RawTable
每张表 → 1 个 table_chunk
序列化为 Markdown table，嵌入前加 [表格] 类型标记
```

**切分阈值常量：**

```rust
const MAX_CHUNK_CHARS: usize = 1500;    // 单 chunk 上限 (~1000 tokens)
const MIN_CHUNK_CHARS: usize = 100;     // 低于此合并到前一个
const OVERLAP_CHARS: usize = 200;       // 硬切时重叠量
const TARGET_CHUNK_CHARS: usize = 600;  // 理想大小 (≈400 tokens)
const LIST_MIN_LINES: usize = 3;        // ≥3 行连续编号视为列表
```

**预估效果**：智慧教室标书 → 60-90 个 chunk，中位数 ~400-600 字。

### 3.3 Layer 2 — 上下文增强（LLM 辅助）

核心思想：先把 chunk 切细（保证 embedding 精度），再用 LLM 为每个 chunk 注入文档级和章节级上下文。

#### 文档摘要（SAC — Summary-Augmented Chunking）

每个文档只调一次 LLM，生成 150 字摘要，所有 chunk 共享：

```
LLM 输入: 文档前 2000 字
LLM 输出:
  "东莞理工学院松山湖校区智慧教室环境改造工程（二期）竞争性磋商文件，
   采购计划编号441901-2023-03715，预算金额3,363,838.20元。
   核心要求：建筑工程施工总承包三级或装修装饰二级以上资质。"
```

#### 逐 chunk 上下文（Contextual Retrieval）

每个 chunk 通过 Prompt Caching 调一次 LLM，生成 50-100 字位置说明：

```
LLM 输出:
  "此条款来自第一章'供应商的资格要求'，是《政府采购法》第22条规定的
   5项基本条件中的第1项，要求投标人提供营业执照证明独立法人资格。
   不满足此项将导致投标无效。"
```

#### 嵌入文本组装

```rust
fn build_embed_text(chunk: &Chunk, doc_summary: &str, chunk_context: &str) -> String {
    format!(
        "【文档】{}\n【位置】{}\n【内容】{}",
        doc_summary,      // 150字 — 区分"哪份标书"
        chunk_context,    // 50-100字 — 区分"哪个条款"
        chunk.text,       // 原始内容
    )
}
// → 送入 embedding 模型
```

**效果参考**（Anthropic 2024 论文）：

| 方案 | Top-20 检索失败率 | 降低 |
|------|-------------------|------|
| 纯原文 embed | 5.7% | — |
| + Contextual Embeddings | 3.7% | −35% |
| + Contextual BM25 | 2.9% | −49% |
| + Reranker | 1.9% | −67% |

### 3.4 Layer 3 — 双索引检索

```
写入（离线）:
  ┌───────────────────────────────────────────────┐
  │ 向量库: 存 Layer 2 增强后的 embed_text（小粒度）│
  │ 文档库: 存原始 chunk + prev/next 邻居引用       │
  │ 元数据库: 存 section_path / page_range / bbox  │
  └───────────────────────────────────────────────┘

查询（在线）:
  Step 1: 用增强后的 embed_text 做向量匹配 → 命中 8-12 个小 chunk
  Step 2: 通过 prev/next 拉取前后邻居 → 补全上下文
  Step 3: 合并同一 section_path 下相邻命中 → 去重、拼接
  Step 4 (可选): Reranker 精排
  Step 5: Top-K 传给 LLM
```

> 当前阶段只做 Step 1-3，Reranker 和混合检索（BM25）是后续优化项。

## 4. 数据库设计

### 4.1 结构化存储 — PostgreSQL JSONB

**定位**：所有"回查原文"的数据都放这里。这是回溯高亮的根。

**存储内容**：

| 表 | 内容 | 查询模式 |
|----|------|---------|
| `raw_documents` | RawDocument 完整 JSON（page/words/blocks/tables/bbox） | 按 document_id 整取 |
| `chunks` | Chunk JSON + 元数据字段（document_id, page_range, section_path） | 按 chunk_id / document_id / page_range 查 |
| `section_trees` | SectionizeOutput JSON | 按 document_id 查章节树 |
| `extraction_results` | Requirement / Evidence / RiskFlag JSON，含 source_block_ids | 按 document_id / 对象类型查 |

**关键索引**：

```sql
-- chunks 表：按文档和页码范围快速定位
CREATE INDEX idx_chunks_doc_page ON chunks USING GIN (document_id, page_range);

-- extraction_results：按来源 block 反查
CREATE INDEX idx_results_source ON extraction_results USING GIN (source_block_ids);
```

**为什么用 JSONB 而不是规范化表**：chunk 的结构因文档类型而异（标书、合同、规范各有不同字段），JSONB 避免了频繁 schema 变更。

### 4.2 向量数据库

**定位**：语义召回——"这段要求在哪里有响应？"

**技术选型**：

| 阶段 | 推荐 | 说明 |
|------|------|------|
| MVP（当前） | pgvector (PostgreSQL 扩展) | 与结构层同一数据库，运维成本为零 |
| 生产 | Qdrant | Rust-native，HNSW 性能更好，支持多租户和 metadata 过滤 |

**存储内容**：

```
每个 chunk 的 embed_text → encoder → vector(1024)
  + payload: { chunk_id, document_id, section_path, chunk_type }
```

**检索参数**：

```rust
// 默认检索配置
const TOP_K: usize = 20;           // 召回数量
const SIMILARITY_THRESHOLD: f32 = 0.65;  // 最低相似度
```

**为什么不用图数据库做语义搜索**：图数据库的向量索引通常不如专用向量库；
LegalGraphRAG（NetworkX）也只是用图做关系遍历，语义匹配靠独立的 embedding 索引。

### 4.3 图关系存储

**定位**：关系确认——"这个证据支撑了哪个要求？这个风险从哪条证据中检出？"

**核心判断**：当前阶段的大部分查询是 1-2 跳（"要求有响应吗""风险关联了哪个证据"），
PostgreSQL 邻接表 + 递归 CTE 完全能够应对。当且仅当出现 3 跳以上的查询
（"资质缺失 → 影响 A 条款 → A 条款关联 B 要求 → B 要求触发 C 风险"），
才需要引入专用图数据库。

**技术选型**：

| 阶段 | 推荐 | 说明 |
|------|------|------|
| MVP（当前） | PostgreSQL 邻接表 | 零新组件，与 pgvector 共享连接，单份标书几十个节点 |
| 生产 | Neo4j Community | 当出现 3+ 跳查询或需要图可视化时迁移 |

#### 节点设计（4 种）

| 节点类型 | 字段 | 真实数据对应 |
|---------|------|------------|
| **RequirementGroup** | `id, title, section_path, source_chunk_ids, document_id` | `"1.供应商应具备《政府采购法》第22条规定的条件"`（容器节点，body=0） |
| **Requirement** | `id, title, content, mandatory, req_type, regulation_refs, source_chunk_ids, group_id` | `"1）具有独立承担民事责任的能力：在中华人民共和国境内注册的法人..."` |
| **Evidence** | `id, content, evidence_type, source_chunk_ids, document_id` | 投标文件中对应的资质证书描述、承诺函内容 |
| **RiskFlag** | `id, title, description, severity, risk_category, regulation_refs, source_chunk_ids, review_status` | `"★条款无响应"` `"资质证书过期"` |

**移除了 RegulationRef 和 Review 节点**：

| 移除 | 原因 | 替代方案 |
|------|------|---------|
| RegulationRef | 真实数据中 80%+ 是文档内一次性引用（15+ 条 GB 标准只被引用一次），建成节点是死胡同 | 作为 `regulation_refs: Vec<String>` 字段挂在 Requirement/RiskFlag 上；跨文档共享的法规（如政府采购法第22条）在 Phase 2 按需建节点 |
| Review | 本质是审计日志，每次人工审核追加一行，不是图关系 | PostgreSQL `review_logs` 审计表；审核状态作为 `review_status` 字段挂在 RiskFlag 上 |

#### 边设计（5 种）

| 边 | 方向 | 何时建立 | 真实示例 |
|----|------|---------|---------|
| `belongs_to` | Requirement → RequirementGroup | Chunk 抽取时自动建立（利用 section_path 层级关系） | `"1）具有独立承担..."` → `"1.供应商应具备《政府采购法》第22条"` |
| `supports` | Evidence → Requirement | 向量匹配 + LLM 确认（高置信度） | `"营业执照副本复印件"` → `"独立法人资格要求"` |
| `partial` | Evidence → Requirement | 向量匹配 + LLM 确认（部分匹配） | `"资质证书（已过期）"` → `"资质要求"` |
| `violates` | Evidence → Requirement | LLM 检测到偏离 | `"偏离声明"` → `"技术参数要求"` |
| `derived_from` | RiskFlag → Evidence 或 RiskFlag → Requirement | Risk 抽取时自动建立 | `"资质过期风险"` → `"过期证书"` |

**移除了 3 种边**：

| 移除 | 原因 |
|------|------|
| `cites` (RiskFlag → RegulationRef) | RegulationRef 不在图中 |
| `reviewed_by` (RiskFlag → Review) | Review 不在图中 |
| `relates_to` (Requirement ↔ Requirement) | 没有自动发现依赖的抽取逻辑，Phase 2 按需加入 |

#### 构建时机

图关系**不在招标文件上传后立即构建**——此时只有 Requirement，全是孤立节点，没有遍历价值。

```
T1: 招标文件上传
    → Chunk → 向量库 (embed_text)
    → PostgreSQL: Requirement + RequirementGroup (无图边)

T2: 投标文件上传
    → Chunk → 向量库 (embed_text)
    → 向量召回: Requirement ←→ Evidence 候选匹配
    → LLM 确认: supports / partial / violates 边
    → 此时图才"活"了——可以遍历证据链
```

#### MVP 的 PostgreSQL 邻接表实现

```sql
-- 替代图数据库的核心表
CREATE TABLE evidence_chain (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    evidence_id UUID NOT NULL,
    requirement_id UUID NOT NULL,
    relation_type TEXT NOT NULL CHECK (relation_type IN ('supports', 'partial', 'violates')),
    confidence REAL,
    source_chunk_ids TEXT[],
    created_at TIMESTAMPTZ DEFAULT now()
);

CREATE INDEX idx_chain_req ON evidence_chain(requirement_id);
CREATE INDEX idx_chain_ev ON evidence_chain(evidence_id);

-- 查询"未响应的强制要求"（1 跳，不需要图数据库）
SELECT r.id, r.title
FROM extracted_items r
WHERE r.item_type = 'requirement'
  AND r.mandatory = true
  AND r.document_id = $1
  AND NOT EXISTS (
    SELECT 1 FROM evidence_chain ec
    WHERE ec.requirement_id = r.id
      AND ec.relation_type = 'supports'
  );

-- 查询"某个缺失对其他要求的影响"（2 跳，邻接表递归 CTE 可以胜任）
WITH affected AS (
    -- 第 1 跳：找到缺失直接影响的 Requirement
    SELECT r2.id, r2.title, 1 AS depth
    FROM evidence_chain ec
    JOIN extracted_items r1 ON ec.requirement_id = r1.id
    JOIN extracted_items r2 ON r1.group_id = r2.group_id
    WHERE ec.evidence_id = $1 AND ec.relation_type = 'partial'
      AND r2.id != r1.id
)
SELECT * FROM affected;
```

#### 图数据库不该存的内容

| 不要存 | 原因 | 替代方案 |
|--------|------|---------|
| Chunk 全文 | 图节点应轻量（百字以内） | PostgreSQL JSONB |
| Embedding 向量 | 图数据库的向量索引非其强项 | pgvector / Qdrant |
| PDF 二进制 | 图数据库不是 Blob 存储 | 文件系统 |
| 中间解析产物 | 临时数据不需持久化到图 | 临时文件或中间表 |
| 法规条文全文 | 法规原文长，且大部分是死胡同引用 | `regulation_refs: Vec<String>` 字段 |
| 审计日志 | 每次人工操作追加一条，与内容关系无关 | PostgreSQL 审计表 |

### 4.4 各层职责速查

| 问题 | 负责层 | 查询方式 |
|------|--------|---------|
| "第 3 页第 2 段写了什么？" | 结构层 | SQL: `SELECT text FROM chunks WHERE block_ids @> '{b_3_2}'` |
| "和这条要求语义相似的有哪些？" | 检索层 | 向量检索: `query_vec <-> embed_vec LIMIT 20` |
| "这 20 个候选分别属于哪个章节？" | 结构层 | SQL: `SELECT section_path FROM chunks WHERE chunk_id IN (...)` |
| "哪些候选已被标记为风险？" | 关系层 | SQL: `SELECT * FROM evidence_chain WHERE evidence_id IN (...) AND relation_type = 'violates'` |
| "为什么说这个风险点引用的是这条法规原文？" | 结构层 | `regulation_refs` 字段 → SQL 回查原文（法规不在图中） |
| "高亮框应该画在哪里？" | 结构层 | SQL: `SELECT bbox_refs FROM chunks WHERE chunk_id = $1` |
