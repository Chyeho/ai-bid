# AI 招标文件合规审查系统 — 验证

本文档与 [设计.md](./设计.md) 中的各模块一一对应，每个模块覆盖 **验证目标 → 验证用例 → 期望产出**，
与设计、实现形成 **设计 → 实现 → 验证** 的闭环。

验证总原则：

- **确定性验证优先**：规则引擎（无 LLM）模块，相同输入必须产生相同输出 — 精确回归测试可行。
- **分层验证**：单元验证（函数级）→ 模块验证（Step 级）→ 集成验证（全链路）。
- **Golden Data 策略**：用真实标书的已知正确输出作为回归基准。

**用例 V1.1 — LibreOffice 查找策略**

```
前置条件: 准备三种环境配置

  环境 B: 不设环境变量，LibreOffice 安装在 Windows 默认路径

  1. 在环境 A 中调用 find_soffice() → 期望返回 LIBREOFFICE_PATH 指向的路径
```

**用例 V2.1 — 文本清洗**

```
前置条件: 准备含中文绝对定位字符的 PDF（已知 layout raw_text）

验证步骤:
  1. 对每页的 raw_text 调用 clean_layout_text()
  2. 检查输出文本中不存在 "字  字" 模式（中文字符间不应有
     连续空格，即 CJK 字符之间的空格已被合并）

测试输入构造:
  输入: "投  标  人  须  在  东  莞  地  区  设  有  常  驻  服  务  机  构"
  期望: "投标人须在东莞地区设有常驻服务机构"

  输入: "符合  以下  条件"（英文词间保留 2 空格）
  期望: "符合  以下  条件"

  输入: "第一章  总  则\n第二条  合同  标的"
  期望: "第一章  总则\n第二条  合同标的"

通过标准:
  - CJK_SPACE_RE 规则：中文字符间不再出现空格（"字字" OK，"字 字" NG）
  - MULTI_SPACE_RE 规则：所有连续空格被压缩为 2 空格
  - 迭代最多 5 轮收敛（不无限循环）
```

**用例 V2.2 — 单词 ID 和 BBox**

```
前置条件: 对已知结构的 PDF 执行 extract_pdf_to_raw_json()

验证步骤:
  1. 遍历所有 pages[].words[]
  2. 对每个 word:
     a. 验证 id 格式匹配 Regex: ^w_\d+_\d+$
     b. 验证 id 的前缀页号与 page_index 一致
     c. 验证 bbox 约束:
        - x0 ≤ x1（宽度非负）
        - top ≤ bottom（高度非负）
        - x0 ≥ 0, x1 ≤ page.width（水平在页面内）
        - top ≥ 0, bottom ≤ page.height（垂直在页面内）
     d. 验证 text 非空（空字符串的 word 应被过滤）
  3. 验证同一页内 word id 的序号从 0 开始连续递增（无跳号）

通过标准:
  - 100% word 满足 ID 格式约束
  - 100% word 满足 BBox 几何约束
  - 每页 word 序号连续
```

**用例 V3.1 — 七种标题模式匹配**

```

测试数据（每行对应一个模式）:
  第一章 磋商邀请                          → level=1, pattern=chapter
  第二节 项目概况                          → level=2, pattern=section
  一、供应商资格要求                       → level=2, pattern=cjk_numbered
  二.项目预算                             → level=2, pattern=cjk_numbered
  （一）基本资格条件                       → level=3, pattern=paren_cjk
  (二) 特定资格要求                       → level=3, pattern=paren_cjk
  1. 具有独立承担民事责任的能力              → level=4, pattern=digit_dot
  2、具有良好的商业信誉                     → level=4, pattern=digit_dot
  3)健全的财务会计制度                      → level=4, pattern=digit_dot
  （1）营业执照副本                        → level=5, pattern=paren_digit
  (2) 法定代表人证明                       → level=5, pattern=paren_digit
  第九条 工程的支付、结算                   → level=4, pattern=article

边界 case（不应匹配）:

验证步骤:
  1. 对每个正例，验证对应 pattern.regex.is_match() == true
  2. 验证匹配到的 level 与设计文档的映射表一致
  3. 边界 case 验证: 空行不匹配、仅有编号而无后续字符的不匹配
```

```
      L5: 1）具有独立...            ← body="在中华人民共和国境内注册..." (叶子)
      L5: 2）有依法缴纳税收...      ← body="提供《资格条件承诺函》..." (叶子)
      L5: 3）具有良好的商业信誉...  ← body="..." (叶子)

验证步骤:
  1. 对整棵树调用 chunk_sections()
  2. 验证 L2 和 L4 本身不生成任何 chunk（容器不占 chunk 名额）
  3. 验证生成 1 个 Merged chunk（规则 2 聚合 + 规则 3 合并）
  4. 检查该 chunk 的 section_path:
     期望 = ["二.供应商的资格要求", "1.供应商应具备..."]
     验证 L2 和 L4 的标题都在 path 中（容器提供了命名空间）
  5. 检查 chunk 的 text 包含全部 3 个 L5 的内容

通过标准:
  - 容器节点数量 = 0 chunk（不产生冗余空块）
  - 子节点的 section_path 携带了容器标题链
  - 聚合后的 chunk 语义完整（一个 chunk 包含法条全部条件）
```

#### 用例 V4.3 — 规则 3：相邻短叶子合并

```
前置条件: 构造同一父节点下有 4 个短叶子的树

测试数据:
  父节点 L3: 一.项目概况
    L4: 1.项目地点：东莞理工学院松山湖校区6号教学楼。     ← 41 字
    L4: 2.项目工期：合同签订后 60 个日历日内完成。         ← 35 字
    L4: 3.质保期：项目验收合格之日起 2 年。                ← 30 字
    L4: 4.完工后，成交供应商需提供竣工图纸。               ← 47 字

  4 个叶子各 < 100 字，合并后 ~150 字 < 1500

验证步骤:
  1. chunk_sections() → 期望生成 1 个 chunk
  2. chunk_type == Merged { rule: "adjacent_merge", child_count: 4 }
  3. chunk.text 包含全部 4 条的标题和正文

边界 case:
  场景 A: 3 个叶子 [30字, 120字, 25字]，中间 ≥ 100 字
    期望: 第1个入缓冲 → 第2个字够大，先 flush 缓冲(第1条单独)，
          第2条单独 Leaf，第3条入新缓冲
    结果: 3 个 chunk: Merged(child_count=1), Leaf, 单独的短叶子

  场景 B: 5 个叶子各 400 字（合并后 2000 字 > 1500）
    期望: 前 3 个合并 flush（~1200 字），后 2 个合并 flush（~800 字）
    结果: 2 个 Merged chunk

  场景 C: 全部叶子 ≥ 100 字
    期望: 各自成 Leaf，不触发合并

通过标准:
  - merge_min_len=100: <100 进入合并候选，≥100 单独 Leaf
  - 合并中总长触及 split_max_len=1500 时提前 flush
  - child_count 准确反映实际合并的叶子数
```

#### 用例 V4.4 — 规则 4：硬切与 Overlap

```
前置条件: 构造一个 1800 字符的 body_text，其中包含段落边界

测试数据:
  text = "第一段...(800字)\n\n第二段...(600字)\n\n第三段...(400字)"
  split_max_len = 1500, split_overlap = 200

验证步骤:
  1. chunk_sections() → 期望生成 2 个 Split chunk
  2. 验证切分点在 \n\n 段落边界（而非 1500 字符处硬切）
  3. 第 1 个 chunk: Split { part: 1, total: 2 }
     末尾 200 字符与第 2 个 chunk 开头 200 字符相同（overlap）
  4. 第 2 个 chunk: Split { part: 2, total: 2 }
  5. 验证 overlap 内容确实重复（不是截断导致信息丢失）

边界 case:
  场景 A: 1600 字无任何段落边界
    期望: 在 1500 字符处硬切（找不到边界就精确切）
  场景 B: 3000 字 → 期望 3 个 Split chunk
  场景 C: 边界恰好在 1500 处 → 精确切，不 overlap 到边界另一侧

通过标准:
  - 切分点在段落边界（\n\n 或 \n 后跟中文序号）
  - overlap 长度 = split_overlap (200)
  - Split.part 和 Split.total 编号正确（part 从 1 开始连续到 total）
  - 所有 part 拼接（去 overlap 重复）≈ 原始 text
```

#### 用例 V4.5 — 规则 5：embed_text

```
前置条件: 构造一个 section_path 已知的 chunk

测试数据:
  chunk.section_path = ["第一章 磋商邀请", "二.供应商的资格要求", "1.基本条件"]
  chunk.text = "1）具有独立承担民事责任的能力：在中华人民共和国境内注册..."

验证步骤:
  1. embed_text(ctx_depth=2):
     期望 = "【二.供应商的资格要求 > 1.基本条件】\n1）具有独立承担民事责任的能力：在中华人民共和国境内注册..."
  2. embed_text(ctx_depth=1):
     期望 = "【1.基本条件】\n1）具有独立承担民事责任的能力：在中华人民共和国境内注册..."
  3. embed_text(ctx_depth=0) 或 section_path 为空:
     期望 = chunk.text（无前缀，直接返回原文本）

通过标准:
  - 前缀取 section_path 最后 ctx_depth 级
  - 格式为 "【L(N-1) > L(N)】\n{text}"
  - ctx_depth 超过 path 长度时取全部（不 panic）
  - 空 path 不产生 "【】" 空壳
```

### 4.4 与阶段 1 前序模块的关系

```
RawDocument JSON ──→ sectionize_service ──→ Section 树 JSON
                                                │
                    chunking_service ◄──────────┘
                         │
                         ▼
              output/chunks/{文档名}_chunks.json
                         │
                         ▼
              embed_text() → Embedding → ChromaDB → Agent search_document
```

Chunk 切分的上游依赖是 Section 树（§3），下游消费者是 Embedding 和 Agent 审查。
验证时需要确保：Section 树中的 `block_ids` 经过 Chunk 透传后仍可追溯到 RawDocument 的原始坐标。
