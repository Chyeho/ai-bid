## MVP 范围声明

本项目分阶段交付，**MVP = 审招标文件**（单文档合规审核）。后续阶段逐步扩展。

```
Phase 1-2: 审招标文件 ──→ 第一个可 Demo 的产品
Phase 3:   + 审投标文件 ──→ 双文档独立审核
Phase 4:   + 招投标全流程 ──→ 招标+投标对照审核 + 知识飞轮完整闭环
```

| 阶段 | 审核对象 | 审核逻辑 | 核心差异 |
|---|---|---|---|
| **MVP (Phase 1-2)** | 招标文件 | 单文档合规检查：条款合法性、排斥性条款、评分合理性 | 对着一份文件找问题 |
| **Phase 3** | + 投标文件 | 单文档完整性检查：资质响应、参数偏离、漏项、格式 | 同上，但规则体系不同 |
| **Phase 4** | + 招投标全流程 | 双文档对照：招标要求 vs 投标响应逐条比对 | 需要关联两份文档的对应条款 |

> **为什么先做审招标文件**：招标文件是源头——招标文件有问题，后面所有投标都会有问题。而且审招标文件的规则更偏向法律法规合规，知识库冷启动更容易（法规是公开的）。审投标文件需要行业参数库（不同产品的技术参数标准），冷启动成本更高。

## 一、项目概述

### 1.1 产品定位

一款 **AI 驱动的标书合规性审核 SaaS 平台**。客户上传招标文件或投标文件，系统自动检测合规问题、条款缺失、资质不匹配等风险，输出结构化审核报告。

### 1.2 核心技术理念：平台能力分层

每做一个产品，都要把底层能力沉淀为可复用的平台。本项目的 9 个组各对应一层平台能力，层与层之间只通过数据结构通信，可独立开发、独立测试、独立演进。

### 1.3 全局设计原则

- **解耦优先**：组与组之间仅通过 JSON Schema 接口通信，禁止隐式依赖
- **先跑通再优化**：MVP 阶段优先打通全链路，性能优化在链路跑通后进行
- **规则引擎前置**：确定性规则过滤 90% 简单问题，AI 只处理剩余的复杂语义
- **异步非阻塞**：重任务（文档解析、AI 审核）全部走异步队列，前端即时响应
- **知识飞轮**：每次审核的结果回写到知识库，让系统越用越准

### 2.4 高亮回溯链路：从审查结论定位到 PDF 原文位置（跨组协作）

当审核报告显示一条风险（如"第 5 页存在地域歧视性条款"），用户点击后，PDF 查看器自动滚动到第 5 页并高亮对应段落。这是产品体验的核心竞争力——竞品只给文字报告，我们给"可定位、可验证"的审查结果。

**核心原理**：每一层数据都携带指向原始 PDF 坐标的 ID 引用，形成一条永不中断的溯源链。

```
G1 文档解析（PDF 提取阶段）
  为每个段落分配确定性 ID + BBox 坐标
  Block "b_5_2" → bbox: {x0:72, top:320, x1:540, bottom:340}
       │
       ▼  ID 随数据逐层下行
G1 Section 树 ── block_ids: ["b_5_2", ...]
G1 Chunk     ── block_ids + bbox_refs 预计算缓存
       │
       ▼  Agent 输出时引用 block_id
G4/G5 Agent  ── clause_id: "b_5_2", source_quote: "投标人须在东莞..."
       │
       ▼  反向查找：block_id → bbox → 页面坐标
G8 前端      ── GET /api/v1/documents/:id/blocks?ids=b_5_2
               → 在第 5 页 (72,320)-(540,340) 绘制高亮矩形
```

**两层查找机制**：

| 路径 | 方式 | 耗时 | 场景 |
|---|---|---|---|
| 热路径 | Chunk.bbox_refs 预计算缓存 → O(1) 直接取 | < 1ms | 正常情况 |
| 兜底路径 | source_quote 子串匹配 → 在目标页面 blocks[] 中搜索 | < 50ms | PDF 版本差异导致 bbox 偏移 |

**跨组协作关系**：

| 组 | 职责 |
|---|---|
| **G1** | 分配 Block ID（确定性、可复现），计算 BBox 坐标，Chunk 携带 bbox_refs 预缓存 |
| **G4/G5** | Agent System Prompt 强制要求输出 `clause_id` + `source_quote`（原文逐字摘录），禁止改写 |
| **G8** | 提供 `GET /api/v1/documents/:id/blocks?ids=...` BBox 查询接口 |
| **G9** | PDF 查看器渲染：接收 bbox 坐标 → 绘制半透明高亮矩形 → 滚动到目标页面 |

> **实现状态**：全部已实现（设计.md §5）。各组需维护各自环节——G1 保证 ID/BBox 正确性，G4/G5 保证 Agent 输出引用 block_id，G9 保证渲染准确。

### 3.2 G1 文档解析引擎（3 人）

#### 职责

将 PDF/Word 招标投标文件解析为结构化的 `ParsedDocument`，是整个系统的数据入口。文档解析质量决定系统天花板。

#### 技术选型

| 组件 | 选型 | 说明 |
|---|---|---|
| 主解析引擎 | Docling (IBM) | 统一 DoclingDocument 格式，含布局/表格/层级 |
| 中文表格增强 | MinerU | 复杂中文表格场景的补充方案 |
| OCR 增强 | PaddleOCR | 扫描件 PDF 的文字识别 |
| 版面分析 | Florence-2 (可选) | 轻量多模态模型，单图推理极快 |
| 任务队列 | Redis Streams | 异步解析，避免阻塞 HTTP 接口 |

#### 输出 Schema

  "page_count": 120,

#### 核心指标

| 指标 | 目标 |
|---|---|
| 解析耗时 | < 5 秒 / 百页 PDF |
| 表格识别率 | > 95% |
| 章节分割准确率 | > 90% |
| 扫描件 OCR 准确率 | > 95% |

#### 工程要点

- 异步消费 Redis Streams 任务，解析完成后写回结果
- 解析结果缓存：同一文件（hash 相同）不重复解析
- 分片并行：大文档拆分为 4 个分片并行处理（商务/技术/评分/资质）
- 坏页容错：单页解析失败不中断整文档，标记 `parse_error` 字段

### 3.3 G2 规则匹配引擎（2 人）

#### 职责

读取 G1 输出的 `ParsedDocument`，基于 YAML 规则库执行确定性匹配，快速过滤 90% 的简单合规问题。输出 `RuleMatch[]`，**不调用任何 AI**。

> 这是竞品"秒级出结果"的核心原因——规则引擎不调大模型，纯 CPU 模式匹配，毫秒级完成。

#### 技术选型

| 组件 | 选型 | 说明 |
|---|---|---|
| 规则定义 | YAML 文件 | 人类可读写，版本管理友好 |
| 匹配方式 | 正则 + 关键字 + 字段比较 | 轻量，无外部依赖 |
| 规则 IDE | 简版在线规则编辑器（G8 配合）| 方便后续运营人员维护规则 |
| 实现语言 | Rust | 与已有代码统一，性能高 |

#### 规则 YAML 格式

规则本身是核心资产，不是简单的 keyword matching。每条规则需要包含**行业分类、来源追溯、适用条件**三个维度——同一个资质要求在不同行业完全不同，缺少来源的规则不可维护，没有适用条件的规则会产生大量误报。

```yaml
# rules/qualification.yml
rules:
  - id: "QUAL-001"
    category: "资质要求"
    industry: "建筑工程"              # 行业分类（建筑工程/政府采购/IT/医疗/...）
    severity: "critical"
    description: "未明确要求建筑工程施工总承包资质"

    # ── 来源追溯（这条规则从哪里来，法律依据是什么）──
    source:
      law: "建筑业企业资质管理规定"
      article: "第三条"
      version: "2015年修订版"
      effective_date: "2015-03-01"
      url: "https://www.gov.cn/..."

    # ── 适用条件（不是全局扫，满足条件才触发）──
    conditions:
      document_type: "招标文件"       # 适用文档类型
      project_type: "施工招标"        # 适用项目类型（勘察/设计/施工/监理/货物）
      trigger:                        # 触发条件：当文档中存在"资格要求"章节时触发
        chapter_keywords: ["资格要求", "资格条件", "投标人资格"]
      exclude:                        # 排除条件：不适用于这些场景
        project_types: ["勘察设计一体化"]

    patterns:
      - type: "regex"
        value: "建筑工程施工总承包.*资质"
        target: "all_clauses"
      - type: "keyword"
        value: ["资质要求", "资格条件"]
        target: "chapter_titles"
    check: "must_exist"
    suggestion: "建议在投标人资格要求中明确施工总承包资质等级"
    law_ref: "《建筑业企业资质管理规定》第三条"

  - id: "PRICE-001"
    category: "报价要求"
    industry: "通用"                  # 跨行业通用规则
    severity: "warning"
    description: "投标报价超过预算上限"

    source:
      law: "中华人民共和国政府采购法"
      article: "第三十六条"
      version: "2014年修正版"

    conditions:
      document_type: "招标文件"
      trigger:
        table_keywords: ["预算", "最高限价", "控制价"]
        require_field: "budget_limit"  # 只有文档中存在预算金额时才触发

    patterns:
      - type: "field_compare"
        field_a: "total_price"
        field_b: "budget_limit"
        target: "table_values"
    check: "compare_value"
    compare:
      operator: "lte"
    suggestion: "投标报价不得超过预算上限金额"
    law_ref: "《政府采购法》第三十六条"
```

> **规则字段说明**：`industry`、`source`、`conditions` 三个字段是 MVP 必须字段——不是锦上添花，是规则可维护、可审计、可迁移的基础。没有 `source` 的规则客户无法信任，没有 `conditions` 的规则误报率不可控。

{

  "matches": [
    {
      "rule_id": "QUAL-001",
      "category": "资质要求",

    "critical_failures": 3
  }

```

#### 核心指标

| 指标 | 目标 |
|---|---|
| 规则匹配耗时 | < 1 秒 / 百页文档 |
| 召回率 | > 95%（宁可误报，不可漏报）|
| MVP 规则数量 | ≥ 100 条 |
| 规则覆盖类别 | 资质 / 业绩 / 报价 / 工期 / 人员 / 安全 / 环保 |

#### 领域建模要点（关键）

规则引擎的核心挑战不是技术实现，而是**领域建模**——把招标投标法规正确地转化为可执行的规则。2 人团队中，至少 1 人应花 **50% 时间研究法规本身**，而不是写代码。

**为什么领域建模比技术重要**：

| 问题 | 纯技术视角 | 领域建模视角 |
|---|---|---|
| "建筑工程施工总承包资质" | 写一条 regex 匹配 | 不同等级（特级/一级/二级/三级）对应不同合同金额上限，不是简单的"有没有" |
| "安全生产许可证" | 全局搜索关键词 | 建筑施工企业需要，货物供应商不需要——行业的适用条件决定了规则是否触发 |
| 法规变更 | 改 YAML 字段 | 2015 版《建筑业企业资质管理规定》已替代 2007 版——规则必须标注适用版本，否则引用失效法律 |

**G2 第一个交付物不是代码，而是**：

1. **行业分类体系**（W1-W2）：确定 MVP 覆盖的行业（建议：建筑工程优先），定义行业标签树
   ```
   建筑工程 → 施工招标 / 勘察招标 / 设计招标 / 监理招标
   政府采购 → 货物采购 / 服务采购 / 工程采购
   IT       → 软件开发 / 硬件采购 / 系统集成
   ```
2. **法规清单**（W1-W3）：梳理每个行业的核心法规（法律+行政法规+部门规章），标注版本和生效日期
3. **规则抽取**（W2-W5）：从法规中逐条抽取可检查的规则 → 标注来源 → 定义适用条件 → 写入 YAML
4. **规则验证**（W4-W6）：用真实招标文件逐条验证——是否触发？是否误报？是否漏报？

> **核心认知**：规则本身就是资产。1000 条经过验证的、带来源追溯和适用条件的规则，是客户愿意付费的原因——不是"我们用了 AI"，而是"我们整理了 1000 条行业审核规则，每一条都能告诉你是哪个法规第几条要求的"。

#### 工程要点

- **不调 AI**：规则引擎是纯确定性计算，不依赖任何外部 LLM API
- 规则库版本管理：YAML 文件纳入 Git，修改规则 = 修改代码一样走 PR
- 支持规则开关：单条规则可启用/禁用
- 初期规则来源：用 AI 批量从法规文件提取 → 人工校验 → 写入 YAML

思考1§五（规则引擎前置，减少 AI 调用）、思考3§五层漏斗第 2 层（规则引擎层 — 确定性检查）

### 3.4 G3 知识检索引擎（2 人）

#### 职责

审核时被 Agent 实时调用，检索本地法律知识库（Qdrant 向量库 + Neo4j 图库 + BM25 关键词），返回法规/案例/负面清单证据。

> G3 是"消费知识"的一方。知识从哪来？来自 G6（知识沉淀引擎）——每次审核后精华自动入库，G3 下次检索时命中率越来越高。

#### 技术选型

| 组件 | 选型 | 说明 |
|---|---|---|
| 嵌入模型 | BGE-M3 (ONNX 本地) | 1024d dense + sparse，已有代码 |
| 向量数据库 | Qdrant（目标）/ Milvus Lite（过渡）| Qdrant 支持持久化+增量写入+元数据过滤 |
| 词法检索 | BM25 (tantivy) | 关键词精准匹配，Rust 原生 |
| 重排序 | BGE-Reranker-v2-m3 | 对召回结果精排 |

#### 检索流程

```
Agent 调用 search_knowledge("地域限制 资格条件", "法规")
    │
    ├── 第1层：本地知识库（优先，毫秒级，零 API 消耗）
    │   ├── Qdrant 向量语义匹配 → Top-K
    │   ├── Neo4j 图遍历 → 法规→条款→案例 关系链
    │   └── BM25 关键词精准匹配
    │
    └── 第2层：大模型 AI 搜索（兜底，本地未命中时触发）
        └── DashScope 联网搜索 → 结果标记 _curation_mark → G6 后续入库
```

#### 初期知识库冷启动

| 知识类型 | 来源 | 预估规模 | 构建方式 |
|---|---|---|---|
| 国家法规 | 招标投标法、政府采购法、建筑法等 | ~500 条 | AI 批量提取 + 人工校验 |
| 地方规章 | 各省市政府采购管理办法 | ~3000 条 | 爬虫 + AI 结构化 |
| 负面清单 | 各级政府采购负面行为清单 | ~500 条 | 手动整理 |
| 标准范本 | 住建部标准施工合同等 | ~200 份 | 下载 + 切片 |
| 历史案例 | 财政部投诉处理决定 | ~200 条 | AI 摘要 + 人工标注 |

### 3.5 G4 Agent 智能组（3 人）

#### 你要解决的问题

现有 Agent 框架（Coordinator + ReAct Loop + AgentBus + SessionGraph）已经完成了 **"把 Agent 跑起来"**的工作——8000+ 行生产级 Rust 代码，11 个 Agent，7 阶段 Pipeline，并发调度、消息总线、SSE 事件流全部就绪。

**但跑起来 ≠ 审得准。**

客户不会因为"我们用了 Multi-Agent"就付钱。客户付钱是因为——"它能发现我漏掉的废标风险，每条都有法律依据，而且我验证过它是准的"。

G4 的核心问题：**怎么让 Agent 审得准、审得全、审得让人信服？**

> G4 不再"维护框架代码"。现有框架是你们的**实验平台**——在上面跑评测、做实验、测策略。框架代码的适配和 bug 修复顺手处理，但不是主要产出。
>
> **关于现有架构**：Coordinator 7 阶段 Pipeline、11 个 Agent、AgentBus——这些是我的设计，但不是正确答案。如果你认为这个架构过度设计了、或者有更简洁的方案能达到更高的 F1——提出来，设计你的替代架构，跑对比实验。**用评测数据证明你的方案更好，就用你的。** G4 的目标是做最准的 Agent，不是维护我的设计。

#### 三个子方向

**方向 A：审核评测框架（1 人）**

核心问题：**你说 Agent 准确率 85%，怎么证明？每次改 Prompt 是变好了还是变差了？**

你的工作：
- 构建 50 份人工标注的招标文件 Benchmark（与法律专业同学协作，每条标注含法规依据+原文位置+严重程度）
- 搭建自动化评测 Pipeline：每次变更 → 全量跑评测 → 自动输出 Precision/Recall/F1 → 回归检测（新 Prompt 修了 3 个漏报但新增了 5 个误报？）
- 建评测 Dashboard：按 Agent 维度、按问题类型、按行业——让所有人一眼看到瓶颈在哪
- 竞品对标：同一份文档，人工 vs 我们的系统 vs GPT-4 直接审 → 对比报告

**方向 B：Agent 推理质量（1 人）**

核心问题：**Agent 说"依据《招标投标法》第 25 条"，这法律条款真实存在吗？Agent 说"招标文件第 5 页要求……"，原文真的是这个吗？**

你的工作：
- 幻觉检测：法规幻觉（引用不存在法条）、原文幻觉（引用的原文与文档不符）、数值幻觉（数字来自哪？）、推理跳跃（跳过了关键步骤）
- 推理链质量评估：Observation → Evidence → Rule → Conclusion 每一步是否可追溯
- 引用准确性：Agent 输出的 block_id、law_ref、source_quote、evidence_id 是否全部正确
- 可解释性增强：从"我们认为有问题"升级为"因为《XX 法》第 X 条规定 Y，而招标文件第 Z 页写了 W，两者矛盾"

**方向 C：多 Agent 协作策略（1 人）**

核心问题：**3 个 Agent 一起审一定比 1 个好吗？什么情况下该协作、什么情况下该独立？**

你的工作：
- 协作模式对比实验：同 50 份文档，跑 Pipeline（串行）vs Parallel-Vote（并行投票）vs Debate（辩论）vs Single-Agent（基线），对比 F1 + 成本
- 动态路由：不做硬编码关键词匹配——基于文档特征（工程招标/货物采购/服务招标）自动选择最优 Agent 组合
- 成本-质量自适应：简单条款 → 规则引擎（零 API 成本），中等条款 → 单 Agent + qwen-plus，复杂条款 → 多 Agent 辩论 + qwen-max
- 协作可视化：审核报告中展示"这个发现经过了哪些 Agent 审查、它们是否一致、最终置信度如何"

#### 输出与接口

```
对 G5 的接口:
  - 评测结果反馈: G4 跑完评测 → 告诉 G5 "JudgeAgent 在参数倾向性上 F1 只有 0.62" → G5 据此优化 Prompt
  - 工具需求建议: 推理质量分析发现缺少某类检测能力 → 建议 G5 开发对应工具

对 G8 的接口:
  - SSE 进度推送（复用现有 ReviewEventBus）
  - 审核结果回调

对 G3 的接口:
  - 通过 G5 的工具间接调用 G3 知识检索（G4 不直接调 G3）
```

#### 成功标准

| 指标 | Phase 2 目标 | Phase 4 目标 |
|---|---|---|
| **审核 F1 Score**（50 份人工标注文档） | > 0.80 | > 0.88 |
| **Critical Recall**（致命问题不能漏） | > 95% | > 98% |
| **法规幻觉率**（引用不存在法条的比例） | < 10% | < 5% |
| **推理链可追溯率**（每步有据可查） | > 70% | > 90% |

#### 现有资产

现有 `backend-rust/src/agents/` 约 8000+ 行代码是你们的实验平台：Coordinator 7 阶段 Pipeline、ReAct Loop、AgentBus、SessionGraph、SSE 事件流、11 个 Agent、11+ 个工具。**Phase 1 投入理解代码；Phase 2 用精简配置跑通 MVP（3 Agent 串行）；Phase 3-4 在上面跑实验、冲指标。**

#### 建议方向

评测框架用 Python/Rust 均可，与现有框架的 ReviewEventBus SSE 流对接。推理质量检测可与 G5 的 Prompt 工程形成反馈闭环——G5 改 Prompt，G4 跑评测，数据返回 G5 继续优化。

### 3.6 G5 领域工具组（3 人）

#### 你要解决的问题

Agent 能跑起来（G4 有现有框架），但 Agent 知道该审什么吗？知道招标文件里什么东西是问题、什么东西不是问题吗？知道一条法规和当前条款之间的关系吗？

**G5 负责让 Agent"懂行"。** 工具是 Agent 的手，Prompt 是 Agent 的脑，领域知识是 Agent 的底子。G4 告诉你 Agent 哪里审得不准，你负责让它更准。

> G5 和 G4 的关系：G4 跑评测 → 告诉你"JudgeAgent 在参数倾向性检测上 F1 只有 0.62"→ 你改 Prompt、加 Few-shot 示例、调整工具调用策略 → G4 再跑评测验证。这不是上下游交付关系，是**反馈闭环**。

#### 三个子方向

**方向 A：审查工具研发（1-2 人）**

核心问题：**Agent 知道审什么，但有没有合适的工具让它审？** 现有的 6 个专用工具在真实招标文件上覆盖率够不够？有没有关键审查维度现在没有工具覆盖？

你的工作：
- 完善现有工具：为每个工具建立 30-50 个单元测试用例（正常/边界/异常），目标执行准确率 > 95%
- **工具触发验证**（关键）：单元测试通过 ≠ 工具在真实审核中能正确触发。你需要为每个工具设计场景用例——构造包含已知问题的测试文档片段，确认工具在该触发的时候被正确调用、不该触发的时候不被误调、返回结果与预期一致。例如：构造一份招标文件，在报价表中故意写一个超过预算的金额，验证 `validate_calculation` 工具能否被 Agent 正确触发并识别
- 发现工具缺口：与 G2（规则）和 G4（评测）协作——哪些高频问题现在靠 LLM 纯文本推理、错误率很高、应该变成工具？
- 新增工具：基于缺口分析选择优先开发哪些，而非按 V2+ 规划照单全收

**方向 B：Prompt 工程（1 人）**

核心问题：**同样调用 qwen-plus，Prompt 差一行 F1 能差 10 个百分点。** 怎么让 LLM 像资深招标师一样思考——知道关注什么、忽视什么、引用什么证据、给出什么建议？

你的工作：
- 每个 Agent 的 System Prompt：角色定义 + 审查维度 + 证据使用规则 + 输出格式 + Few-shot 示例
- Prompt A/B 测试：每次 Prompt 变更 → 在 G4 评测框架上跑全量 → 对比变更前后的 F1/幻觉率/引用准确率 → 只有全面不退化才合并
- 错误模式分析：G4 评测报告显示某类问题 Precision 很低 → 分析 Agent 的输出 → 找 Prompt 的漏洞 → 修复

**方向 C：领域知识注入（1 人，与 G2/G3 协作）**

核心问题：**检索返回的法规片段，Agent 真的能正确理解和使用吗？** 很多时候不是检索没找到，而是返回的内容不够"Agent 可消费"。

你的工作：
- 检索结果的"Agent 可消费性"优化：不是返回一堆原文，而是返回 Agent 可以直接引用的结构化证据（法规名称 + 条款编号 + 原文 + 适用场景标注）
- 与 G2 协作：规则引擎的结果如何注入 Agent 上下文（"这条规则已经确定性命中了，你重点审它的严重程度和修改建议"）
- 与 G3 协作：优化知识库切片的粒度和元数据格式，让 Agent 引用时准确率更高

#### 输出与接口

```
对 G4 的接口:
  - Agent Prompt: G4 创建 Agent 时读取 G5 维护的 Prompt 模板
  - ToolRegistry: G4 通过 registry.definitions() 获取工具定义 → 发给 LLM
  - 反馈接收: G4 的评测结果 → G5 据此优化 Prompt 和工具

对 G3 的接口:
  - search_knowledge 工具内部调用 G3 HTTP API
  - 领域知识优化建议 → G3
```

### 3.7 G6 知识沉淀引擎（2 人）

#### 职责

审核结束后，将本次审核的精华自动整理入库——写 Neo4j 图数据库（实体+关系）和 Qdrant 向量库（法规/案例 embedding），让 G3 下次检索时命中率越来越高。这是"知识飞轮"的发动机。

> G6 是"生产知识"的一方——它依赖 G4/G5 产出的审核结果（AuditReport + SessionGraph），所以排在 G5 之后。与 G3 形成闭环：**G3 消费知识（读），G6 生产知识（写）。**

#### 子方向 A：Neo4j 图数据库建设（1 人）

构建"法规 → 条款 → 案例 → 风险模式"的关联图，支持图遍历查询。

```
图 Schema 设计:

  (Law:法规)              (Case:案例)
      │                        │
      ├─[:articles]→ (Article:条款)
      │                        │
      └─[:cited_in]←───────────┘
               │
               ▼
          (Risk:风险模式)
               │
               ├─[:found_in]→ (Clause:标书条款)
               ├─[:exemplifies]→ (ProhibitionRule:禁止规则)
               └─[:similar_to]→ (Risk)
```

- 节点类型：Law（法规）、Article（条款）、Case（案例）、Risk（风险模式）、ProhibitionRule（禁止规则）
- 边类型：has_article、cited_in、found_in、exemplifies、similar_to、amended_by
- 去重策略：确定性 ID（SHA256 前 8 位），Neo4j MERGE 自动去重

#### 子方向 B：Knowledge Curator 审核沉淀流水线（1 人）

**素材来源**：审核完成后，系统自动标记值得沉淀的内容（`_curation_mark=true`）：

| 标记条件 | 标记内容 | 原因 |
|---------|---------|------|
| severity=high + Legal Verify verified | 整个 Risk + 关联子图 | 核心判例 |
| 经过 Debate 维持 | Risk + Debate 摘要 | 边界案例 |
| BlindSpot 发现的新风险类型 | Risk + 归类分析 | 改进 Agent |
| 大模型搜索命中的优质法规/案例 | Law/Case 全文 | 避免重复搜索 |

素材以 JSON 快照形式存入 PostgreSQL（G8 配合建 `session_snapshots` 表）。

**Curator Pipeline**（每月 1 日自动触发）：

```
Session Snapshots
    │
    ▼
  Step 1: CuratorDedupAgent (去重清洗)
    规则粗筛 + Agent 精判 → 合并同类/去噪
    │
    ▼
  Step 2: CuratorGraphAgent + CuratorFreshAgent (并行)
    实体抽取 → Neo4j 建图  |  时效性检查 → 标记过期法规/案例
    │
    ▼
  Step 3: CuratorEmbedAgent (向量化)
    新实体 embed → 写入 Qdrant
    │
    ▼
  双库更新完成 → 下次 G3 检索命中率 ↑
```

**MVP 阶段**：Session 快照存储 + 简单规则去重脚本（不调 Agent）。完整 4-Agent Pipeline 第 6 周后启动。

#### 输出与接口

```
对 G8 (SaaS) 的接口:
  POST /internal/session-snapshots    # G4 写快照时调用

对 G3 (检索) 的接口:
  Neo4j + Qdrant 双库直接被 G3 查询（读写分离，G6 写、G3 读）

管理员接口:
  POST /knowledge/curation/trigger    # 手动触发 Curator
  GET  /knowledge/curation/report     # 查看最新整理报告
```

#### 核心指标

| 指标 | 目标 |
|---|---|
| 图遍历耗时 | < 200ms / 2-hop |
| 图节点规模 | ≥ 5000 节点（3 个月积累）|
| 月度新增沉淀 | ≥ 100 条 |
| Curator Pipeline 耗时 | < 20 分钟 / 月 |

#### 工程要点

- G6 是后台异步任务，完全不影响审核主链路（G1→G2→G3→G4→G5）
- Neo4j + Qdrant 独立部署，G6 写、G3 读，读写分离
- 初期可手动触发 Curator，稳定后改为 Cron 自动
- CuratorDedupAgent 的规则粗筛可先用纯规则实现（embedding cosine + exact match），Agent 精判是锦上添花

```

### 7.2 G4 ↔ G5 接口解耦设计（关键）

这是项目中最关键的解耦边界。两组通过 Rust trait + 评测数据双向通信，形成**反馈闭环**（不是单向交付）：

```rust
// ── 正向：G5 → G4（工具 + Prompt 注入）──
// G5 定义（Agent 工具/Prompt 侧）
pub trait AgentTool: Send + Sync {
    fn name(&self) -> &str;
    fn definition(&self) -> serde_json::Value;  // OpenAI tool definition
    async fn execute(&self, args: serde_json::Value) -> Result<serde_json::Value>;
}

pub struct AgentDefinition {
    pub name: String,
    pub system_prompt: String,        // G5 维护的 Prompt 模板
    pub tool_names: Vec<String>,      // 此 Agent 可用的工具列表
    pub max_turns: usize,
    pub complexity: AgentComplexity,
}

// G4 使用（Agent 创建侧）
let registry = ToolRegistry::new();
registry.register(Box::new(ValidateCalculationTool::new()));
// ...

let agent_def = AgentDefinition {
    name: "JudgeAgent",
    system_prompt: include_str!("prompts/judge_agent.md"),  // G5 提供
    tool_names: vec!["search_knowledge", "read_section", "output_finding"],
    max_turns: 8,
};

let agent = Coordinator::spawn_agent(agent_def, registry);

// ── 反向：G4 → G5（评测反馈）──
// G4 每次跑完评测 Pipeline，将结果反馈给 G5：
// {
//   "prompt_version": "v2.4",
//   "precision": 0.73,
//   "recall": 0.84,
//   "f1": 0.78,
//   "regressions": ["参数倾向性检测 Precision -5%"],
//   "improvements": ["资质类 Recall +8%"]
// }
// → G5 据此优化 Prompt 和工具
```

**G5 交付给 G4 的东西**：
1. `ToolRegistry`（包含所有已实现的工具）
2. `Vec<AgentDefinition>`（每个 Agent 的 Prompt + 可用工具列表）
3. `prompts/` 目录下的所有 Markdown Prompt 文件

**G4 反馈给 G5 的东西**：
1. 每周评测报告（按 Agent/问题类型/行业的 Precision/Recall/F1）
2. 幻觉率和推理质量数据（哪类幻觉最多、哪个 Agent 最严重）
3. 工具覆盖率缺口（哪些问题没有合适的工具，纯靠 LLM 推理导致准确率低）

**两者不需要互相知道对方的实现细节**。G4 不碰 Prompt 怎么写，G5 不碰 Agent 怎么调度。但通过评测数据，两者形成完整的"优化 → 验证 → 再优化"循环。
