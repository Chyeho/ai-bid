# 测评驱动开发（EDD）

> 核心原则：**每个组都有一个可量化的评测标准，每周跑一次评测，用数据而非感觉来判断进度。**

---

## EDD 公约

这是 Leader 和每个组的契约。如果你想加入这个项目，先读这五条。

**1. Leader 定义 North Star Metric，团队定义路径。**

Leader 说"Critical Recall 要到 98%"，团队自己决定怎么做到。Leader 不告诉你怎么写 Prompt、用什么工具、怎么设计实验——那是你的领地。

**2. 评测集就是"好"的定义。通过评测 = 做对了，不需要等 Leader 确认。**

如果评测集说你的变更让 F1 从 0.76 提升到 0.79，这就是进步。不需要任何人点头。评测集是你和"好"之间的唯一裁判。

**3. 每周五用数据汇报，不用"我在做"汇报。**

"我这周研究了 PaddleOCR 的参数调优"→ 不合格。"我这周让扫描件表格识别率从 72% 提升到 81%"→ 合格。没有数据的汇报只是在消耗所有人的时间。

**4. 失败的实验和成功的实验同样有价值——只要跑过评测。**

试了 3 种协作模式，发现并行投票反而不如串行 Pipeline？这是重要发现，不是失败。把它写进实验日志，帮后面的人别踩坑。

**5. 如果评测集没覆盖你的贡献，你有责任更新评测集。**

你发现了一个新的审核场景、一种新的幻觉类型、一个之前没人注意的解析边界——把它变成评测用例。评测集是活文档，你是它的共同作者。

## 一、为什么需要 EDD

AI 系统开发最大的风险是**你以为做完了，实际上没做完**。

传统软件开发：代码编译通过 + 手动测一下 = 完成。
AI 系统开发：模型输出看起来对 ≠ 真的对。

EDD 的核心思想：

```
每个组定义自己的评测标准
  → 构建评测集（Ground Truth）
  → 每周自动跑评测
  → 输出一个数字（准确率/召回率/...）
  → 这个数字决定下周做什么
```

**各组评测总览**：

| 组 | North Star Metric | 评测对象 | Phase 2 目标 |
|---|---|---|---|
| G1 文档解析 | 表格识别率 | 50 份真实招标文件 | > 90% |
| G2 规则匹配 | 规则召回率 | 50 份人工标注文档 | > 95%（宁误报不漏报） |
| G3 知识检索 | Top-10 召回率 | 200 条查询→文档标注对 | > 85% |
| G4 Agent 智能 | 审核 F1 Score | 50 份人工标注文档 | F1 > 0.80 |
| G5 领域工具 | 工具执行准确率 | 200 个工具调用测试用例 | > 95% |
| G6 知识沉淀 | 知识增量有效率 | 月度 Curator 产出人工评估 | > 60% |
| G8 SaaS 平台 | API P99 延迟 | 自动化压力测试 | < 500ms |
| G9 前端 | 核心流程可用性 | 5 个用户任务成功率 | > 90% |

## 二、G4 Agent 智能组 — 测评设计

### 2.1 定位

G4 不是"Agent 框架维护组"，而是 **Agent 智能与评测组**。

**核心使命**：让 Multi-Agent 审核系统从"能跑通"变成"审得准"。

**North Star Metric**：审核 F1 Score（在人工标注的 50 份招标文件上的 precision × recall 综合得分）。

### 2.2 三个子方向

```
G4 Agent 智能组（3 人）
  │
  ├── 子方向 A：审核评测框架（1 人）
  │   "Agent 审得准不准，谁说了算？数据说了算。"
  │   构建 Benchmark → 自动化评测 → 准确率 Dashboard
  │
  ├── 子方向 B：Agent 推理质量（1 人）
  │   "Agent 的推理过程能信任吗？"
  │   幻觉检测 → 推理链评分 → 引用验证 → 可解释性
  │
  └── 子方向 C：多 Agent 协作策略（1 人）
      "3 个 Agent 一起审，一定比 1 个好吗？什么时候该协作？"
      协作模式实验 → 动态路由 → 成本-质量权衡 → 可视化
```

### 2.3 子方向 A：审核评测框架

**核心问题**：你说 Agent 准确率 85%，怎么证明？客户凭什么信？

#### 2.3.1 标注数据集

```
构建标书审核 Benchmark
  │
  ├── 数据收集：50 份真实学校采购招标文件
  │   ├── 来源：学校财务处、中国政府采购网、各省采购平台
  │   ├── 覆盖：8 大采购类别（办公设备/信息化/物业/教材/实验室/食堂/工程/安保）
  │   └── 格式多样性：PDF 扫描件 / PDF 电子版 / Word 文档
  │
  ├── 人工标注
  │   ├── 标注员：法律专业同学 2-3 人 + G2 规则组同学
  │   ├── 标注内容：
  │   │   ├── 每条问题的原文位置（block_id + 页码）
  │   │   ├── 问题类型（资质缺失/条款违法/参数倾向/格式违规/日期冲突/...）
  │   │   ├── 严重程度（critical/high/medium/low）
  │   │   ├── 法规依据（法律名称 + 条款编号）
  │   │   └── 是否属于"废标级"问题（yes/no）
  │   └── 标注质量保证：每份文档 2 人独立标注 → 计算标注一致性（Cohen's Kappa > 0.7）
  │
  └── Ground Truth 格式
      {
        "document_id": "doc_001",
        "document_type": "招标文件",
        "industry": "信息化建设",
        "expected_findings": [
          {
            "finding_id": "gt_001",
            "block_id": "b_5_2",
            "page": 5,
            "category": "资质要求不明确",
            "severity": "critical",
            "description": "未明确要求信息系统集成资质",
            "law_ref": "《政府采购法》第二十二条",
            "is_disqualifying": true
          }
        ],
        "expected_negative_count": 0
      }
```

#### 2.3.2 评测指标

| 指标 | 计算方式 | 含义 | Phase 2 目标 | Phase 4 目标 |
|---|---|---|---|---|
| **Precision（精确率）** | TP / (TP + FP) | Agent 报的问题里，多少是真的？ | > 70% | > 85% |
| **Recall（召回率）** | TP / (TP + FN) | 真实问题中，Agent 发现了多少？ | > 85% | > 92% |
| **F1 Score** | 2 × P × R / (P + R) | 综合得分 | > 0.77 | > 0.88 |
| **Critical Recall** | 仅统计 critical 级别的召回率 | 致命问题有没有漏？ | > 95% | > 98% |
| **Finding-level Accuracy** | 完全匹配的 finding 占比（类别+位置都对） | 精确到条款级别的准确率 | > 60% | > 75% |
| **False Positive Rate** | FP / (FP + TN) | 误报率 | < 30% | < 15% |

**为什么 Critical Recall 是最高优先级指标**：漏掉一个"废标级"问题比多报三个 warning 严重 100 倍。宁可误报，不可漏报。

#### 2.3.3 自动化评测 Pipeline

```
每次代码/Prompt 变更
  │
  ▼
触发评测（手动 or CI）
  │
  ├── Step 1: 对 50 份测试文档全部重新跑审核 Pipeline
  │
  ├── Step 2: Agent 输出解析 → 提取所有 finding
  │
  ├── Step 3: Finding 与 Ground Truth 对齐（基于 block_id 匹配 + 文本相似度）
  │   ├── TP: Agent 找到的 = Ground Truth 中存在的
  │   ├── FP: Agent 找到的 ≠ Ground Truth 中不存在的
  │   ├── FN: Ground Truth 中存在的 ≠ Agent 没找到的
  │   └── TN: 不需要计算（审核场景下正常条款太多）
  │
  ├── Step 4: 计算所有指标 → 生成评测报告
  │
  └── Step 5: 回归检测
      ├── 新 Prompt 修了 3 个 FN → ✅ 改进
      ├── 但新增了 5 个 FP → ⚠️ 回归
      └── 自动对比上次评测结果 → 输出 "改进项 / 退化项 / 新增漏报"
```

#### 2.3.5 竞品对标

同一份招标文件，三种审核方式对比：

| 审核方式 | Precision | Recall | 耗时 | 成本 |
|---|---|---|---|---|
| 人工审核（法律专业学生） | 0.90 | 0.85 | ~2 小时 | 人力成本 |
| GPT-4 直接审（Zero-shot） | 0.65 | 0.70 | ~2 分钟 | ~$0.50/文档 |
| **我们的系统** | **目标 0.85** | **目标 0.90** | **< 5 分钟** | **< ¥1/文档** |

> 如果我们的系统在 F1 上超过 GPT-4 Zero-shot 且接近人工，这就是可销售的。

### 2.4 子方向 B：Agent 推理质量

**核心问题**：Agent 的推理过程经得起法律场景的推敲吗？

#### 2.4.1 幻觉检测

| 幻觉类型 | 检测方式 | 示例 |
|---|---|---|
| **法规幻觉** | Agent 引用法律条文 → 在 G3 知识库（法规原文）中全文搜索 → 验证条款是否存在且内容一致 | Agent："根据《招标投标法》第 25 条..."→ 自动验证 → 第 25 条不存在 → **幻觉** |
| **原文幻觉** | Agent 引用 block_id + source_quote → 回溯到 G1 ParsedDocument 中该 block 的原文 → 逐字比对 | Agent："招标文件要求 CPU ≥ 64 核"→ 回溯原文 → 原文写的是"CPU ≥ 32 核"→ **幻觉** |
| **数值幻觉** | Agent 输出数值 → 交叉验证该数值是否来自文档原文或合法外推 | Agent："预算 500 万，最高限价 600 万"→ 文档只提了 500 万 → 600 万从哪来的？→ **幻觉** |
| **推理跳跃** | Agent 跳过关键推理步骤直接跳到结论 → 标记为 suspicious | Agent："资质不满足"但没说哪条资质、哪个条款 → **不完整推理** |

**幻觉率 Dashboard**：

```
每周幻觉率统计
├── 法规幻觉率：12% → 目标 < 5%
├── 原文幻觉率：8% → 目标 < 3%
├── 数值幻觉率：5% → 目标 < 2%
└── 推理跳跃率：20% → 目标 < 10%
```

#### 2.4.2 推理链质量评估

**好的推理链标准**：Observation → Evidence → Rule → Conclusion，每步可追溯。

```
评分维度（1-5 分）：
├── 证据充分性：结论引用了足够的原文证据和法规依据？
├── 逻辑有效性：从证据到结论的推理是否成立？
├── 完整性：是否考虑了反方论点（被告知为什么这不是误报）？
├── 可追溯性：每步推理是否可以追溯到原文或法条？
└── 简洁性：推理是否直接、不绕弯？

评分方式：
├── LLM-as-Judge：用 GPT-4 作为裁判，按上述 5 个维度打分
├── 人工抽查：每周抽取 20 条推理链，G4 同学人工验证 LLM-as-Judge 的评分是否合理
└── 推理链得分 < 3.0 → 自动标记 low_confidence → 走 HumanReview
```

#### 2.4.3 引用准确性

```
Agent 输出的每条 finding 包含：
├── block_id：是否指向正确的原文位置？（回溯 G1 验证）
├── law_ref：引用的法条是否存在且版本正确？（回溯 G3 验证）
├── source_quote：引用的原文是否逐字准确？（与原文比对）
└── evidence_id：引用的知识库证据是否存在？（回溯 G3 验证）

引用准确率 = 四项全部正确的 finding 数 / 总 finding 数
Phase 2 目标：> 80%
Phase 4 目标：> 95%
```

#### 2.4.4 可解释性增强

从"我们认为有问题"升级为：

> 因为**《政府采购法实施条例》第二十条**规定"采购人不得以不合理的条件对供应商实行差别待遇"，而招标文件**第 12 页**要求"投标人须在东莞市注册"，这构成**地域限制**，属于**排斥性条款**。

```
可解释性模板：
├── 发现了什么：[风险描述]
├── 在哪发现的：[原文位置 + 引用原文]
├── 为什么是问题：[法规依据 + 法规原文]
├── 严重程度：[critical/high/medium/low] + 理由
├── 修改建议：[具体怎么改]
└── 类似案例：[历史废标案例参考]
```

### 2.5 子方向 C：多 Agent 协作策略

**核心问题**：3 个 Agent 一起审，一定比 1 个 Agent 审得好吗？

#### 2.5.1 协作模式对比实验

用同一批 50 份测试文档，对比 4 种模式的 F1 Score 和成本：

| 模式 | 描述 | 预期 Precision | 预期 Recall | 预期成本/文档 |
|---|---|---|---|---|
| **Baseline** | 单 Agent（JudgeAgent 独立审核） | 低（没有交叉验证） | 中 | ¥0.30 |
| **Pipeline** | RuleAgent → JudgeAgent → CriticAgent 串行 | 中（Critic 过滤误报） | 中 | ¥0.50 |
| **Parallel+Vote** | 3 个 Agent 独立审 → 2/3 投票 | 高（多数一致才保留） | 低（可能漏掉只有 1 个 Agent 发现的） | ¥0.90 |
| **Debate** | Judge 提出 → Critic 反驳 → Judge 修正 | 很高（辩论过滤） | 高（修正过程发现遗漏） | ¥1.50 |

**核心研究问题**：
- 在什么条件下，多 Agent 显著优于单 Agent？
- 辩论模式额外消耗的 token 是否值得？（∆F1 / ∆cost）
- 能否按问题复杂度自适应选择模式？（简单问题单 Agent，复杂问题多 Agent）

#### 2.5.2 动态路由策略

```
当前路由：关键词匹配（硬编码）
  ├── 问题：文档类型变了（工程→货物），路由逻辑不会自动调整
  └── 结果：不该审的 Agent 也在审，浪费 token

目标路由：基于文档特征的智能路由
  │
  ├── Step 1：文档类型分类
  │   ├── 输入：G1 输出的 ParsedDocument 摘要（目录+关键章节标题）
  │   ├── 方式：LLM 小模型（qwen-turbo）分类 → {工程招标, 货物采购, 服务招标}
  │   └── 准确率目标：> 95%（分类任务简单）
  │
  ├── Step 2：Agent 组合选择
  │   ├── 工程招标 → [RuleAgent, JudgeAgent, CriticAgent] — 审查资质+工期+工程量清单
  │   ├── 货物采购 → [RuleAgent, JudgeAgent] — 审查参数倾向+品牌指定（不需要 Critic）
  │   └── 服务招标 → [RuleAgent, JudgeAgent, CriticAgent] — 审查人员资质+服务标准
  │
  └── Step 3：成本-质量自适应
       ├── 简单条款 → 规则引擎直出（零 API 成本）
       ├── 中等条款 → 单 Agent + qwen-plus（¥0.02/条款）
       ├── 复杂条款 → 双 Agent 辩论 + qwen-max（¥0.10/条款）
       └── 废标级条款 → 三 Agent 共识（¥0.20/条款，但绝对不能出错）
```

## 三、各组测评设计

EDD 不只适用于 G4。每个组都应有自己的评测标准。

### 3.1 G1 文档解析 — 解析质量测评

**North Star Metric**：表格识别率
