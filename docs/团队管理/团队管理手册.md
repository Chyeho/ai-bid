# 团队管理手册

> 给第一次带技术团队的你。基于 Anthropic、Spotify、Shopify、Snowflake 等团队的实践，适配 10 周学生项目的场景。

---

## 一、你的角色：从 coder 到 leader

### 1.1 你的工作变了

| 以前（coder） | 现在（leader） |
|---|---|
| 写出最好的代码 | 让别人写出最好的代码 |
| 解决最难的技术问题 | 把问题分解成别人能解决的大小 |
| 自己的效率 | 团队的整体产出 |
| 被评估代码质量 | 被评估团队是否在正确的方向上进步 |

**核心公式**：你现在的产出 = 团队每个人的产出 × 你消除的摩擦。

> 来自 PostHog 的标准："如果你能消失两周，团队的发布频率和质量不受影响——你就是成功的 Leader。"

### 1.2 Leader 只做三件事

```
1. 定义方向（Alignment）
   ├── 我们要去哪？（产品愿景 + 阶段目标）
   ├── 为什么是现在？（紧迫感）
   └── 怎么算到了？（North Star Metric）

2. 消除障碍（Enablement）
   ├── 缺资源？→ 去找
   ├── 被阻塞？→ 去疏通
   └── 不明白？→ 去解释

3. 建立文化（Culture）
   ├── 什么行为被奖励？什么被纠正？
   ├── 失败的实验是浪费还是学习？
   └── 团队成员敢不敢说"我不懂"？
```

**不做的事**：分配具体任务、检查每行代码、替人做决策、当所有问题的答案。

## 二、团队结构

### 2.1 最小组（Pod）设计

Anthropic 的核心发现：2-4 人的 Pod 是最高效的作战单元。对齐到你的项目：

| 组 | 人数 | Pod 内部细分 |
|---|---|---|
| G4 Agent 智能 | 3 | 评测框架(1) + 推理质量(1) + 协作策略(1) — 每人独立方向 |
| G5 领域工具 | 3 | 工具研发(1-2) + Prompt工程(1) — 紧密协作 |
| G2 规则匹配 | 2 | 领域建模(1) + 规则实现(1) — 配对工作 |

**关键**：每个 Pod 内的成员不需要互相等待。如果一个人依赖另一个人才能工作，说明 Pod 设计有问题。

### 2.2 组长不是"小 Leader"

组长不是管人的，是**信息枢纽**。组长的职责：

| 做什么 | 不做什么 |
|---|---|
| 确保组内信息透明（谁在做什么、遇到什么问题） | 替组员做技术决策 |
| 每周五代表小组汇报数据 | 替组员写代码 |
| 在跨组联调时做接口对接人 | 替组员参加所有会议 |
| 发现组员被阻塞时主动求助 Leader | 微管理组员的每日安排 |

## 三、会议节奏

### 3.1 越少越好，但要准时发生

业界共识：**过多的会议是第一生产力杀手**。给 10 周项目的建议节奏：

| 会议 | 频率 | 时长 | 干什么 | 不干什么 |
|---|---|---|---|---|
| **全员站会** | 周一、三、五 | 15 分钟 | 每人 1 分钟：昨天做了什么、今天做什么、被什么阻塞 | 不讨论方案、不展开技术细节 |
| **1:1 面谈** | 每周每人 1 次 | 20 分钟 | 聊职业发展、聊困惑、聊"你觉得哪里不对" | 不聊进度——那是站会的事 |
| **周五数据评审** | 每周五 | 30 分钟 | 各组展示 North Star Metric 变化 | 不展示 PPT——只展示数据和实验结论 |
| **跨组联调** | 每周五下午 | 2 小时 | 上下游接口对接、Mock 验证 | 不讨论新需求 |
| **双周回顾** | 每两周 | 45 分钟 | 团队回顾：什么做得好？什么能更好？下周做什么？ | 不指责个人 |

### 3.2 1:1 是 Leader 最重要的工具

Pluralsight 2025 的研究：有定期 1:1 的员工**敬业度高出 3 倍**。

**1:1 的正确姿势**：

```
前 10 分钟：听对方说
  "这周有什么让你兴奋的？有什么让你沮丧的？"
  "你觉得哪里效率不够高？"
  "有没有什么事情你觉得应该做但我们没在做？"

中间 5 分钟：你说
  "我观察到你做得很好的地方是..."
  "我有一个建议..."

最后 5 分钟：对齐下周
  "下周你最想推进的一件事是什么？"
  "需要我帮你解决什么问题？"
```

**1:1 绝对不要做的事**：检查进度、追问"那个bug修完了吗"、变成批斗会。

### 3.3 站会不走形式

如果有人说"一切正常"三天了，但 North Star Metric 没变——说明"一切正常"是假的。

**好站会**：每人 60 秒，说清楚三件事。有人被阻塞？会后 2 人单独聊。站会结束。

**坏站会**：15 分钟变成 40 分钟技术讨论，所有人听着两个人争论架构细节。

## 四、委托与授权

### 4.1 "问题分配"代替"任务分配"

这是整个管理手册里最重要的一节。

| 任务分配（坏） | 问题分配（好） |
|---|---|
| "你写一个幻觉检测模块" | "Agent 会编造法律条文——你怎么让幻觉率降到 5% 以下？" |
| "你优化 Coordinator 并发" | "3 个 Agent 串行 vs 并行——哪种更准？用数据说话" |
| "你维护 Prompt 模板" | "参数倾向性检测的 F1 现在只有 0.62——你觉得问题出在哪？" |

**为什么**：任务分配让人变成执行者（"Leader 已经想好了，我只是写代码的"），问题分配让人变成探索者（"这是一个值得研究的问题，我来找到答案"）。

### 4.2 委托的五个层次

让你知道什么时候该插手、什么时候该放手：

| 层次 | 你做什么 | 团队成员做什么 | 适用场景 |
|---|---|---|---|
| L1: 我来做，你看着 | 你做，边做边讲 | 观察、提问 | 新人第一天 |
| L2: 我们一起做 | 你做核心，对方做辅助 | 参与、尝试 | 第一周 |
| L3: 你做，我在旁边 | 对方做，你随时可以接手 | 独立执行，有安全网 | 第二周 |
| L4: 你做，做完给我看 | 只在关键节点检查 | 独立拥有 | 正常状态 |
| L5: 你全权负责 | 只在对方求助时出现 | 完全自主 | 信任建立后 |

**目标**：2 周内把每个团队成员从 L1 推到 L4。如果有人在 L3 以下超过 2 周，要么你没给够信任，要么他没准备好。

### 4.3 退出机制：别"买回"已委托的任务

当团队成员遇到困难向你求助时，**最容易犯的错误是把任务拿回来自己做**。

```
❌ "这个比较复杂，我来处理吧。"
✅ "你觉得卡在哪里？需要什么资源？有什么我能帮你解除的障碍？"
```

如果你每次都"买回来"，团队学到的不是"困难时要找 Leader 帮我"，而是"困难时等着，Leader 会接手"。

### 4.4 "我打算"方法

来自 David Marquet 的 *Turn the Ship Around!*（2025 年管理文章引用最多的来源之一）：

**不要等你去分配任务**。让团队成员主动向你提出："我打算做 X，目的是 Y，预期结果是 Z——你觉得可以吗？"

你只需要说"可以"或者"考虑一下 A/B 风险，然后继续。"

这能做到三件事：① 团队学会主动思考 ② 你不用猜每个人在做什么 ③ 决策权在正确的人手里。

## 五、反馈与心理安全

### 5.1 Google 项目亚里士多德的结论

Google 研究了 180+ 个团队，发现**心理安全（psychological safety）是高效团队的第一预测因素**——比其他所有因素（能力、经验、资源）都重要。

**心理安全的定义**：团队成员敢不敢冒人际风险——说"我不懂"、"我搞砸了"、"我不同意你的方案"——而不必担心被惩罚或被认为无能。

**在一个心理安全的团队里**：
- 有人主动说"这个东西我不理解，能再讲一遍吗"
- 有人主动说"我上周的方向好像不对，想换一个思路"
- 代码评审时讨论的是代码，不是人
- 失败被公开讨论，不被隐藏

**在一个心理不安全的团队里**：
- 遇到问题不说，直到最后一天才发现
- 代码评审变成人身攻击或敷衍
- 失败被隐藏，直到变成更大的失败
- 只有意见最大的人说话，其他人都沉默

### 5.2 Leader 怎么建立心理安全

**最重要的工具：你自己先脆弱。**

在团队面前说："这个我也不确定，你们觉得呢？"
在出错时说："这个决策是我做的，结果不好，我来承担。"
在某人不发言时说："XX 之前做过类似的，你怎么看？"

**第二个工具：区分"可以归咎的失败"和"学习机会"。**

研究显示只有 2-5% 的失败是归咎于个人的（偷懒、恶意、违反明确规则）。但 70-90% 的失败被*当作*归咎性失败处理——这扼杀了所有创新。

你的规则：
- 团队尽了全力但方向错了 → 学习机会，记录下来
- 团队尝试了一个风险方案但失败 → 庆祝他们有勇气尝试
- 团队偷懒、敷衍、隐瞒 → 这才是需要严肃对待的

### 5.3 怎么给人反馈

**SBI-I 模型**（最广泛使用的反馈框架）：

| 步骤 | 意思 | 例子 |
|---|---|---|
| **S**ituation | 具体场景 | "上周五的代码评审中..." |
| **B**ehavior | 客观行为，不加判断 | "你连续三次直接说'这样写不对'，没有解释为什么" |
| **I**mpact | 造成的影响 | "对方可能觉得被否定而不是被帮助，评审的氛围变冷了" |
| **I**ntent | 澄清意图（可选） | "我知道你的初衷是帮代码变得更好" |

**正向反馈也要具体**：
- ❌ "做得不错"
- ✅ "上周你在评审中，对那个内存泄漏的怀疑是对的——你坚持往下挖，结果真的找到了根因。这种不放过任何疑点的态度，就是我希望团队学习的。"

## 六、新人入职

### 6.1 第一周目标：周五前 merge 一个真实 PR

业界最强共识：**新人第一天就应该接触真实代码**。不要给"练习任务"——那等于告诉对方"我们还不能信任你做真正的工作"。

**你的第一周清单**：

| 时间 | 做什么 |
|---|---|
| **入职前** | 环境一键安装脚本就绪（`./setup.sh`），账号全部开通，文档准备好了 |
| **Day 1** | 介绍团队、跑通代码、分配一个 mentor（同组的学长/学姐） |
| **Day 2-3** | 分配第一个"穿行任务"：修改一个日志级别、修复一个已知小 bug、添加一个单元测试 |
| **Day 4-5** | 第一个 PR merge，周五 Demo 展示自己做了什么 |

**一小时规则**：告诉新人"自己试一小时，解决不了必须马上问"。这防止了两个极端：每 5 分钟问一次（没独立思考）和闷头三天不出声（陷入困境）。

### 6.2 Mentor 制度

**每个新人配一个 mentor**，不是"全组共同指导"（那等于没人指导）。

Mentor 的工作：
- 每天 10 分钟快速对一下（"今天有什么卡住的？"）
- 新人的前三个 PR 优先 review
- 回答"傻问题"

Mentor 不是"替新人写代码的人"。如果 mentor 觉得自己在替对方工作，那方法就错了。

## 七、防止倦怠

### 7.1 倦怠不是你个人的失败——是流程的失败

研究反复证明：**倦怠不是意志力问题，是系统问题**。一个人加班到凌晨两点，不说明他努力，说明团队的时间估算、任务分解或优先级管理出了问题。

### 7.2 早期信号

| 信号 | 你应该做什么 |
|---|---|
| 站会上开始沉默 | 当天 1:1 私聊——"最近怎么样？"（不问进度） |
| "我自己搞就行，不用帮忙" | 他可能在挣扎但不好意思求助——派 mentor 看看 |
| 开始缺席非强制性会议 | 可能是时间压力——检查任务量是否合理 |
| 代码质量突然下降 | 可能是在赶进度——检查交付压力来自哪里 |

### 7.3 预防机制

- **每天硬性结束时间**——哪怕是"建议"性的，让人有借口停下来
- **小胜利公开庆祝**——不要等到项目结束才庆祝，每解决一个难题、每提升一个指标都值得被看见
- **轮换任务**——有人在一个问题上卡了三天？给他一个完全不同的任务换换脑子
- **你做榜样**——如果你自己在凌晨两点发消息、周末在群里催进度，你说的"注意休息"等于零

## 八、Leader 的自我管理

### 8.1 你也会倦怠

第一次带团队最容易犯的错误：以为自己是超人。你也在写代码、也在做设计、也在协调、也在安抚情绪——你的角色是最累的。

**保护自己**：
- 你每周至少有一天完全不看工作消息
- 找一个可以倾诉的人（不是你的团队成员）——前任、同学、导师
- 记录"今天我帮团队解决了什么障碍"——这是你作为 Leader 的"可见产出"
- 如果你的 North Star Metric 是团队的产出，你的"个人 coding 量"下降是正常的，不是你变差了

### 8.2 最危险的时刻

**项目中期（W4-W6）** 是团队最脆弱的时刻：
- 最初的兴奋感过去了
- 核心链路还在调试，看不到成果
- 各组开始遇到真正的技术困难
- 时间过半，但看起来离完成还很远

**你需要做的**：
- 在这个阶段 **增加 1:1 频率**（每周两次）
- 公开承认困难——"我知道现在是项目最难的阶段，这很正常"
- 找出并展示任何可见的进展——哪怕只是"G1 终于能正确解析那个表格了"
- 重新讲一遍 WHY——"10 周后，当这个产品能自动审核招标文件的时候..."

### 8.3 什么时候该坚持，什么时候该变通

| 该坚持 | 该变通 |
|---|---|
| North Star Metric 不变 | 达到它的路径可以换 |
| 阶段交付时间不变 | 交付范围可以砍 |
| EDD 公约不变 | 评测集的内容可以改 |
| 团队文化不变 | 具体流程可以调 |

## 九、模板与清单

### 9.1 每周五数据评审模板

```markdown
## [组名] 第 X 周数据评审

**North Star Metric**：[指标名]
- 上周：[数字]
- 本周：[数字]
- 变化：[+/- X%]

**本周做了什么**：
- [1-2 句话]

**一个成功的实验**：
- [做了什么 → 数据变化 → 学到了什么]

**一个失败的实验**：
- [做了什么 → 数据变化 → 学到了什么]

**下周赌哪个方向**：
- [方向] — 预期影响：[指标变化预估]

**需要帮助**：
- [阻塞项]
```

### 9.2 1:1 对话模板

```
开场（任选）：
  - "这周最让你兴奋的一件事是什么？"
  - "如果有一个地方你觉得我们浪费了时间，是哪里？"
  - "你最近学到了什么新东西？"

中间：
  - 如果是正向反馈："我注意到你在 XX 上做得很好，具体来说..."
  - 如果是改进建议："有一个地方我想给你一个建议..."

收尾：
  - "下周你最想搞定的一件事是什么？"
  - "有什么我能帮你移除的障碍吗？"
```

### 9.3 双周回顾模板

```markdown
## 双周回顾 — 第 X-Y 周

**什么做得好？（Keep doing）**
1.
2.
3.

**什么可以更好？（Improve）**
1.
2.

**我们不该再做什么？（Stop doing）**
1.

**下周最重要的三件事**
1. [负责人]
2. [负责人]
3. [负责人]

**North Star Metrics 总览**
| 组 | 指标 | 当前值 | 趋势 |
|---|---|---|---|
| G1 | 表格识别率 | 88% | ↑ +3% |
| G2 | 规则召回率 | 91% | → |
| ... | ... | ... | ... |
```

### 9.4 项目启动 Day 1 清单

- [ ] 每人拿到环境一键安装脚本，跑通 `cargo run`
- [ ] 每人能讲清楚：我们要做什么产品、给谁用、他们为什么愿意付钱
- [ ] 每人知道自己属于哪个组、组的 North Star Metric 是什么
- [ ] 每人认识自己的 mentor（如果是新人）或知道自己 mentor 谁
- [ ] 每人知道：站会时间、1:1 时间、周五评审时间
- [ ] 每人读了 EDD 公约
- [ ] Leader 讲了 WHY：为什么这个项目值得他们投入 10 周
